# 旧接口与源码缺陷清单（ok112 后端逆向）

> **前置硬性约束**：数据库 `audioserver.sql` 表结构完全锁定。
> 本文档给出的**所有优化思路均为代码实现层面**，**禁止**通过新增字段、修改字段类型、加索引、加外键、建视图/触发器等 DDL 手段修复问题。
> 凡是"改 SQL 写法、改分页算法、改递归实现、改事务/锁范围、改参数绑定"的方案都是允许的；凡是需要动 schema 的方案一律不采纳。

## 0. 系统技术形态速览

| 项 | 现状 |
|---|---|
| 语言/框架 | PHP + Smarty（`<{ }>` 定界符），无 MVC 分层，页面即控制器 |
| 数据访问 | `mysqli_*` 过程式 API，**全部为字符串拼接 SQL，无预处理语句** |
| 入口形态 | 每个业务页一个 PHP 文件（295 个明文 PHP + 7 个被 PM9SCREW 加密） |
| 写操作总入口 | **`do.php` 单文件 30605 行**，`switch($_GET['act'])` 分发 200+ 分支 |
| 会话 | PHP `$_SESSION`，键：`admin_id`/`username`/`userid`/`user_right`/`servermodel`/`language`/`serverip`/`registerflag`/`tran_mid_value` |
| 与后台服务通信 | UDP/TCP socket，文本命令 `type?state=X&id=Y`，另有定长二进制 SDK 协议 |
| 加密文件 | `adadd.php` `addfile.php` `admin.php` `application.php` `dataselect.php` `left.php` `phptest.php` —— **无法逆向，需按行为黑盒补齐** |

## 1. 旧接口清单

### 1.1 接口约定说明

- 旧系统**没有 REST 接口**。所有"接口"是两类：
  - **页面型**：`xxx.php?参数` → 直接输出 HTML（Smarty 渲染）
  - **动作型**：`do.php?act=xxx&参数` → 执行写操作后 `echo <script>` 跳转/刷新
- 返回值均为 HTML/JS 片段，**没有结构化响应体**，没有状态码语义。
- 少数 AJAX 接口返回裸文本或 JSON-RPC 片段。

### 1.5 媒体上传

#### `fileadd.php` → 上传页；`uploadfile.php` → 实际接收

| 项 | 内容 |
|---|---|
| 方式 | POST（plupload 分片），`uploadfile.php?folderid=<folderid>` |
| 入参 | 文件流；`name`/`chunk`/`chunks`；`folderid` |
| 前端限制 | 仅 `mp3`/`wav`；单文件 ≤300MB |
| 业务流程 | ① 写临时文件 `link/backup/mediadata/<time+rand>.mp3.part` ② 分片合并后重命名 ③ **调 ffmpeg 转码**：统一 mp3、`folderid==9`（提示音）→ 16000Hz，否则 44100Hz，并 `concat` 追加 2 秒静音 ④ 删源文件 ⑤ `chmod 777` ⑥ 按 `(name, folderid)` 判定新增或覆盖 ⑦ 向广播服务发 `file?state=1&id=<folderid>` |
| 原有 SQL（查重） | `SELECT media.name,filename,media.id FROM media WHERE media.name='$oldName_f' AND media.folderid='$folderid'` |
| 原有 SQL（新增） | `INSERT INTO media (media.name,size,typeid,priority,filename,folderid,timelength,channel,sample,bitrate,userid) VALUES('$oldName_f','$filesize','mp3','0','$newfilepaths',$folderid,'0',0,0,0,$userid)` |
| 原有 SQL（覆盖） | `UPDATE media SET size='$filesize',timelength=0,sample='0',bitrate='0',filename='$newfilepaths' WHERE media.id='$getid'` |
| 返回 | JSON-RPC `{"jsonrpc":"2.0","result":null,"id":"id"}` |

> ⚠️ 新增/覆盖时 **`timelength`、`sample`、`bitrate`、`channel` 全部写 0**，真实值由**后台 C 服务扫描后回填**。这是新旧共存的关键契约（见兼容性说明）。

#### `do.php?act=fileadd_msg` —— 历史批量登记接口（已基本废弃）

| 项 | 内容 |
|---|---|
| 方式 | POST `folderid`/`oldNameArr`/`newNameArr`（逗号分隔的新旧文件名串） |
| 业务流程 | **函数内 `#if 0 ... #else ... #endif` 是 C 风格注释，在 PHP 中不生效 → 两段代码全部执行**。前半段用未定义变量 `$newfile_name`/`$newfile` 做 `copy()` 和 `INSERT`，后半段再循环 `INSERT` 一遍 |
| 原有 SQL | `INSERT INTO media (name,filename,folderid,size) VALUES ('$oldNameArr[$i]','$newNameArr[$i]','$folderid',0)` |

## 2. 源码缺陷清单

> 编号 `D-xx`。每条给出：现象 → 根因 → **代码层修复方案（不动 schema）**。

### 2.1 安全类

#### D-01 全站 SQL 注入（**最高危**）

- **现象**：几乎所有 SQL 都是 `"... WHERE x='$_GET[y]'"` 直接拼接。`media_file.php` 的 `$get_folder_id`、`filefoldermanager.php` 的 `searchvalue`、`do.php` 中 `$_GET['id']` 逗号串等全部未做参数化。
- **根因**：无预处理层；防护手段仅是 `login` 里对 `and`/`or`/`updatexml` 的关键字黑名单（可被大小写/编码/注释绕过）。
- **代码层修复**：
  1. 数据访问统一收敛到一个 Repository/DAO 层，**全部改为预处理 + 参数绑定**（PDO / mysqli prepared statement）。
  2. 逗号分隔的 ID 串（`id=1,2,3`）改为：先 `explode` → 逐个 `intval`/整数正则校验 → 过滤空值与非法值 → 再用 `implode` 生成占位符 `?,?,?` 绑定，**绝不把原串拼进 SQL**。
  3. 排序字段走**白名单映射**（`{'size'=>'media.size','id'=>'media.id'}`），不接受用户传入的列名。
  4. `LIKE` 关键字对 `%` `_` `\` 做转义后再绑定。
  5. 移除关键字黑名单，改为纯参数化。
- **不涉及 DDL**：查询的表名列名完全不变。

#### D-02 任意文件读取 / 目录穿越（`download_media_file.php`）

- **现象**：接口不校验会话，`file_name` 参数直接拼进物理路径；虽有"遍历目录逐个比对文件名"的间接限制，但 `Content-Length` 用的是**未过滤的 `$media_path`**，且逻辑上仍可被构造。
- **根因**：以 URL 参数为路径来源，而非以数据库记录为准。
- **代码层修复**：
  1. 接口改为只接受 `mediaId`，**查 `media` 表拿 `filename`**，用户不能直接指定路径。
  2. 校验会话与"媒体权限"。
  3. `basename()` + `realpath()` 双重规范化，并断言结果仍在媒体根目录之内。
  4. 下载名从 `media.name` + `media.typeid` 生成，用 RFC 5987 编码，去掉 gb2312 转换。
  5. 用流式输出替代 `opendir` 全目录遍历。

#### D-03 命令注入 + 危险的 `system()` 调用

- **现象**：
  - 删除：`system("rm -rf link" . $row['filename'])` —— `filename` 来自库，若被写入含空格/分号的值即为命令注入；且 `rm -rf` + 拼接一旦 `filename` 为空 → **`rm -rf link`，直接删掉整个媒体链接目录**。
  - 上传：`ffmpeg -i <path> ... -y <path>`、`cmdhost --cmd="chmod 777 ..."` 均为字符串拼接。
- **代码层修复**：
  1. 删除物理文件改用 PHP `unlink()`，不走 shell。
  2. 必须调外部程序时用 `proc_open`/`escapeshellarg` 逐参转义，**绝不拼整条命令行**。
  3. 删除前断言路径非空且位于媒体根目录内，空值直接跳过并记警告。
  4. 取消 `chmod 777`，改为按最小权限设置属主与 0640/0750。

#### D-04 万能验证码后门 `htjy123`

- **现象**：`checknum == "htjy123"` 时同时跳过验证码校验**和密码校验**，直接以该用户名登录。
- **代码层修复**：**直接删除该分支**。如需自动化/运维通道，改为独立的、可审计的 API Token 机制。

#### D-05 密码为无盐 MD5

- **现象**：`md5(password)` 存 `book_admin.userpwd`。
- **约束冲突**：`userpwd varchar(100)` 字段长度足够放 bcrypt（60 字符），但**新旧系统共用一套库**，旧程序仍会用 MD5 比对 → 不能单方面改哈希算法。
- **代码层修复（兼容优先）**：
  1. **保持写入格式为 MD5**，确保旧系统可正常登录（这是共存的硬要求）。
  2. 在新版**接入层**补强：登录失败次数限制（用现有 `logincheck` 表）、验证码强校验、会话固定攻击防护、传输层强制 HTTPS。
  3. 把"升级为强哈希"列为**旧系统下线后**的独立迁移项，本期不做。

#### D-06 会话与越权

- **现象**：`verifysessionvalid()` 只判会话是否为空，不判过期、不重新生成 session id；`download_media_file.php`、`get_tree.php`、`uploadfile.php` 等无会话校验；权限只在**渲染层**用 JS 置灰链接，**服务端动作接口 `do.php` 并不重新校验权限**。
- **代码层修复**：
  1. 统一鉴权中间件：**每个写接口在服务端强制校验**"已登录 + 具备对应权限 + 备机模式拒写"，前端置灰只作为体验优化。
  2. 会话超时 + 登录后 `session_regenerate_id(true)`。
  3. 越权判定下沉到数据层：查询本身就带上"归属过滤条件"，而不是查完再判断。

### 2.2 递归与树结构类

#### D-07 文件夹树三层写死，第四层被注释（**核心缺陷**）

- **现象**：`media_folder_tree.php` 与 `get_filelist()` 都是三重嵌套 `while`，第四层递归代码被 `/* */` 注释。
- **影响**：
  - 数据库中允许存在任意深度（`parentid` 无层数约束），第 4 层及以下文件夹**在 UI 上完全不可见**，但数据真实存在，媒体也在里面 → **孤儿目录**。
  - `media_file.php` 的"能否建子目录"判定（`parentid ∈ {0,1,2,3,4,5}`）与树的三层渲染耦合，硬编码顶层库 ID。
- **代码层修复（不动 schema）**：
  1. **一次性取全表构树**（`filefolder` 量级很小）：`SELECT id,name,userid,priority,parentid,createtime FROM filefolder` → 在内存里按 `parentid` 建邻接表 → 迭代（非递归）构建任意深度树。
  2. **环路防护**：构树时用 `visited` 集合，检测到 `parentid` 成环立即断开并记录告警（旧数据可能存在脏的 `parentid`）。
  3. **深度上限保持业务语义**：仍在**业务层**限制"最多 3 层"（与旧系统一致），但**读取时完整展示已存在的深层数据**，避免孤儿不可见。是否放开层数由产品决策，与库结构无关。
  4. 顶层库 ID 白名单（1~9）从散落的硬编码改为**单一常量配置**。

#### D-08 删除文件夹只递归一层 → 孤儿数据

- **现象**：`folderdel_msg` 删完本级后，只处理了 `parentid IN ($ids)` 这一层子级，孙级及以下不处理。
- **代码层修复**：
  1. 先用 D-07 的内存树，**自顶向下收集整棵子树的全部文件夹 ID**（迭代 BFS/DFS，带 visited 防环）。
  2. 对整棵子树的媒体统一做"引用校验 → 物理删 → 关联清理 → 删记录"，最后统一删文件夹。
  3. 全程在**一个事务**内完成（见 D-11）。

#### D-09 递归拼接 IN 字符串的通用风险（含 C 层同构问题）

- **现象**：本系统（PHP 层与后台 C 层同构）普遍采用"递归遍历文件夹 → 把 id 拼成 `IN (1,2,3,...)` 字符串"的做法。C 层用固定尺寸字符数组累加拼接，**深层/宽层目录时溢出**；PHP 层则会产生超长 SQL。
- **代码层修复（不动 schema）**：
  1. **禁止拼接字符串**：ID 收集结果用**整型数组**承载，长度只受内存约束。
  2. 查询下发时**分批**：每批固定 N 个（建议 500~1000）生成 `?` 占位符绑定，多批结果在应用层合并。
  3. 或改用**单条自连接/子查询**避免下发大 IN：如"取文件夹及其子孙下的媒体"可在应用层先算出 ID 集合再分批查，**仍然只查 `filefolder.id/parentid` 与 `media.folderid`，不引入任何新字段**。
  4. C 层若需同步整改：用动态增长缓冲（`realloc`）或直接分批下发，**杜绝定长栈数组 + `strcat`**；每次追加前校验剩余容量。

#### D-10 `get_folder_info()` 的读操作带写副作用

- **现象**：查 `parentid==5`（录音库）时，若不存在名为"录音媒体库"的子目录，函数会**自动 INSERT 一条文件夹**，并 `UPDATE media SET folderid=<新ID> WHERE folderid=5` —— **一个"取列表"的函数在做数据迁移**。
- **影响**：并发渲染树时可能重复插入；语言切换会导致按不同语言的名字反复创建目录；读接口不可缓存。
- **代码层修复**：
  1. 读函数**纯读**，移除所有写逻辑。
  2. 把"录音库归档子目录"的保障逻辑抽成**独立的、幂等的初始化/维护任务**（启动时或定时执行一次）。
  3. 该子目录名**不再随界面语言变化**，固定为中文名，翻译只在展示层做（否则英文环境会创建出第二个目录）。

### 2.3 分页类

#### D-11 分页"总页数"硬编码除以 18

- **现象**：`pagination.class.php::calculate()` 第一行：
  `ceil($this->total_pages/18)` —— 用**字面量 18**，而下方真正的 `$lastpage = ceil($this->total_pages/$this->limit)`。
- **影响**：`limit` 一旦不是 18，页头"共 N 页"就是错的。
- **代码层修复**：改为 `ceil($total / $this->limit)`；新版直接由分页服务统一返回 `total/page/pageSize/totalPages`。

#### D-12 每次列表查询执行两遍完整 SQL

- **现象**：`$result = query($sql); $Num = num_rows($result); $result = query($sql." LIMIT $start,$NumOfPage");` —— **先把全量结果集拉回来只为了数行数**，再查一次带 LIMIT。
- **影响**：媒体表大时内存与耗时翻倍。
- **代码层修复**：改为 `SELECT COUNT(*) ...`（同 WHERE 条件）+ `SELECT ... LIMIT ? OFFSET ?` 两条轻量查询；`COUNT` 不带 `ORDER BY`。**列名与表名完全不变。**

#### D-13 翻页丢失筛选条件（**用户可感知的最大缺陷**）

- **现象**：媒体列表的筛选用 **POST** 提交，而分页链接 `?id=..&userinfoid=..&page=N` 是 **GET**，**不带 `searchkey/searchvalue/orderby`** → 翻到第 2 页筛选条件全部失效，用户看到的是未筛选的全量数据。
- **代码层修复**：筛选统一改 **GET**，全部条件进 URL query；分页链接携带当前全部查询参数。副作用是可分享、可后退、可刷新。

#### D-14 页码参数未做边界与类型校验

- **现象**：`$start = ($_GET['page']-1)*$NumOfPage`，`page` 未 `isset` 先用（`media_file.php` 第 62 行先用后判）、未校验为正整数。`page=0` → `$start = -18` → `LIMIT -18,18` **SQL 语法错误**；`page` 传字符串 → 拼进 SQL。
- **代码层修复**：`page = max(1, intval($page))`；`pageSize` 白名单；`offset = (page-1)*pageSize`；超出总页数时返回空列表而非报错。

#### D-15 分页 `target` 拼接产生畸形 URL

- **现象**：`filefoldermanager.php` 里 `$p->target("?id=".$_GET['id']."&")`，而该页根本没有 `id` 参数 → 生成 `?id=&page=2`。
- **代码层修复**：分页链接由统一的 URL builder 从"当前有效查询参数白名单"生成。

### 2.4 查询逻辑类

#### D-16 `filefoldermanager.php` 的排序分支被整体覆盖（死代码）

- **现象**：`if(!empty($searchvalue))` 内部先按 `searchkey`/`orderby` 精心组装了 4 个分支的 `$sql`，**紧接着在 if 块末尾又无条件重新赋值一次 `$sql`**（不带排序）→ 前面所有分支全部作废。
- **影响**：页面上的"按创建时间排序"下拉**永远不生效**。
- **代码层修复**：删除覆盖赋值，改为"基础 SQL + 条件片段 + 白名单排序"的组装方式。

#### D-17 SQL 字符串拼接产生语法错误的死分支

- **现象**：`filefoldermanager.php` 第 90 行 `$sql.= "'ORDER BY $_GET[orderby] DESC ";` —— **多了一个单引号**；第 125-126、131-132 等处 `... and (filefolder.id = '0' OR filefolder.userid = '$group_id' ORDER BY ...` —— **左括号未闭合**。
- **影响**：这些分支一旦被走到就是 SQL 语法错误（因 D-16 恰好被覆盖而未暴露，属于"靠 bug 掩盖 bug"）。
- **代码层修复**：随 D-16 一并重写；所有条件片段用数组收集后 `implode(' AND ')`，不手工拼括号。

#### D-18 非 admin 分支缺少空格导致 SQL 拼接错误

- **现象**：`media_file.php` 第 172 行 `... FROM media"` 后紧接 `"WHERE ..."` → 生成 `FROM mediaWHERE`。
- **影响**：非 admin 用户 + 按名称搜索 + 不排序 时**查询直接失败，页面 die**。
- **代码层修复**：随参数化改造统一重写查询构造。

#### D-19 权限归属判定：用户组 ID 与用户 ID 混用

- **现象**：`filefoldermanager.php` 取的是 `book_admin.usergroupid` 存进 `$group_id`，却拿它去比 `filefolder.userid`（该列语义是**创建者用户 ID**）。而 `media_file.php`、`get_filelist()` 用的是 `$_SESSION['userid']`（用户 ID）。
- **影响**：同一用户在"文件夹管理页"和"文件管理页"看到的文件夹集合不一致；用户组 ID 恰好等于某个用户 ID 时会看到别人的文件夹。
- **代码层修复**：**统一按用户 ID 判定归属**，即 `filefolder.userid = <当前登录用户 id>`；共享判定用 `filefolder.priority=1`。字段完全不变，只改比较用的变量来源。

#### D-20 `filefolder.id = '0'` 恒不成立的兜底条件

- **现象**：非管理员分支写 `WHERE filefolder.id='0' OR filefolder.userid='$group_id'`。`filefolder.id` 是自增主键，**不可能为 0**，该条件是死条件（原意应为 `parentid=0` 或"共享"）。
- **代码层修复**：按业务真实语义改为 `(filefolder.priority = 1 OR filefolder.userid = :uid)`，即"共享的 或 自己创建的"。**仍然只用 `priority`/`userid` 两个已有字段。**

#### D-21 `media_file.php` 的"共享"语义丢失

- **现象**：媒体列表非 admin 分支只过滤 `media.userid = <当前用户>`，**完全没有考虑文件夹的共享属性**。结果：共享文件夹里别人上传的媒体，普通用户在文件管理页**看不到**，但在任务的媒体选择树里**看得到**（因为那里按 `priority` 过滤）。
- **影响**：两个入口对"同一个共享文件夹"呈现不同内容，用户困惑。
- ✅ **已定稿（2026-08-22 产品确认）：保持旧语义，不改行为。**
  - **媒体**：`WHERE media.folderid = :fid AND (:isAdmin OR media.userid = :uid)` —— 普通用户**只看自己上传的媒体**，即使该媒体位于共享目录内。
  - **目录**：`WHERE filefolder.priority = 1 OR filefolder.userid = :uid` —— **共享目录全员可见、可进入**。
  - 二者差异属**设计意图**："共享目录是可见的容器，不是可见的内容"。仅在 UI 顶部固定标注"仅显示我上传的媒体"消除困惑，**不提供切换开关**。
  - 本条因此**不再属于待修缺陷**，仅保留 D-19/D-20 中"归属判定字段用错"的修复。

#### D-22 内连接导致孤儿媒体在任务清单中消失

- **现象**：`displaymedia.php` 用 `FROM media,mediaoftask,filefolder WHERE ... AND media.folderid=filefolder.id`（隐式内连接）。文件夹被删后媒体成孤儿 → 任务清单里看不到该媒体。
- **代码层修复**：改为 `LEFT JOIN filefolder ON filefolder.id = media.folderid`，文件夹名为空时展示"(已删除目录)"。**表与字段不变，只改连接方式。**

#### D-23 目录容量统计把全部行拉回 PHP 累加

- **现象**：`SELECT size FROM media WHERE folderid=$fid` 后在 PHP 里 `$getsize += $row['size']`。
- **代码层修复**：改为 `SELECT COALESCE(SUM(size),0) FROM media WHERE folderid = ?`。字段不变。

#### D-24 `media.filename != 'tts'` 与 `media.typeid != 'tts'` 混用

- **现象**：`media_file.php` 用 `filename!='tts'` 过滤 TTS 记录，`get_filelist()` 用 `typeid!='tts'`。两个字段语义不同。
- **影响**：过滤口径不一致，TTS 记录可能在某些列表泄漏。
- **代码层修复**：统一为**同时判定**（`typeid <> 'tts' AND filename <> 'tts'`），或抽成一个共用的 `isTtsPlaceholder()` 条件常量。**字段与取值完全沿用旧约定，不改数据。**

#### D-25 无筛选分支不过滤 TTS

- **现象**：admin 无筛选时 SQL 是 `WHERE media.folderid=$fid ORDER BY id DESC`，**没有 tts 过滤**；有筛选时才加。
- **影响**：不搜索时 TTS 占位记录会出现在列表里，搜索一下反而消失。
- **代码层修复**：把 TTS 过滤提到公共 WHERE 片段，所有分支一致。

### 2.5 事务、锁与并发类

#### D-26 `LOCK TABLES` 与 `START TRANSACTION` 混用（**语义被破坏**）

- **现象**：`folderdel_msg` 顺序为：`LOCK TABLE ... WRITE` → `START TRANSACTION` → ... → `COMMIT/ROLLBACK` → `UNLOCK TABLES`。
- **根因**：MySQL 中 `LOCK TABLES` 会**隐式提交**当前事务；`START TRANSACTION` 也会**隐式释放**表锁。两者混用导致**事务边界事实上不存在，ROLLBACK 无效**。
- **影响**：删除文件夹中途失败 → 媒体已删、文件夹未删（或反之），数据处于不一致状态且不可回滚。
- **代码层修复**：
  1. **二选一，统一用事务**：InnoDB 表全部走 `START TRANSACTION` ... `COMMIT`，**移除所有 `LOCK TABLES`**。
  2. 需要防并发写同一目录时，用 `SELECT ... FOR UPDATE` 对目标 `filefolder` 行加行锁（表与字段不变）。
  3. 物理文件删除**移出事务**：事务内只记录待删文件清单，`COMMIT` 成功后再删文件（避免回滚了但文件已被删）。

#### D-27 异常路径不解锁

- **现象**：`delfiletask_msg` 中多处 `exit_back_function()` 直接 `exit`，**`UNLOCK TABLES` 永远执行不到**；`delallfiletask_msg` 全程没有 `UNLOCK TABLES`。
- **影响**：表锁悬挂到连接关闭，期间其它请求全部阻塞。
- **代码层修复**：移除 `LOCK TABLES`（见 D-26）；所有资源释放走 `try/finally`。

#### D-28 上传的"查重-插入"竞态

- **现象**：`SELECT ... WHERE name=? AND folderid=?` 判定后再 `INSERT`，两步之间无保护。
- **约束**：`media` 表**没有** `(name, folderid)` 唯一索引，且**不允许新建索引**。
- **代码层修复（应用层串行化，不动 schema）**：
  1. 用**应用级命名锁**：`SELECT GET_LOCK(CONCAT('media_upload_', :folderid), 5)` → 执行查重+写入 → `RELEASE_LOCK(...)`。命名锁不改表结构。
  2. 或用文件锁 / Redis 锁按 `folderid` 粒度串行化上传写入。
  3. 写入后再做一次"同名多条"的自检并合并，作为兜底。

#### D-29 `add_terminal_dirarea()` 使用未定义变量

- **现象**：`$resultss = mysqli_query($con,$sqls);` 但下一行 `if($row = mysqli_fetch_array($results))` —— **变量名写错**（`results` 未赋值）。
- **影响**：整个"folderid==0 时自动建根目录"的分支**从未执行成功**。
- **代码层修复**：修正变量名；同时开启严格错误报告，禁止未定义变量静默通过。

#### D-30 `folderdel_msg` 中的变量串用

- **现象**：删除子级媒体的循环里判断与拼路径用的是**外层循环遗留的 `$row_folder`**，而不是当前的 `$row`：
  `if($row_folder['id']>1) { system("rm -rf link".$row_folder['filename']); }`
- **影响**：子级媒体的物理文件**要么没删（残留垃圾文件），要么重复删了上一个文件**。
- **代码层修复**：改用当前行变量；随 D-08 的整棵子树删除逻辑一并重写。

### 2.6 缓冲区与协议类（对应 C 层同构问题）

#### D-31 定长缓冲拼接（Web 端二进制协议封装）

- **现象**：`features_wrapper_class.php::send_socket_vediotask()` 及 `upload_file.php` 中，把终端 ID 列表**固定循环 256 次**填充定长报文；`getallBytes($str, 256)` 把路径截/填到 256 字节。
- **风险**：
  - 终端数 > 256 时**静默截断**，超出的终端收不到任务。
  - 媒体路径 > 256 字节时截断，后台拿到半截路径。
  - `explode(",", $terminalids)` 后未校验元素个数与 `$terminalnum` 是否一致，数组越界读到 `null` 被当作 0 下发。
- **代码层修复**：
  1. 封装报文前**先断言**：终端数 ≤ 协议上限、路径字节长度 ≤ 上限；超限则**明确报错**给用户，而不是静默截断。
  2. 终端数超限时**自动分批下发**多条报文。
  3. 路径使用相对短路径（媒体目录固定前缀由后台补全），从源头压缩长度。
  4. 数组访问统一用 `?? 0` 并校验 `count()`，禁止越界。
- **C 层对应整改建议**（同一问题的服务端镜像）：
  - 递归收集文件夹 ID 时，**禁止 `char buf[N]` + `strcat` 累加**；改为动态数组（`realloc` 扩容）或链表。
  - 每次追加前校验 `remaining = cap - len`，用 `snprintf` 并检查返回值。
  - 递归改**显式栈迭代**并设深度上限与 visited 判环，避免深目录导致栈溢出。
  - 生成 `IN (...)` 时**分批**（每批 ≤N 个 ID）多次查询，而不是构造一条超长 SQL。
  - **所有整改只影响 C 层内存管理与 SQL 分批下发方式，查询的仍是 `filefolder.id/parentid`、`media.folderid`，表结构零变更。**

## 5. 新版自身的缺陷（权限隔离实测发现）

用户模块（F-14~F-24）上线后，用一个「有媒体/文件夹权限、无用户管理权限」的普通账号
对新版做了一轮实测。目录树本身的裁剪是对的，但**媒体侧几条路径各自漏掉了同一道闸门**：
只按 `folderid` 查内容，从不校验这个 `folderid` 本身对调用者是否可见。

| 编号 | 位置 | 缺陷 | 影响 | 修复 |
|---|---|---|---|---|
| **N-01** | `media.Upload` / `handleMediaUpload` | 上传全程不校验目标目录归属，只判了「是否录音库」 | **越权写**：普通用户可把文件直接写进别人的私有目录（该目录在他的树里根本不显示） | handler 最前置 `AssertFolderVisible` |
| **N-02** | `media.List` | 只对 media 行做 `userid` 过滤，未校验 `folderId` 可见性 | 元信息泄露：构造 `?folderId=<别人的私有目录>` 可读到目录名、容量、`canUpload`（媒体行本身是干净的） | `List` 入口先过闸门，早于 `folderInfo` |
| **N-03** | `media.ClearFolder` | 确认文本校验排在权限校验之前 | 「确认文本与文件夹名称不一致」成为目录名猜测预言机 | 闸门提到确认文本之前 |
| **N-04** | 路由 `GET /api/usergroups/options` | 挂在「仅需登录」级别 | 任何账号可枚举全部用户组名与级别 | 收紧到 `userpriv` |
| **N-05** | `web/.env.production` | `VITE_API_URL = /api` 被当作 axios `baseURL`，而各 API 模块路径本身已带 `/api`（`PORT1` 为空串） | **登录完全不可用**：实际请求 `/api/api/login`，后端无此路由 | `VITE_API_URL = ""` |
| **N-06** | `staticHandler` | `mux.Handle("/", ...)` 把未匹配的 `/api/*` 也回落到 `index.html`，返回 200 + HTML | 让 N-05 变成**静默失败**，排查成本极高 | `/api/*` 未匹配时回 JSON 404 并单独打告警日志 |

### N-05 / N-06 的失败链

这两条必须一起看 —— N-06 是让 N-05 完全隐形的原因：

1. 浏览器 `POST /api/api/login`
2. mux 未匹配 → 落到静态处理器 → 回 **200 + index.html**
3. axios 响应拦截器判断 `data.code !== SUCCESS` 才报错，而 HTML 根本没有 `code` 字段 → **当成功处理**
4. `data.access_token` 是 `undefined` → `setToken(undefined)`
5. `initDynamicRouter()` 拉菜单，无 token → 401 → 抛错
6. `catch` 里清 token + 跳回登录页

**用户看到的现象：点登录，页面闪一下回到登录页，没有任何报错。**
一个纯粹的路径拼写问题，表现成「登录功能坏了」。

同时把访问日志从「方法 路径 耗时」补成「方法 路径 **状态码** 耗时」。
原先 200 和 404 在日志里长得一模一样，`/api/api/login` 打了两天都看不出异常。

> 注意 `httpx.Fail` 按 Geeker 拦截器的约定统一回 HTTP 200、业务码放 body，
> 所以未匹配接口在访问日志里仍是 200，必须额外打一行 `⚠ 未注册的接口路径` 才看得见。

### N-05 / N-06 实测复验（2026-08-24）

| 用例 | 期望 | 实测 |

| `GET /api/captcha` | 200 正常出图 | ✅ 返回 captchaId + base64 |

## 6. 终端管理模块（F-25 ~ F-31）的实测结论

### 6.1 手册的 GBK 处方是错的

开发手册要求写 `terminal.postion` 前先做 utf8 → gbk 转换。**这条必须废弃。**

`postion` 是 `gbk` 字符集列，而连接字符集是 `utf8`，MySQL 会**自己**在两种字符集之间转换。
现网实测：经 utf8 连接写入 `教学楼一层东`，存储字节就是正确的 GBK `BDCCD1A7C2A5D2BBB2E3B6AB`。
按手册再手工转一次 → 双重编码，数据直接烂掉。

代码里已按「不转换」实现，并在 `terminal/edit.go:99` 留了注释说明原因。

### 6.2 真正的 GBK 风险是静默截断，不是编码方向

MySQL 转换时遇到 GBK 表示不了的字符**不报错，直接换成 `?`**。
实测 `测试🔊` 存进去变成 `B2E2CAD43F3F3F3F` —— emoji 无声无息地没了，且不可逆。

修复：写入前用 MySQL 自己做一次 utf8 → gbk → utf8 往返，不等就拒绝
（`terminal.checkGBK`）。用真实转换表判定，比在 Go 里按码位范围猜准确，
也免了引入 `golang.org/x/text`。长度同样按 GBK 字节数算（上限 255），不是按字符数。

现网复验：

| 输入 | 结果 |
|---|---|
| `测试🔊` | ✅ `位置信息含有 GBK 无法表示的字符` |

### 6.3 `postion` 现网存的是固件版本串 —— 已按「设备侧不代管」处理

列名叫「位置」，界面也按「位置」暴露成可编辑字段。但现网这一列里躺的是后台 C 服务写入的固件版本：

| 终端 | `postion` 实际内容 |
|---|---|
| 4 一体化音箱LED | `TW_V1.0.0.3:Aug 19 2026-23:57:47` |
| 13 一体化音箱2.86 | `TW_V1.0.0.3:Aug 19 2026-17:57:07` |
| 17 TTS主机2.86 | `V2.4.7.2 Aug 24 2026 13:15:06` |

也就是说**这一列是 C 服务的输出，不是给人填的输入**。Web 端一旦让用户改，
下次终端上线时会被 C 服务原样覆盖；反过来说用户填的内容也没有任何消费方。

**已确认的处置**（2026-08-24，用户决策）：编辑弹窗里**去掉**该字段，
提交时由 `openEdit` 读到的原值原样回填 —— 既不覆盖 C 服务写的内容，
也不会因为漏传而把该列清空。列表也不单独加「固件版本」列。

依据是用户给出的职责划分：**终端自己跑着一套独立的 Web 程序，
设备侧的配置归它管；这里做的是服务器 Web，不代管设备侧数据。**
同一条划分也决定了操作列只提供「打开连接」跳过去，不在服务器端复刻终端的配置界面。

服务端的 GBK 校验（6.2）仍然保留作兜底 —— 接口是公开的，
不能依赖「前端不传」来保证不写坏数据。

### 6.4 回呼开关不下发 UDP 通知（有意为之）

旧代码里回呼（backcall / `isselectcall`）的通知调用被整段注释掉了，
而且仅存的两处开、关用的是**同一个** `state=15`。
没有可信的状态码可用，因此新版只写库、不发通知，
并在 `terminal_handlers.go::notifyToggle` 就地记了原因。
其余四个开关（紧急 / 录音 / 对讲 / 发言）的状态码都从旧调用点提取，照原样下发。

### 6.5 新版自身的缺陷 N-07（本轮发现并已修复）

**N-07 删除预演把关联任务条数报少**

`fillImpact` 原来拿任务名列表的长度当条数：

```go
imp.Tasks = len(imp.TaskNames)   // ← 错
```

而那条查询是 `SELECT DISTINCT COALESCE(t.taskname,'') ... LIMIT 50`：
按**名字**去重、且截断到 50 条。现网终端 3 实际关联 10 个 taskid，
其中 `2222`/`222`/`444` 各有两条同名任务，去重后只剩 7 个名字 —— 预演就报「关联任务 7」。
用户据此判断影响面，会低估删除后果。

修复：条数改用独立的 `COUNT(DISTINCT tot.taskid)`，名字列表只作展示；
前端在 `tasks > taskNames.length` 时补一句「等 N 条」。

现网复验（终端 3）：

| 项 | 修复前 | 修复后 | 数据库真值 |
|---|---|---|---|
| `tasks` | 7 | **10** | `COUNT(DISTINCT taskid)` = 10 |
| `taskNames` | 7 个 | 7 个（展示用） | 去重后 7 个名字 |

## 7. 任务管理模块（F-32 ~ F-37）的实测结论

### 7.1 ⚠ 手册记录的启停协议是错的，以旧代码实测为准

手册说「启动写 `state=3`，停止写 `0`，暂停写 `2`」。实际把 `do.php`
四个函数逐行读下来完全不是这样：

| 动作 | 数据库 | 通知报文 | 手册记的 |
|---|---|---|---|
| 启动 | `state = 3` | `task?state=3&id=X`（**不带** type） | 一致 |
| 停止 | `state = 2` | `task?state=2&id=X&type=2` | ✗ 手册写 `state=0` |
| 暂停 | **不写库** | `task?state=22&id=X&type=2` | ✗ 手册写 `state=2` 落库 |
| 恢复 | **不写库** | `task?state=23&id=X&type=2` | ✗ 手册未记录 |
| 新增 | — | `task?state=4&id=X&volume=V` | ✗ 手册未记 `&volume=` |
| 修改 | — | `task?state=5&id=X&volume=V` | ✗ 手册未记录 |
| 删除 | — | `task?state=6&id=X&type=2` | ✗ 手册未记 `&type=` |

报文有三种形态（`send_socket_generate_general` / `..._general2` / `..._task_volume`），
分别对应「不带 type」「带 `&type=2`」「带 `&volume=`」。混用后台服务解析不了。
新版按实测实现，见 `notify` 包里的常量块。

现网实测确认这套协议是活的：启动后立刻查库，主任务 `state` 已被后台 C 服务
从我们写的 `3` 改成 `1`（执行中）；停止后又被改回 `0`（准备）。
**也就是说 `task.state` 归后台服务所有**，Web 写入只是一次交接信号，
控制接口返回后马上读 `state` 读到的是 C 服务的值，不是我们写的值。

### 7.2 ⚠ 更正：`projectstate` 是 **0 = 启用、1 = 停用**，旧版没有写反

> **本节推翻了本文档 2026-08-24 版的原结论。**
> 原文断言「`enableTask` 写 0 是停用、`disableTask` 写 1 是启用，函数名与行为颠倒」，
> 并据此把新版实现成 `启用 → projectstate = 1`。**这是错的**，
> 错因是把 `audioserver.sql` 的列注释当成了权威：
>
> ```sql
> `projectstate` int(11) NOT NULL DEFAULT '0' COMMENT '方案是否启用，1启用，0停用'
> ```
>
> **注释本身是错的。** 四条互相独立的证据一致指向 `0 = 启用`：

| # | 证据 | 位置 |
|---|---|---|
| 1 | `enableTask()` 写 `0`，`disableTask()` 写 `1` | `do.php:26303` / `do.php:26344` |
| 2 | `start_file_task_msg()`（启动任务）同样写 `0` | `do.php:26251` |
| 3 | 「浏览生效中的任务」过滤 `projectstate = 0`；安卓端任务列表也是 `projectstate = 0` | `Browse_active_task.php` / `androidfilemanage.php:19` |
| 4 | 模板 `projectstate == 0` 渲染 `Enabled`、`== 1` 渲染 `Disenabled` | `BellManager/bellManager_form.html:55` |

再加一条旁证：旧版新建任务的 INSERT 里 `projectstate` 填的是 `'0'`
（`do.php:12365`）—— 建出来就是启用的，符合直觉。
列表排序 `ORDER BY projectstate, playtime asc`（`taskmanager.php:183`）
也是升序把启用的排在前面。

**结论：旧代码在这里是对的，`enableTask` / `disableTask` 没有颠倒。**

这个错误的实际后果很严重：用户点「启用方案」会写进 `1`，
在后台 C 服务眼里等于**停用**，整批广播任务会静默失效。

已修复的位置：

| 文件 | 原实现 | 改为 |
|---|---|---|
| `task/control.go::SetProjectState` | 启用 → `1` | 启用 → `StateEnabled`(0) |
| `task/control.go::Control` 的启动闸门 | `r.projectState != 1` 判为停用 | `!= StateEnabled` |
| `task/task.go::startable` | `ProjectState != 1` 判为停用 | `!= StateEnabled` |
| `task/task.go::defaultOrder` | `projectstate DESC` | `projectstate ASC`（与旧版一致） |
| `task/edit.go::validate` | 文案「0（停用）/ 1（启用）」 | 「0（启用）/ 1（停用）」 |
| `views/task/index.vue` 状态标签 | `=== 1` 显示「启用」 | `=== 0` 显示「启用」 |
| `views/task/index.vue` 编辑单选 / 新建默认值 | 启用 = 1，默认 1 | 启用 = 0，默认 0 |

同时在 `task` 包里加了 `StateEnabled` / `StateDisabled` 两个常量，
禁止再出现裸的 0 / 1。

> 补充：`internal/user/delete.go::SetEnable`（更早的模块）**本来就是对的**，
> 注释里已经写明「0 = 启用」并给出了同一批证据。
> 也就是说同一个字段在两个模块里曾经有两套相反的理解 —— 现已统一。

现网复验（2026-08-25，192.168.2.159）：

| 用例 | 期望 | 实测 |
|---|---|---|
| 现网 6 条任务的 `projectstate` | 全为 0，列表应显示「启用」 | ✅ 修复前它们会被全部判成「方案已停用、不可启动」 |
| 新建任务（不传 projectstate） | 落库 0（与旧版 INSERT 一致） | ✅ |
| 点「停用方案」 | 落库 1，列表显示停用 | ✅ `startable:false / blockReason:"方案已停用"` |

### 7.2c ⚠ 更正：`prepower` 的单位是**秒**，不是分钟

> **本节同样推翻了 2026-08-24 版的实现。** 原文把 prepower 当分钟，
> 复验时记的是「prepower=5 → 子任务播放时间提前 5 分钟 = 23:45:00 ✅」——
> 数值对得上我自己的实现，但和旧系统对不上。

判据：

| 证据 | 位置 |
|---|---|
| 下拉选项：0/5/10/…/55 逐个标「秒」，然后 60/120/180/240/300 标「1~5 分钟」，默认选中 15 | `FileAd/AddFileTask_form.html:940-964` |
| 现网作息方案「333」：prepower=15，主任务 08:00:00、功放子任务 **07:59:45** | 生产库 `task` 表 |
| 旧代码四处平移点写法完全一致 | `do.php:1922 / 11960 / 12391 / 13440`、`addonebellplan.php:106` |

旧代码的写法是把「秒」硬拆成两个分支：

```php
if ($prepower > 59) { $t = $prepower / 60; ... "- {$t} minutes" }
else                { $t = $prepower % 60; ... "- {$t} seconds" }
```

这只在 prepower 是 60 的整数倍时正确。`prepower = 90` 会算出 `"1.5 minutes"`，
PHP 的 `strtotime` 解析不了小数相对量，返回 `false`，
`date('H:i:s', false)` 于是给出一个与本意无关的时间。

新版直接**按秒平移**：逐值复现旧版正确时的结果，同时把 90 这类值算成它本来的意思。

已修复的位置：

| 文件 | 原实现 | 改为 |
|---|---|---|
| `task/edit.go::shiftTime` | 形参 `deltaMinutes`，`+ deltaMinutes*60` | 改名 `ShiftTime`，形参 `deltaSeconds`，`+ deltaSeconds` |
| `task/edit.go::validate` | `0 ~ 1440 分钟` | `0 ~ 3600 秒` |
| `views/task/index.vue` | `el-input-number` + 「分钟」提示 | 与旧界面同一组下拉（0~55 秒 + 1~5 分钟） |

现网复验：方案 333 的详情接口回 `prepower: 15 / powerPlayTime: "07:59:45"`，
与库里存量数据逐字一致；新建 prepower=15 的方案，三个条目的功放子任务
分别是 07:19:45 / 07:59:45 / 08:44:45，都恰好早 15 秒。

### 7.2b 新版自身的缺陷 N-08：枚举类校验被误判成 500

`isTaskValidationErr` 用关键词匹配区分「用户输入错误」和「服务器故障」，
关键词表里漏了 **「只能是」**，于是这六条消息全部落到 500 分支：

- 本地优先播放只能是 0 或 1
- 播放方式只能是 0（随机）或 1（顺序）
- 发送模式只能是 0（单播）或 1（组播）
- 方案状态只能是 0（启用）或 1（停用）
- 间隔播放模式只能是 1（时间）或 2（循环）
- 时长类型只能是 1（按秒数）或 2（按循环次数）

用户看到的是「服务器内部错误」，真正的原因只写进了服务端日志
（`[500] 新建任务: 间隔播放模式只能是 1（时间）或 2（循环）`）——
本轮就是这样被发现的。已补上关键词。

现网复验：`timelengthtype=9` → `40001 时长类型只能是 1（按秒数）或 2（按循环次数）`；
`israndomplay=7` → `40001 播放方式只能是 0（随机）或 1（顺序）`；两次均零写入。

> 关键词匹配这套做法本身是脆的。真正的解法是给校验错误一个哨兵类型
> （`errors.Is(err, task.ErrValidation)`），但那要动所有 `fmt.Errorf` 调用点，
> 属于跨模块的统一重构，本轮没做，记在这里。

旧版这两个函数的其余行为予以保留（是合理的）：方案开关会同时把 `state` 与
`offlinestate` 复位为 0，并且主任务（`sec_task_id = 0`）与功放子任务
（`sec_task_id IN (ids)`）一起改 —— 否则会出现「主任务停用、子任务还启用着」的组合。

### 7.3 旧版复制任务丢数据（两处）

1. **`endtime` 被漏掉**。`copyFileTask` 按位置下标 `$getrows[2..11]` 再跳到
   `[13..32]` 取源任务的列，正好跳过下标 12 —— 也就是 `endtime`。
   复制出来的任务结束时间被重置成 `00:00:00`。
2. **只复制第一条媒体**。取 `mediaoftask` 用的是 `if` 而不是 `while`，
   多媒体任务复制完只剩一首。

新版改成显式列名的 `INSERT ... SELECT`：列错位会在执行期立刻暴露，
而不是像按下标取值那样静默错位。现网实测源任务 3 条媒体、副本也是 3 条，
`endtime` 两边都是 `23:55:00`。

### 7.4 旧版 `set_task_synch` 假定「子任务 id = 主任务 id + 1」

```php
INSERT INTO terminaloftask ... VALUES('$bbb', ...)   // 主任务
$bbb = $bbb + 1;
INSERT INTO terminaloftask ... VALUES('$bbb', ...)   // 「功放子任务」
```

这个假设只在「建完主任务紧接着建子任务、中间没有任何其他插入」时成立。
一旦不成立，终端关联行就被插到一个毫不相干的任务上，且没有任何报错。
新版按 `sec_task_id` 查出真正的子任务 id。

顺带一提：手册把 F-37「同步任务」描述成「把一个任务的配置同步到其他任务」，
与代码完全不符 —— 它实际做的是「把一批终端补加到一批任务上」。以代码为准。

### 7.5 `area` 掩码：代码写 16 个 1，数据里是 8 个 1

旧 `addfileplaytask_msg` 的 INSERT 里 `area` 写死 `'1111111111111111'`（16 位），
而列定义的默认值和现网 `terminaloftask` 全部 35 行的实际取值都是 `'11111111'`（8 位）。
新版以**现网数据**为准用 8 位 —— 写 16 位会让新建的行和存量数据不一致。

### 7.6 `mediaoftask.sort` 是 0 基，不是手册说的 1 基

手册 BR-167 写「从 1 连续递增」。旧版写入器用的是 `$i`，从 0 起；
现网存量数据也是 0。新版按 0 基写入。

### 7.7 旧版启动语句的类型集合与列表对不上

列表查 `tasktype IN (2,7)`，而 `filetaskstart_msg` 限定 `tasktype IN(2,15)`。
**类型 7 的任务在列表里看得见、却永远启动不了**，点了没有任何反馈。
现网暂无类型 7 的数据，所以没暴露。新版启停的类型集合是 `{2,7,15}`，与列表对齐。

### 7.8 新版自身：删除任务不连带清理「其他类型的关联任务」

现网任务 70009（`tasktype=30`）的 `sec_task_id` 指向 70007（文件广播）。
旧版和新版都只连带删除类型 9（功放）与 24（LED）两种子任务。
删掉 70007 之后，70009 的 `sec_task_id` 就成了悬空引用。

**没有扩大删除范围** —— 类型 30 的业务语义未确认，贸然连带删除风险更大。
改为在删除预演里加一个 `otherLinked` 计数如实告知用户。
现网实测：`ids=70007` 的预览返回 `otherLinked: 1`，对照组 `70022` 返回 `0`。

| 删除预演：不存在的 id | 进 blocked 而非报错 | ✅ |
| 删除预演：作息任务 70016 | `NOT_DELETABLE_TYPE` | ✅ BR-178 |
| 残留检查 | 6 项全 0 | ✅ 孤儿 mediaoftask / terminaloftask / parentid / 子任务均为 0 |

测试期间在生产库建的 zz_test 任务、副本、三层测试分组已全部删除，
`filetaskfree` 恢复为只有 `admin` 一行。

sec_task_id=417 / createtime=2013-08-15` —— 这是 `audioserver.sql`
自带的种子行，不是测试产生的，未做任何处理。

### 7.10 与终端模块相同的权限口径

读（列表、分组树、详情、选择器）只要登录，可见范围由 `task.task_user_id` 收敛；
写（增删改、启停、复制、分组管理）要 `taskpriv`。
按钮权限键 `task: {add, edit, delete, control, copy, folder}`。

顺带修掉一处潜在的隐蔽 bug：`media` 表**也有** `priority` 和 `userid` 两列，
与 `filefolder` 同名。`folder.VisibleCond` 返回的是裸列名条件，
放进 `IN (SELECT ... FROM filefolder WHERE ...)` 时靠 SQL 作用域规则碰巧绑对，
但一旦写成 JOIN 的 ON 子句就会静默绑到 `media` 上 ——
而 `media.priority` 的列注释明写着「此字段没被使用」，恒为 0，
结果就是所有媒体对普通用户全部不可见，且不报任何错。
新增 `folder.VisibleCondAlias(u, alias)` 作为唯一实现，`VisibleCond` 退化为它的空别名调用。

### 7.11 本轮未做的部分

- **F-37 的「任务配置同步」**：手册描述的那种语义在旧代码里不存在（见 7.4），
  没有可对齐的旧行为，需要产品侧先明确要不要这个功能。
- **采播 / 网络电台 / TTS / LED / 视频 / 声场任务**：与文件广播同构，
  差异在 `tasktype` 取值与少量扩展字段，本模块的模式可直接套用，但未实现。
- **`task.keyid` 与 `terminalkeymaptask`**：快捷键绑定属于终端快捷键功能，
  删除时已连带清理，但没有对应的编辑入口。

会话存在进程内存（`auth.Manager.sessions`），服务重启即全部失效。
这是「服务端会话可吊销」的代价，不是缺陷；但每次发版都会把在线用户踢下线，
后续如果介意，可以把会话落到数据库或改用无状态 JWT ——
两条路都不需要改 `audioserver.sql`（前者可复用现有表，后者不落库）。

## 8. 报警管理模块（F-38 ~ F-42）的实测结论

### 8.1 ⚠ 手册 D-137「变更后通知后台服务」无法实现，也不该实现

手册要求报警映射/分区变更后向后台 C 服务发通知。**旧系统里根本没有这种报文。**

把 `ok112` 全量扫一遍，`send_socket` 系列函数用到的 `msg_type` 只有六种：
`config` / `file` / `project` / `server` / `task` / `terminal`。
唯一带「alarm」字样的 `alarmstart_msg` 是个只写着「保留使用」就 `exit` 的空壳。

新版因此**刻意不发任何通知**。凭空编一个 state 码比不发更糟：
后台服务解析不了的报文会被丢弃或误判，而我们无法验证。
决策与理由写在 `internal/alarm/alarm.go` 的包注释里，
`alarm_handlers.go::handleAlarmMappingCreate` 处也留了就地说明。

报警配置的生效路径是 C 服务**轮询数据库**，不是 Web 推送 —— 这一点与任务模块相反。

### 8.2 通道数：`terminal.channel` 与 `terminaltype.switchcount` 长期对不上

编辑弹窗要生成「1 ~ N 通道」下拉，N 有两个候选来源，现网两者矛盾：

| 报警主机 | `terminal.channel` | 类型 7 声明的 `switchcount` |
|---|---|---|
| 8 报警主机-0 | 2 | 16 |
| 9 报警主机-0 | 32 | 16 |
| 15 报警主机-0 | 32 | 16 |
| 16 报警主机-0 | 32 | 16 |

四台里没有一台对得上。旧 `setalarmkeymap.php` 用的是 `terminal.channel`，
新版沿用（每台机器的实际路数以自身为准更合理），
但把 `typeSwitchCount` 一并下发到前端，界面上可以对照排查配置错误的设备。

校验也按 `terminal.channel` 做：主机 8 只接受 1~2，主机 9 接受 1~32。

### 8.3 `alarmgroupmap` 没有 (主机, 通道) 唯一约束

一个报警主机的一路开关只能对应一条映射，但库里没有唯一索引，
旧版也不查重 —— 同一个通道配两条，触发时行为不确定。

R1 红线禁止 DDL，所以**不能加唯一索引**。改用与终端/任务模块相同的做法：
`GET_LOCK('htweb_alarm_channel_<主机id>_<通道>')` 串行化「查重 + 写入」。

顺带补掉旧版的一处遗漏：**修改**映射时旧版完全不查通道占用（D-132），
只有新建才查。新版两条路径都查，且修改时排除自身 —— 否则把一条映射
「改成它自己原来的通道」都会被自己挡住。

### 8.4 报警音必须放在「报警媒体库」（folder 4）下 —— 手册没写

旧 `setalarmkeymap.php` 的媒体下拉限定在 `folderid = 4` 及其子目录内，
手册完全没有记录这条规则。新版保留该限定并显式校验。

旧版的子目录收集是**三层嵌套 OR 子查询硬编码**（与 D-07 同型），
第四层目录里的媒体选不到。新版改成 BFS + 访问集合，深度不限、`parentid` 成环也不死循环。

另一处旧版体验缺陷：报警媒体库为空时旧页面直接 `alert` 一句然后 `history.back()`，
**整个页面进不去**。新版返回空列表加一句说明，界面正常打开并告诉用户该去哪儿传文件。

### 8.5 一台终端到底属于哪个报警分区：两套数据各说各话（本轮修复）

归属被记在两个地方：

- `terminalofalarmgroup`（多对多关联表，`alarmgroupid` 是 **varchar**）
- `terminal.firealarmgroup`（**单个 int**，无分区时为 `-1`，见列注释）

最终生效的是 `firealarmgroup` —— 它是一个 int，天然只装得下一个分区。
而旧版维护这一列的语句被整段注释掉了（D-139），于是两套数据长期不一致。

把已属于 A 的终端加进 B，旧库里会留下两条成员行、`firealarmgroup` 只指向 B：
A 的成员列表从此虚报一台；更糟的是之后编辑 A 时，清成员的那条
`UPDATE terminal SET firealarmgroup = -1` 会顺手把这台终端从 B 也摘掉，**把 B 一起搞坏**。

新版按实际生效语义收敛成一对一：写成员前先把这些终端从别的分区的成员表里摘掉
（`area.go::writeMembers`），并给清成员的 UPDATE 加上 `firealarmgroup = <本分区>` 限定
（`area.go::clearMembers`），使旧库里的脏数据不会被误伤。

现网实测这条链路：

| 步骤 | 结果 |
|---|---|
| 建分区 A，成员 3、4 | `terminalofalarmgroup` 两行，终端 3/4 的 `firealarmgroup` 均为 1 |
| 建分区 B，成员 4、5 | 终端 4 的 A 成员行被摘掉；4→2、5→2、3 仍为 1 |
| 改 A 成员为 5 | 5 的 B 成员行被摘掉；5→1、3 复位 -1、**4 保持 2 不受影响** |

### 8.6 引用失效的映射：旧版整条藏起来，新版标脏

旧列表用 INNER JOIN 关联主机 / 分区 / 媒体，任何一个被删掉，
整条映射就从界面上消失 —— 但它**仍在库里**，报警触发时照样命中。
用户看不见也删不掉，只能靠直接改库。

新版四张表全用 LEFT JOIN，缺失的一方回显「(已删除)」，
并给出 `invalid` / `invalidReason` 让界面标红，用户可以看见并删掉它。

现网实测：删掉媒体后三条映射全部标为
`mediaDeleted: true / invalid: true / "媒体已删除 —— 报警触发时不会正常播放"`，
仍可正常列出与删除。

### 8.7 拼错名字的诱饵表 `terminalofararmgroup`

库里同时存在 `terminalofalarmgroup` 和 `terminalofararmgroup`（`alarm` 拼成了 `ararm`）。
后者现网 0 行，旧代码里也没有任何地方写它。新版只用前者，
但这张表**不能删**（R1 红线：禁止任何 DDL），在此记录以免后人误用。

### 8.8 `firealarmgroup` 的复位值取 `-1` 而不是 `0`

旧代码里复位这一列的那行是被注释掉的，注释掉的写法用的是 `0`。
但列定义的默认值是 `-1`，列注释也写着「-1 表示没有分区」。
新版按**列定义**取 `-1`（`alarm.NoArea`）。`0` 会被当成「分区 id 0」，
而 `alarmarea.id` 是自增无符号，不会有 0，属于一个恰好不炸但语义错误的值。

### 8.9 其余对齐旧版的实现细节

- `alarmarea.name` / `info` / `alarmgroupmap.info` 都是 `varchar(45)`，
  超长 MySQL 静默截断。新版按 **UTF-8 字节数**校验并明确报「上限 45 字节（约 15 个汉字）」。
- 分区名**全局唯一**（BR-195），与旧版口径一致，同样用命名锁串行化查重。
- `terminalofalarmgroup.alarmgroupid` 是 varchar，写入纯数字字符串（BR-200）。
- 新建分区取 id 用 `LAST_INSERT_ID()`，不是旧版的 `SELECT MAX(id)`（D-142）。
- 成员「全删重插」放进事务 —— 旧版没有事务，中途失败分区就变空了（D-140）。
  旧版还把 `LOCK TABLES` 写在 `START TRANSACTION` **之后**（破坏事务），
  且有一处把 `die` 写成了 `dir`，错误被静默吞掉（D-141）。
- 分区成员只列有解码能力的终端（`terminaltype.isdecode = 1`）——
  依据是 `firealarmgroup` 的列注释「只对有解码功能的终端有效」。
- 删除分区会级联删掉该分区下的全部报警映射，删除前用
  `/api/alarm-areas/delete-preview` 如实告知条数（旧版不提示，D-143）。

## 9. 作息方案 / 打铃模块（F-48 ~ F-52）的实测结论

### 9.1 数据模型：方案不是一张表（契约 C-38）

一个「作息方案」= `task` 表中**共享同一个 `task.info`** 的一组行，
每行是一次打铃。方案没有自己的主键行，属性全靠聚合：

```
方案名   = task.info            ← 业务主键
代表 ID  = MIN(taskid)          ← 只用于兼容旧的按 taskid 传参
条目数   = COUNT(*)
起止日期 = MIN(startdate) / MAX(enddate)
状态     = ROUND(AVG(projectstate))
```

过滤条件四项缺一不可：`tasktype IN (1,15)`、`info` 非空串、`channel = 0`、
`sec_task_id = 0`。少一项就会把普通任务或功放子任务混进来。

`planScope()` / `planScopeWithPower()` 两个函数是这条规则的**唯一定义**，
列表、启停、删除、复制全部引用它 —— 旧版正是因为各分支各写各的才有 D-164/D-165/D-176/D-182。

新建条目一律写 `tasktype = 1`（`addonebellplan.php:121` 与 `do.php:11916` 都是
`$tasktype=1`，15 那行在两处都被注释掉了）；查询/删除范围仍按 `IN (1,15)` 兼容存量数据。

### 9.2 ⚠ 手册记错的两处通知报文

| 项 | 手册 §1.3 / §1.4 | 旧代码实际 |
|---|---|---|
| 启停报文的参数名 | `project?state=1&info=<方案名>` | **`&name=`**（`features_wrapper_class.php:359`） |
| 删除通知的粒度 | 「逐条目发 `task?state=6`」 | 只对**用户勾选的那几个 taskid** 发（`belldel_msg` 里 `explode(",", $_GET['id'])`） |

第一条写错了后台服务解析不到方案名，新版按实际实现用 `&name=`。

第二条是旧版的漏发：删一个方案会删掉 18 节课，却只对用户点选的那 1 个 id 发通知，
后台服务继续持有另外 17 个已经不存在的任务。**新版按实际删掉的每个 taskid 发** ——
这是补漏不是改语义。

另外删除通知的 `&type=` 是 **1** 而不是文件广播的 2
（`send_socket_generate_general2("task", 6, $id, 1)`），混用后台会按错误的类型去卸载。

### 9.3 方案名是下发给后台的字符串标识，必须校验字符

启停报文以**方案名字符串**为标识（BR-233）。名字里出现 `?` `&` `=` 会把报文切断，
后台解析到的方案名就不是我们发的那个。旧版对此毫无防护 ——
方案名直接拼进 SQL（D-174），也直接拼进 UDP 报文。

新版 `checkPlanName` 做四件事：`TRIM`、非空、≤255 字节、拒绝 `? & =` 与控制字符。

### 9.4 重名：旧版只拦「别人的同名方案」

旧 `do.php:11833` 的查重条件带了 `AND task_user_id != '$userid'` ——
**同一个用户可以建出两个同名方案**，之后它们被 `GROUP BY info` 聚成一个，
条目混在一起，启停互相影响（D-168）。

新版方案名全局唯一（BR-222），并用 `GET_LOCK('htweb_bell_plan_name')`
串行化「查重 + 写入」。**不能靠唯一索引** —— 加索引是 DDL（红线），
何况 `info` 本来就允许重复：同一方案的每个条目都用同一个 info。

想往已有方案里加条目请走「添加条目」入口，语义更清楚。

### 9.5 改名必须一条语句覆盖全组

改方案名 = 把组内每一行的 `info` 都改掉。旧版逐行 UPDATE 且没有事务（D-169），
中途失败会把一个方案劈成两半：一部分新名、一部分旧名，
之后 `GROUP BY info` 就把它显示成两个方案，**再也合不回去**。

新版一条 `UPDATE ... WHERE info = ? AND <planScopeWithPower>` 覆盖全组，整体在事务里。

### 9.6 打铃时间重复：只提示，不拦截

手册 BR-226 说「同一方案内打铃时间不允许重复」，D-173 说旧版不校验。
但**现网方案「333」的两个条目都排在 08:00:00** —— 真实数据就长这样。
做成硬拦截，用户连编辑这个方案都进不去。

按手册原文「重复时提示」实现：列表返回 `duplicateTimes`，
条目返回 `duplicateTime`，界面标黄提示，不阻断保存。

现网实测：方案 333 的列表行返回 `duplicateTimes: ["08:00:00"]`。

### 9.7 组内属性不一致时如实报出

方案级属性（起止日期、星期、音量、优先级、提前量、发送模式）理论上组内一致，
但旧版逐行 UPDATE 无事务，中途失败就会留下一半新一半旧。
详情接口返回 `mixedAttrs`（哪些属性不一致）、列表返回 `mixedState`（启停状态不一致），
而不是随便取一行糊弄过去 —— 旧版显示的是 `ROUND(AVG(projectstate))` 的多数派，
用户看到「启用」而其中几节课实际停用，界面毫无提示（D-163）。

### 9.8 删除范围补上 `tasktype` 过滤

旧 `belldel_msg` 的范围是：

```sql
WHERE task.info IN (SELECT info FROM task WHERE taskid IN (…) AND info<>'' AND channel=0)
  AND info<>'' AND channel=0
```

**完全没有 tasktype 过滤**（D-182）。只要有一个文件广播任务的 `info` 恰好和作息方案同名，
删方案就会把它一起删掉，且无任何提示。

新版补上 `tasktype IN (1,15,9)`，并在删除预演里回一个 `sameNameOtherTasks` ——
如实告诉用户「库里还有 N 条同名任务，但新版不会删它们」。

同时补齐旧版漏清的三张关联表（D-184）：`terminalkeymaptask`、
`offlinetaskofterminal`、`offlinemediaofterminal`。旧版只清 `mediaoftask` 与
`terminaloftask`，而且是逐条 DELETE（每条任务 3 条 SQL，18 节课 = 54 次往返，D-185）。

### 9.9 复制：三个硬伤

| 编号 | 旧版做法 | 后果 |
|---|---|---|
| D-189 | `SET sec_task_id = '$taskid_row[taskid]' - 1` | 假设「功放子任务 ID = 主任务 ID + 1」。并发插入或表里有自增空洞（删过任务就有），子任务挂到毫不相干的任务上 |
| D-190 | `INSERT … SELECT` 字段清单不完整 | `endtime`、`disableday`、`interval_s`、`intplaylength`、`intplaylengthtype`、`localplay`、`keyid`、`offlinestate` 全丢成默认值 |
| D-191 | `WHERE taskid = (SELECT MAX(taskid) FROM task)` | 并发下拿到别人的任务 |

新版：显式 33 列的 `INSERT ... SELECT`（列错位会当场报错而不是静默错位），
主任务先插拿到 `LastInsertId`，再用这个真实 ID 写子任务的 `sec_task_id`，全程一个事务。

### 9.10 新版自身的缺陷 N-09（本轮发现并已修复）

**N-09 条目级接口的通知漏带音量**

`task?state=4&id=X&volume=V` 里的 `volume` 是后台服务用来设置任务初始音量的。
「加条目」「改条目」「复制方案」三个入口最初写死传 `0` ——
后台会把音量设成 0：任务照常触发，但**一点声音都没有**，而界面上一切正常。

现网日志里抓到的原始报文：

```
task?state=4&id=70045&volume=0     ← 加条目
task?state=5&id=70039&volume=0     ← 改条目
task?state=4&id=70047&volume=0     ← 复制
```

修复：`AddItem` / `Copy` 从方案带出 `defaultvolume`，`UpdateItem` 从条目自身读。
复验后同样三个入口的报文全部变成 `volume=55`（测试方案音量）。

## 10. 日志模块（F-54 / F-55）的实测结论

### 10.1 新版此前一行操作日志都不写 —— 审计断档

这是本轮开工时才发现的：`log` 表在新版代码里**只有 doctor 探活查过一次**，
没有任何写入。旧 PHP 在 `do.php` 派发器末尾统一调一次
`insert_log($opt, $olduser)`，每个写请求落一行，`$opt` 就是动作名
（现网库里能看到 `start_mediatask`、`update_mediafile` 这类原始动作码）。

也就是说：新版做的任何操作都查不到，日志页面只能看见旧系统和后台 C 服务的记录。

新增 `internal/audit` 包 + `auditMux` 路由包装层，照搬旧版的粒度：
**一个写请求落一行**，操作名从 `auditLabels` 表按路由模式取中文描述。

做成中间件而不是逐个 handler 里写，理由是四十多个写接口手写迟早会漏几个，
而「漏记」平时完全看不出来，只有出事要追责时才发现。

与旧版一致的两点：`log.time` 写**东八区字符串**（契约 C-15，用 `FixedZone`
而不是 `LoadLocation`，目标机可能没有 tzdata）、`log.user` 按 11 字符截断（C-16）。

与旧版不同的一点：**只在业务码为 200 时记录**。旧版无论成功失败都记，
连 `default` 分支的「非法操作」也记；失败请求记进操作日志会让审计噪音大到没法看，
排查失败看访问日志（那里逐条带状态码）。

### 10.2 `log` 表是三方共用的 —— 清空会波及后台服务

现网 156 行（本轮测试前）里能分出三个写入方：

| `user` | 条数 | 谁写的 | 典型 `operate` |
|---|---|---|---|
| `server` | 52 | 后台 C 服务 | 回收临时文件0 |
| `主机:-1` | 35 | 后台 C 服务 | 播放通道:1, 节目:8 / 停止通道:1 |
| `admin` | 9 | 旧 PHP Web | 用户登录 / 修改方案任务 |
| （空） | 60 | 旧 PHP Web，会话里没有用户名 | start_mediatask / stop_mediatask |

**清空日志会连 C 服务的记录一起清掉，而且清完它还会继续往里写。**
旧版是无差别 `TRUNCATE`，从没提示过这一点。
新版在 `/api/logs/stats` 里单列 `fromServer` 条数，清理面板上直接写出来。

列表另外回一个 `source` 字段（后台服务 / Web / 未知）做展示区分，不落库。

### 10.3 旧版这一页是全站可利用性最高的注入点

```php
"... where log.".$_GET['searchkey']." like '%".$_GET['searchvalue']."%'"
```

**列名和值都来自 URL、都是拼接**（D-199）。列名那个位置参数绑定用不上，
只能走白名单；值走参数绑定。排序 `ORDER BY ".$searchsequence." DESC`
同样是裸拼（D-200）。

现网复验：`searchKey=id=1 OR 1=1 --` 被忽略（回落成不筛选，200 正常返回），
`orderBy=id;DROP TABLE log` 回落默认排序；而合法的
`searchKey=operate&keyword=登录` 精确返回 4 条 —— 白名单没有误伤正常功能。

### 10.4 清空日志不能用 TRUNCATE

旧版用 `TRUNCATE TABLE log`（D-201）。TRUNCATE 是 DDL 级语句：
隐式提交、不可回滚、重置 AUTO_INCREMENT。在「禁止任何 DDL」的红线下尤其不能用 ——
何况新版的数据库账号 `htweb` 只有 DML 权限，TRUNCATE 会被服务器直接拒掉。

改用 `DELETE`，并支持三种模式：`all` / `beforeDate` / `keepDays`（BR-250）。

### 10.5 清空前先写审计，用 id 作分界

旧版清空日志本身不留痕（D-202）：谁清的、什么时候、清了多少，全查不到。

新版在同一个事务里**先插一条审计记录**，再删 `id < 审计记录id` 的行。
用 id 而不是时间作分界——同一秒内可能有别的写入。这样审计记录必然是幸存者，
且删除条数已经写在它的描述里。

现网复验（刻意选一个命中 0 条的条件，不动真实数据）：

```
DELETE /api/logs {"mode":"beforeDate","beforeDate":"2000-01-01","confirmed":true}
→ {"deleted":0,"auditLogId":164,"kept":164,"describe":"2000-01-01 之前"}
log 表新增一行：admin | 清空操作日志（2000-01-01 之前，共 0 条） | 127.0.0.1
```

2013 年的种子行完好，`MAX(id)` 与行数一致（= 自增没被重置，确认没走 TRUNCATE）。

### 10.6 ⚠ 任务日志文件是**混合编码**的

这是手册完全没提、本轮实读文件才发现的。

现网 `log2026-05-08.html`：表头那行是 **GBK**（「时间」= `CA B1 BC E4`），
而事件行里的「终端上线」是 **UTF-8**。同一个文件里两种编码。
`log2026-08-19.html` 则是**整个文件都是 GBK**。

旧 `setlog.php` 是 `$smarty->display("datelog/$filename")` —— 把文件原样塞进
HTML 页面输出，浏览器按页面 charset 解析，所以旧页面对其中一半内容一直是乱码，
只是没人深究过。

新版按**行**判别并转码：一行里只要出现非法 UTF-8 字节，整行按 GBK 解。

**为什么必须按行而不是按字节**：GBK 的双字节序列可能碰巧构成合法 UTF-8 ——
上面那个 `CA B1` 解成 UTF-8 就是 U+02B1（ʱ），一个完全合法但毫无意义的字符。
所以「这段字节是不是合法 UTF-8」在字节粒度上不足以判别编码。

**转码路上踩的两个坑**（都是现网实测出来的，值得记下来）：

| 写法 | 结果 |
|---|---|
| `CONVERT(_binary ? USING gbk)` | **语法报错** Error 1064。`_binary` 是字面量引导符，只能贴在字面量前面，贴在占位符前面直接挂 |
| `CONVERT(CAST(? AS BINARY) USING gbk)` | **语法过了，但结果全是 `???`**。连接字符集是 utf8，参数在**进入服务器时**就被当成 utf8 文本，其中的非法字节在那一刻已经被替换成 `?`，轮不到 CAST 去剥字符集 |
| `CONVERT(_binary 0x<hex> USING gbk)` | ✅ 正确。十六进制字面量不经字符集解释，字节原样进服务器 |

拼接 hex 到 SQL 里是安全的：hex 编码的输出只有 `[0-9a-f]`，带不出引号或分号。

之所以用 MySQL 转而不是引入 `golang.org/x/text`：转 GBK 需要一张映射表，
给这个锁死依赖的部署环境新增模块不合适（构建机也不一定能联网拉取），
而 MySQL 本来就带着全套字符集 —— 终端模块的 GBK 校验用的也是同一个办法。

现网复验：`log2026-05-08.html` 转了 3 行，表头还原成「时间/终端IP地址/操做/状态/参数」，
UTF-8 的正文行原样保留；`log2026-08-19.html` 转了 50 行，整篇可读。

## 17. 新版自身的缺陷（续）

### N-18 单元格插槽里访问 `scope.row` 的嵌套属性，会让整张表只剩最后一列

**这是新版自己写出来的 bug，不是旧版遗留。级别：高 —— 一旦踩上，整页数据看不见。**

**现象**：文件广播页（`/task`）表格只显示一个「操作」列，
表头、勾选框、展开箭头、其余 11 列全部消失，
控制台**不报任何错**，Vue 也不发警告。

**根因**在 Element Plus 的 `el-table-column`：

```js
// element-plus/es/components/table/src/table-column/index.mjs  render()
try {
  const renderDefault = this.$slots.default?.({ row: {}, column: {}, $index: -1 });
  //                                             ^^^^^^^^ 空对象
  ...
} catch (e) {
  return h("div", []);      // ← 异常被自己吞掉，外面什么也看不到
}
```

它每渲染一列，都会先拿 `row = {}` **空跑一遍单元格插槽**，
目的是识别「这一列里是不是又套了子列」（多级表头）。

于是插槽里写：

```vue
<template #operation="scope">
  终端({{ scope.row.terminals.length }})   <!-- ❌ row 是 {} → terminals 是 undefined → 抛 TypeError -->
</template>
```

空跑时就抛异常。EP 用 `try/catch` 吞了异常，但**异常是在 Vue 渲染过程中抛出的** ——
`openBlock()` 已经调用、`closeBlock()` 没机会执行，block 栈就此错位。
结果是这张表后续的列全部挂不上 `el-table` 的 store：
`_columns` 最终只剩最后一个插入进去的列。

**排查时的关键读数**（现网 dev 环境实测，留作以后复现的参照）：

| 观察点 | 值 | 说明 |
|---|---|---|
| `props.columns` | 14 条，`isShow` 全 true | 列配置本身没问题 |
| `.hidden-columns` 里的 `<div>` | 14 个，位置 0..13 | 列组件确实都挂载了 |
| `store.states._columns` | **1 条** | 只有最后一列进了 store |
| 控制台 | 空 | EP 吞掉了异常，什么都不打 |

一开始怀疑过 `v-for` 的 `:key="item"`（对象当 key）、`type: "expand"` 列、
列表里那段 HTML 注释、弹窗里的 `el-table` —— 逐个排除，全不是。
最后靠「把插槽一个个改名禁用」二分出来：**只留 `#operation` 仍然坏，全禁用就好了**。

**修法**：单元格插槽里凡是访问 `scope.row` 的**嵌套属性**，一律加可选链。

```vue
{{ scope.row.terminals?.length ?? 0 }}
<span v-if="!scope.row.media?.length">未设置</span>
```

⚠ 注意这条规则同样适用于**弹窗里手写的 `el-table`** ——

### N-19 文字语音任务的 `task.cmd`（TTS采播终端）被修改操作抹成 0

**这是新版自己写出来的 bug。级别：高 —— 会静默丢掉后台执行任务所需的配置。**

`typedtask/edit.go` 的 `cmdOf()` 原来只给终端功放和采播填 `cmd`，
文字语音走 `return 0, "0"`。于是**每次修改一条文字语音任务，`cmd` 都被写成 0**。

现网数据说明这一列对文字语音是有意义的：

| taskid | tasktype | cmd | 含义 |
|---|---|---|---|
| 70033 | 15 | 2 | terminal.id = 2 |
| 70014 | 19 | 12 | terminal.id = 12 |

`:80` 的文字语音表单里这一项叫「**TTS采播终端**」，也就是「由哪台 TTS 主机去合成」。
抹成 0 之后这条任务就没有合成方了。

**修法**：`cmdOf()` 里把 `KindTTS` 并进 `KindCollect` 分支（两者都是往 `cmd` 写终端 id），
详情接口补上终端名，界面上新增「TTS采播终端」下拉，修改时回填原值。

⚠ 顺带一条同源的坑：**终端功放的 `prepower` 不能当业务字段用**。
功放列表的判据是 `channel=0 AND sec_task_id=0 AND prepower=0`
（`typedtask.go` 的 `spec.Extra`）—— 给功放任务写了非 0 的 prepower，
它立刻从自己的列表里消失。所以 :80 的功放表单里没有「预开电源」，
新版 `normPerKind()` 也对功放强制 `prepower = 0`。

### N-20 ~ N-22 LED 播放整条链路都串错了

**三个连在一起的缺陷，都是新版自己写的。级别：高。**

#### 真实的表关系


| 70024 | 30 | 0 | 独立的 LED 任务 |

#### N-20 `ledsentence` 的关联键用错

以为 `mediaoftask.mediaid` 存的是 `ledsentence.id`，于是到处写

实测不成立：现网 `mediaoftask.mediaid` 是 59/63/67/68，而 `ledsentence.id` 只有 1~4；

按 `tasktype = 24` 查，现网**一条都没有**。真实数据全是 30。

#### N-22 删除任务时漏清 LED 子任务与虚拟媒体

#### 启用管理为什么要拆成两条

`enabletask.enstate` 是**整行一个值**、`taskid` 是一串 id ——
一条记录装不下「这几条启用、那几条停用」两种意图，红线又禁止改表。

所以：界面上是一个时间点，库里最多两行（启用一行、停用一行，日期时间相同）。
这不是绕过表结构，而是把「一个时间点要做两件事」如实写成两行 ——
后台扫表时本来就是逐行执行的。

编辑时以被编辑那行的**原日期时间**为一个「时间槽」，槽里最多维护两行：
某一侧变空就删掉那行，原本没有的一侧就新建。所以反复编辑不会越攒越多。

**现网实测**：

```
新建 2 启用 + 2 停用  → created=[2,3]              （拆成两行）
读回时间槽            → 启用 2 条 / 停用 2 条        （合并回一个对象）
改成全部启用          → updated=[2] deleted=[3]     （停用那行被删掉）
清理                  → 剩余计划数 0
```

### N-23 备机模式把「服务器信息」这一页自己也锁死了

**这是新版自己写出来的 bug。级别：高 —— 一旦踩上，只能进数据库才能救回来。**

原来的口径（BR-260）是：`serverbaseparam.model = 2`（备机模式）时
`u.ReadOnly = true`，`RequireRight` 对**所有**带权限的接口一律回 40302，
`serverparam.Save` 也直接 `ErrReadOnly`。

问题在于：**主备模式的开关就在「服务器信息」这一页上**。
所以只要在这一页把模式切成「备份服务器」，这一页立刻连读都读不到，
再没有任何界面能把它改回主服务器 —— 只能直接改数据库。

**修法**：新增 `RequireRightAllowReadOnly`，只给「服务器信息」那一组接口用：

| 接口 | 备机模式下 |
|---|---|
| `GET/PUT /api/server/params` | **放行**（仍然校验 serverpriv） |
| `GET/PUT /api/server/auto-restart` | **放行** |
| 其余所有带权限的接口 | 照旧 40302，全站只读 |
| `POST /api/server/factory-reset` | 仍然禁止 —— 那是清库，不是改配置 |

界面上同步把 `readonlyMode` 的 20 处 `:disabled` 去掉，
警示条改成「其余模块只读，本页照常可改」。

**回归测试**：`server/internal/auth/readonly_test.go`（5 个用例，不连数据库、不碰生产）

```
备机 + 普通模块        → 40302  拦下
备机 + 服务器信息      → 200    放行   ← 就是这个 bug
备机 + 无 serverpriv   → 40301  仍然校验权限
主机模式               → 两条中间件都放行
```

⚠ 验证时特意**没有**去动生产库的 `model` —— `ReadOnly` 是登录时快照进会话的，
要真验就得「改库 → 重新登录 → 测 → 改回」，而现网有人在用。
写成 Go 测试既严谨又零风险，还能防以后回归。

## 19. 服务器信息 / 时间设置与 :80 的逐项对照

`serverbaseparam` 一共 48 列，逐列查过。两处关键结论：

### 「重启设置 / 重启时间」不在 serverbaseparam 里

那张表**没有任何重启或关机相关的列**。:80 上显示的「重启时间 04:00:00」
实际来自 `task` 表里那条系统任务：

```
taskid 70000  taskname 'reset'  tasktype 13  playtime 04:00:00  exemodel 0001000
```

`tasktype = 13` 就是「系统任务」，`audioserver.sql` 的建表脚本里自带这一行，
后台 C 服务扫到它就按 playtime 定时重启整机。所以新版的读写也落在 task 上：

| :80 的项 | 落在哪 |
|---|---|
| 噪声设置 | `serverbaseparam.sounddetect`（就是我们原来叫「声压检测」的那一项） |
| 重启设置 | task 70000 的 `projectstate`（⚠ 0 = 启用）+ `cmdargs='0'` |
| 重启时间 | task 70000 的 `playtime` |
| 关机设置 | 同一条 task 70000 的 `projectstate` + `cmdargs='shutdown'` |
| 关机时间 | 同一条 task 70000 的 `playtime`（**与重启时间共用这一列**） |

关掉只把那条系统任务置成停用，**不删它** —— 它是建库脚本自带的行。

#### ⚠ 关机不是「没做完」，是存在同一条记录上 —— 而且和重启互斥

早前这里写的是「关机设置/关机时间无存储，旧系统没做完」。**这个结论是错的**，
在 `ok112/do - 副本.php` 第 6006~6046 行里找到了真正的实现 —— 它只写这一条 SQL 的三种形态：

```sql
-- 重启启用
UPDATE task SET projectstate='0', playtime=<重启时间>, cmdargs='0'        WHERE taskid=70000;
-- 重启停用 + 关机启用
UPDATE task SET projectstate='0', playtime=<关机时间>, cmdargs='shutdown' WHERE taskid=70000;
-- 两个都停用
UPDATE task SET projectstate='1'                                          WHERE taskid=70000;
```

由此三条结论：

1. **只有一个 `playtime`**，重启时间和关机时间共用它，同时只有一个有值；
2. `cmdargs` 是判别位：`'0'` 是重启，`'shutdown'` 是关机；
3. 两者**互斥**，旧版先判重启，所以都开时以重启为准。

:80 上关机那两项是灰的，但那只是**界面**没放开，存储一直都在。
新版把它放开了：两个开关联动，开一个自动把另一个置成停用（因为库里只存得下一个）。

#### ⚠ 顺带修掉一个会「到点关机而不是重启」的隐患

新版原来的 `SaveAutoRestart` 只写 `projectstate / playtime / exemodel`，**从不写 `cmdargs`**。
如果库里那条正好是 `cmdargs='shutdown'`，在界面上点「重启设置 = 启用」，
存出来的其实仍是一条**关机**任务 —— 到点直接关机。现在每次都显式写 `cmdargs`。

另外 `cmd` 列在这条任务上存的是旧版的「复杂密码」开关（`fuzamima`），与重启/关机无关，
所有 UPDATE 都不碰它。

现网实测（三种形态往返，做完已还原成原样 reboot / 04:00:00 / 0001000）：

```
reboot   04:00:00 → shutdown 22:30:00 → reboot 04:00:00 → off → reboot 04:00:00
exemodel 全程保持 0001000 不变
```

### 19.1.3 全站选终端的地方统一改成树

产品要求：除「终端管理」页本身外，所有用到终端的地方都做成树形，直观。

改之前全站有 **15 处**终端选择控件，除「音乐下发」外**全是扁平 el-select** ——
几百台终端拉成一条长列表，看不出哪台在哪个分区。

#### 先扫清了三个障碍

**① 七个接口字段名互不一致。** 主键有的叫 `id` 有的叫 `terminalId`；
名称有的叫 `name` 有的叫 `terminalname`。改接口会牵动一堆别的调用方，
所以在组件里做了一层适配（`normalize()`），两种写法都认。

**② 四个接口根本没有分组字段**，建不了树。补上了 `groupName`：

| 接口 | 原来 | 现在 |
|---|---|---|
| `typedtask.TerminalOptions` | 只有 `groupId`，没有名字 | 加 `groupName` |
| `timeset.Terminals` | 无 | 加 `groupName` |
| `sound.TerminalOptions` | 无 | 加 `groupName` |
| `alarm.AlarmHosts` | 无 | 加 `groupName` |

取值方式与 `task/picker.go` 一致（分区名在 `serverplaystream`，
终端与分区的关系在 `terminalofgroup`，一台终端取 id 最小的那条）：

```sql
COALESCE((SELECT sps.name FROM terminalofgroup tog
          JOIN serverplaystream sps ON sps.streamid = tog.groupid
          WHERE tog.terminalid = t.id ORDER BY tog.id LIMIT 1), '')
```

全部是只读子查询，零 DDL。

**③「没有分区」后端有两种写法。** `task` / `alarm` 那两个接口在
`fillOptionGroupNames` 里填的是字面量 `"(未分区)"`，其余接口返回空串 ——
不处理的话同一棵树上会同时冒出「(未分区)」和「未分区」两个组。
组件里统一归一化掉。

#### 两个组件

| 组件 | 形态 | 用在哪 |
|---|---|---|
| `components/TerminalTree/index.vue` | 整棵树摊开，带搜索 / 全选 / 清空 / 已选计数 | 对话框里「勾一批终端」，10 处 |
| `components/TerminalTree/Select.vue` | 收成下拉，展开后仍是同一棵树 | 表单里一格宽的**单选**，4 处 |

为什么分两个：像「TTS采播终端」「采播源终端」「LED 所属终端」「北斗校时」
「报警主机」这些都躺在 `:span="12"` 的表单格里，塞一棵 300px 高的树会把对话框撑变形。

⚠ 取选中值必须用 `getCheckedNodes(true)`（`true` = 只要叶子）。
分组是虚拟节点，不加这个参数会把分组也算进结果里，而它没有 `terminalId`，
会变成一串 `NaN`。组件里除了传 `true`，还额外 `filter(n => !!n.terminalId)` 兜了一道。

#### 顺带修掉一类会显示裸「0」的 bug

`adjusttime = 0`、`sourceTerminalId = 0` 在库里都表示「未选 / 不指定」，
但下拉里**没有** `0` 这个选项。直接把 `0` 塞进 `v-model`，
el-select / el-tree-select 找不到匹配项，就把裸的「**0**」显示在框里，占位符也不出现。
现网实测中「北斗校时」和「采播源终端」两处都是这个现象。
现在 `0` 一律当成「未选」，除非调用方显式声明了一个「（不指定）」选项。

#### ⚠ 第一版做反了：分区节点必须来自**分区表**，不能从终端归纳

第一版是遍历终端、按 `groupName` 分桶。后果是**一台终端都没有的分区根本不会出现** ——
现网只有一个空分区「22」，于是树上只剩「无分区终端」一个节点，看着就像分组没做。

对照 ok112 的 `inc/common.php:get_terminallist5()`，它的做法是：

```php
// ① 先遍历 serverplaystream 全表，每个分区都出一个 <item>，哪怕是空的
while ($rowstream = mysqli_fetch_array($resultstream)) {
    $tree_str .= "<item text=\"{$rowstream['name']}\" id=\"stream_{$rowstream['streamid']}\">";
    //   ② 再查 terminalofgroup 把该分区的终端填进去
    $tree_str .= "</item>";
}
// ③ 最后一个节点：terminal.id NOT IN (SELECT terminalid FROM terminalofgroup)
$tree_str .= "<item text=\"无分区终端\" id=\"stream_0\"> … </item>";
```

树的骨架来自**分区表**，终端只是往里填。现在与它一致：

- 分区清单走 `/api/zones/options`（同样是遍历 `serverplaystream`，按 userid 收敛可见范围）
- 组件自己拉，结果在 `TerminalTree/zones.ts` 里做进程内缓存 —— 全站 14 处树共用一次请求，
  不用在 14 个调用点各写一遍；终端分区页保存/删除后调 `invalidateZones()` 让缓存失效
- 「无分区终端」措辞照 ok112 的 `language/chinese.php`：`No_group_terminal = "无分区终端"`，恒排最后
- ⚠ 与 ok112 有一处**故意的出入**：它在没有无分区终端时不输出这个节点，
  新版恒输出。这样「一台都没归位」和「归位完了」两种状态下树的行数不会突变。

**归组按 id 不按名字。** `serverplaystream.name` 上没有唯一索引（建索引属 DDL，红线禁止），
两个同名分区按名字归会被并成一个。为此给 `timeset` / `sound` / `alarm主机`
三个接口补了 `groupId`（原先只补了 `groupName`），终端分区页则用
`currentZoneId` / `currentZoneName`。

#### 验证

现网只有 1 个终端分区（名叫「22」）而且 `terminalCount = 0`，
真实数据下的结果（三处抽查一致）：

```
  22          [0 台]        ← 空分区照样出现，这就是修复点
  无分区终端  [12 台] -> 服务器1.53 / 一体化音箱166 / …
```

分区归属的正确性用浏览器端假数据验（只改浏览器收到的响应，服务器和数据库不碰）：


（只改浏览器收到的响应，服务器和数据库一个字节都不碰）：

### 19.1.4 N-24 按回车登录必报「验证码错误」——双提交把验证码吃掉了

**这是新版自己写出来的 bug，级别：高（挡住登录）。用回车登录 100% 复现，点按钮不会。**

现象：验证码输的是对的，却提示「验证码错误」。

`LoginForm.vue` 上挂了**两个**回车处理器：

| 位置 | 触发时机 |
|---|---|
| `onMounted` 里的全局 `document.onkeydown` | keydown |
| 验证码输入框上的 `@keyup.enter` | keyup |

在验证码框里按一次回车，两条路各调一次 `login()`，发出**两个** `/api/login`。
而验证码是**一次性**的（`captcha.Verify` 无论对错都 `delete`），于是：

1. 请求 #1 到达服务端 → `Verify` 通过并**删除**该 id
2. 请求 #2 发出时，`axiosCancel` 判定是重复请求，**取消了 #1**
3. 服务端处理 #1 到一半发现客户端跑了 → `[500] 登录: 读取服务器参数: context canceled`
4. 请求 #2 带着**同一个** id 上来 → 已被删除 → 「验证码错误」

现网日志里的形态（2026-08-27 08:16:02）：

```
POST /api/login  200 0s      ← #1，被取消
GET  /api/captcha 200 1ms
POST /api/login  200 81ms    ← #2，报验证码错误
[500] 登录: 读取服务器参数: context canceled
```

`document.onkeydown` 里那句 `if (loading.value) return` 挡不住，因为
`loading = true` 原来写在 `formEl.validate` 的**异步回调**里 ——
keyup 到来时第一次的回调还没跑到那一行。

**修法两条**：

1. 去掉验证码输入框上重复的 `@keyup.enter`（全局那个已经管回车了）
2. 重入锁**同步**加在 `login()` 最开头，不放在 validate 回调里 ——
   这样连点两下按钮也只发一个请求

**复现与复验**（用 CDP 数 `/api/login` 的实际请求条数）：

| | 修之前 | 修之后 |
|---|---|---|
| 在验证码框按回车 | **2** | 1 |
| 连点两下「登录」 | — | 1 |
| 点一下「登录」 | 1 | 1 |

修完用真码走了一次完整登录：请求 1 条、跳到 `#/home`、token 已写入。

### 19.1.5 N-25 隔夜之后早上第一个请求必失败（连接池被 MySQL 掐了）

排 N-24 时在同一段日志里发现的，是另一个独立问题。

`store.go` 为了躲开每次建连约 10 秒的反向 DNS 代价，把
`SetConnMaxLifetime(0)` 和 `SetConnMaxIdleTime(0)` 都设成了「永不回收」。
但**我方不回收 ≠ 对方不关闭**：MySQL 的 `wait_timeout`（默认 8 小时）到点
会把空闲连接单方面掐掉，而 `database/sql` 并不知情。

现网实测：服务 08-26 18:25 启动，隔夜无人访问，次日 08:16 第一批请求全部撞上死连接：

```
[mysql] packets.go:149 write tcp …->127.0.0.1:3306: write: broken pipe
[mysql] connection.go:706 closing bad idle connection: connection reset by peer
[500] 登录: 读取服务器参数: context canceled
```

**没有改成 `ConnMaxIdleTime`**：那等于让连接定期自杀重建，10 秒的建连代价
会落在某个倒霉用户的请求上。改成加一个后台 `keepAlive` goroutine，
每 4 分钟把池里每条连接都 ping 一遍（和 `warmUp` 一样，先全部攥住再一起放，
否则只会反复 ping 同一条）。ping 不通的当场 `Close` 剔除，
重建的代价落在后台而不是用户请求上。

4 分钟远小于任何常见的 `wait_timeout`（最短的默认值也有 600 秒），
代价是每 4 分钟几条 ping，可以忽略。

### 19.1.6 备份还原补上「上传备份包」

原来这一页只能「在本机备份 → 在本机还原」：下载下来的包、或者从另一台机器
拿来的包，**没有任何途径传回去**，也就还原不了。换机器、装新服务器、
从归档里取一个旧包回滚 —— 三件事全都做不成。

新增 `POST /api/backups/upload`（超管）。传上来的包落进备份目录，
之后与「本机自己备的包」完全等价：同一个列表、同一套还原前置检查、同一条恢复路径。
**不新增任何存储、不碰数据库。**

实现要点：

- **流式收，不用 `ParseMultipartForm`。** 后者会先把整个请求体读进内存/临时文件
  再交给你，一个 80MB 的包就是 80MB 的内存峰值。用 `MultipartReader` 边读边写盘，
  内存占用恒定。
- **先落临时文件 → 校验 → 原子改名落位。** 任何一步不过就删临时文件走人，
  不往备份目录里丢半成品。同目录 rename 是原子的，列表里要么看不到、要么是完整的包。
- **同名不覆盖**：目录里已有同名包时自动加时间戳后缀。覆盖是不可接受的 ——
  上传一个碰巧同名的包会把本机那份备份悄悄弄没。
- **上传阶段不比对结构指纹**。指纹不一致的包照样收下，兼容与否由列表里的
  `compatible` 显示，真正的拦截在 Precheck / Restore（BR-272）。
  上传就拒收会让人连包里是什么都看不到。

四道校验：大小上限 512MB、必须是能打开的 zip、包内必须有 `_manifest.json`
且格式版本认识、包内条目路径不许有 `..` 或绝对路径（zip slip）。
上传文件名只取 basename 且 `/` 与 `\` 都算分隔符 ——
`filepath.Base` 在 Linux 上不认反斜杠，`..\x.zip` 会被原样留下。

现网实测（做完已把测试包删干净，只剩原来那两个 `bk-*`）：

| 用例 | 结果 |
|---|---|
| 下载一个包再用**同名**传回 | 200，自动改名 `pkg-20260827-093526.zip`，原包未被覆盖 |
| 传一个不是 zip 的文件 | 40001「不是有效的 zip 文件」 |
| 传一个 zip 但没有清单 | 40001「这不像一个本系统的备份包：包内没有 _manifest.json」 |
| 传空文件 | 40001「上传的文件是空的」 |
| 文件名 `../../etc/evil.zip` | 路径成分被剥掉，随后按内容拒收 |
| 备份目录残留 `.upload-*` 临时文件 | 0 个 |

### 19.1.7 :80 的第二套协议：sdk:8877 二进制 UDP（已验通）

排「终端管理 → 批量操作」对齐时挖出来的，**比对齐本身更重要**。

#### 两套协议，不是一套

| | ok112（旧 PHP） / 新版 htweb | :80（oktw + lumen） |
|---|---|---|
| 通道 | UDP **文本**：`terminal?state=1&id=5` | UDP **二进制**：`setbianma(cmd, len, states, args)` |
| 目标 | `127.0.0.1:8886`（serverbaseparam.webport） | `sdk:8877` |
| 命令号 | state=0 停止 / 1 启动 / 3 对讲开 … | cmd=16 启用 / 17 禁用 / 18 对讲开 / 256 读服务属性 … |

新版一直只会说文本那套，所以 :80 上很多批量操作在我们这边**根本没有对应的下发手段** ——
不是没做界面，是没有通道。

#### 帧格式（`lumen/app/Models/Serverbaseparam.php:setbianma`）

16 字节头 + 载荷，**小端**：

```
偏移  0   2     4     6        8         12        16
     AAAA cmd   len   states   serial    session   args…
     u16  u16   u16   u16      u32=0     u32=用户id
```

响应同样以 `0xAAAA` 开头；各接口按自己的偏移解载荷。

#### ⚠ 端口没有发布到宿主，但宿主够得着

`a9000_sdk` 容器**没有 publish 任何端口**，宿主上只监听着 8886。
但它在 `a9000_panetwork` 上有地址 `212.218.2.153`，而宿主有这个网段的路由：

```
212.218.2.0/24 dev br-ccd7c4f108dd proto kernel scope link src 212.218.2.1
```

所以宿主可以直接发到 `212.218.2.153:8877`，**不用改 docker 编排**（符合部署原则 P1~P3）。

⚠ 容器 IP 不能写死在配置里 —— 容器重建后会变。要按容器名/网络别名解析，
或者从 `docker inspect` 取，运行时探。

#### 实测验证（只读命令 256，没改任何东西）

```
发: aa aa | 00 01 | 1c 00 | 00 00 | 00000000 | 01000000
收: 44 字节，header=0xaaaa cmd=256 len=28
    偏移16 噪声=0  偏移20 重启=1  偏移24 关机=0  偏移28 "04:0…"
```

与数据库里的「噪声停用 / 重启启用 04:00:00 / 关机停用」逐项吻合，帧格式与字节序确认无误。

### 19.1.8 ⚠ :80 的「重新注册」其实是删除终端（踩过坑）

`oktw` 的批量操作定义里：

```js
{ name:"重新注册", code:"delete", permission:"terminal-option-delete",
  single:!1, isNetwork:!1, api: g.delete }
```

名字叫「重新注册」，`code` 和接口都是 **delete**，而且 `isNetwork:false`（**离线终端也照删**）、
点了**不弹确认框**。在线设备被删后会自行重新注册回来，所以看着像"重新注册"；
**离线设备就是丢了**。

2026-08-27 在现网踩实：用脚本勾选全部终端后逐个点批量操作项做界面调研，

`terminaloftask`(37 行)、`userterminal`(5 行) 等按旧 id 建立的关联随之悬空。

**教训**：不要在生产系统上脚本化点击语义未知的菜单项。
先读源码判定每一项是「打开对话框」还是「立即执行」，再决定能不能点。

新版实现这一项时：**保留「重新注册」这个名字**（与 :80 一致），
但必须加确认框，说明它会删除终端记录、在线设备会自动注册回来、
离线设备会丢，并列出本次影响的离线台数。

### 19.3 免密 sudo：从「手工配、漏了不报错」变成部署脚本的一步

版本设置的提交、时间设置的两个按钮，都要以 root 跑几条具体命令，
而 htweb 以普通账号运行。缺规则时它们只是**静静变灰** —— 换台机器就得重排一遍。
现在固化成 `deploy/install-sudoers.sh`，由 `deploy/install.sh` 自动调用。

装的内容（`/etc/sudoers.d/htweb`，0440 root:root，`visudo -c` 校验后原子替换）：

```
Cmnd_Alias HTWEB_CLOCK = /usr/bin/timedatectl set-time *, /usr/bin/timedatectl set-ntp *
Cmnd_Alias HTWEB_AUDIO = /opt/apps/a9000/script/cmd/update_audioserver.sh
tw ALL=(root) NOPASSWD: HTWEB_CLOCK, HTWEB_AUDIO
```

排这件事的过程中挖出**三个会让「配了也不生效」的坑**，都已修：

#### 坑 1（最隐蔽）：`NoNewPrivileges=true` 让 sudo 根本调不动

原来的 systemd 单元里有这行，看着像加固。但 `NoNewPrivileges` 会禁掉整个
**setuid 提权路径**，而 sudo 正是 setuid 程序 —— sudoers 写得再对，
服务里的 `sudo -n` 也一律失败，报的还是「服务账号没有免密权限」，
指向一个明明已经配好了的地方。**光加 sudoers 是不够的，这一行必须去掉。**
`deploy/htweb.service.in` 里注释掉了并写明原因；真正的边界在 sudoers 那一侧。

#### 坑 2：探测用的命令不在放行名单里

原来两处都用「随便跑条命令」来探能力：

| | 原来探的 | 问题 |
|---|---|---|
| clock.go | `sudo -n timedatectl status` | `status` 不在放行名单里 |
| version.go | `sudo -n true` | `true` 更不在名单里 |

受限免密下这两条都会失败，于是**装好了的机器被误判成没装**。
改成 `sudo -n -l <与真正要跑的那条形态一致的命令>` —— `-l` 只查权限不执行。

#### 坑 3：`update_audioserver.sh` 必须用 `sudo` 跑，不能直接跑

原来是 `exec.Command(脚本)`。脚本内部每条都是 `sudo docker ...`：
以服务账号身份执行时，那些**内层** sudo 会去要密码；以 root 执行时，
root 再 sudo 才不需要密码，整条链才通。

#### 顺带修正：NTP 在跑不该是阻断条件

原来是「`NTPActive` → `CanSet=false`」。但现网这台机器是
`NTP service: active` 而 `System clock synchronized: **no**` ——
内网够不着上游，自动校时形同虚设，手工拨的时间反而留得住。
按原逻辑等于把一个能用的功能永久挡死。

改成：`NTPActive` 只给一句提醒（分「已同步」「未同步成功」两种措辞），
要不要关掉自动校时由操作员在界面上**明确勾选**
（勾了才执行 `timedatectl set-ntp false`，且先关校时再拨表 —— 反过来的话
两条命令之间那一小段时间里 NTP 还在跑，刚拨好的值可能立刻被改掉）。
程序不替操作员去动系统服务。

#### 现网验证结果

```
NoNewPrivileges=no
GET /api/time            → canSetClock:true, ntpActive:true, ntpSynced:false
GET /api/server/version  → canSwitch:true，五个包 available 全 true
真执行 sudo -n timedatectl set-ntp true（原值即 true，无副作用）→ 成功
sudo -n cat /etc/shadow            → 被拒 ✓
sudo -n timedatectl set-timezone   → 被拒 ✓（只放开了 set-time / set-ntp）
原有的 dmidecode 规则               → 未受影响 ✓
```

### 10.7 任务日志的删除：三道闸门

旧版 `delete_task_log` 是遍历目录 `unlink()` 所有文件（D-205）：
不校验会话、不校验权限、无二次确认；不递归子目录；
也**不判断文件是否正被后台写入** —— 删掉当天的文件，后台服务的文件句柄还在，
会继续往一个已被 unlink 的 inode 里写，日志静默丢失。

新版：

1. **文件名正则** `^log\d{4}-\d{2}-\d{2}\.html$` —— 名字里有 `/` 或 `..` 根本匹配不上
2. **解析后前缀断言** —— `EvalSymlinks` 后确认仍在目录内，防符号链接绕过
3. **跳过当天文件**（BR-252），预览里列出被跳过的文件名并说明原因

只留一道都不够：正则可能哪天被放宽，前缀断言可能被符号链接绕过。

现网复验：`../../../etc/passwd`、`config.php`、`log2026-05-08.html%00.txt`
三种穿越尝试全部回 `40001 任务日志文件名不合法`。

另外 `dirWritable` 用「建一个临时文件再删掉」实探，而不是读 mode 位 ——
mode 位要配合 uid/gid 才能判断，还有 ACL、只读挂载、SELinux 这些读 mode 根本看不出来的情况。

### 10.8 新版自身的缺陷 N-10（本轮发现并已修复）

**N-10 审计中间件取不到用户名，落出一行 `user='-'`**

`withAudit` 包在鉴权中间件**外面**，里面这样传上下文：

```go
next(w, r.WithContext(context.WithValue(r.Context(), userKey, u)))
```

`r.WithContext` 返回的是**一个新的 `*http.Request`**，用户只存在于那个副本里。
外层拿着的还是原始的 `r`，它的上下文里永远没有用户。

现网实测就是这样落出了 id=159 那一行 `user='-' | 启停作息方案`。

与鉴权中间件同一个数据来源，不依赖上下文能不能传出来。

## 11. 备份与恢复（F-58 ~ F-60）的实测结论

> 用户明确的范围：**「备份和恢复只要把数据库和媒体备份恢复就可以。媒体在
> /opt/apps/a9000/backup/mediadata」**。本节据此实现。

### 11.1 ⚠⚠ 最重要的一条：`server?state=1` 会让整台服务器立刻重启

旧 `restore_backup_file.php` 恢复完成后调 `send_socket_restart("server", 1)`。
我按字面把它理解成「通知后台服务重新加载配置」，在恢复流程末尾自动调了一次。

**现网实测的结果是整机重启**，日志前后差 **1 秒**：

```
2026/08/25 16:09:58  notify -> 127.0.0.1:8886 : server?state=1
2026/08/25 16:09:59  systemd[1]: Stopping Create final runtime dir for shutdown pivot root...
2026/08/25 16:10:10  systemd[1]: Reached target Reboot.
2026/08/25 16:10:37  （重新开机）
```

函数名里的 restart 说的是**这台机器**，不是服务进程。

排除了其它可能：`heartbeat` 那一串 `bad node [ha30]` 报错是常态背景噪音
（上一个启动周期内 29923 条），`cron.d` 里没有定时重启项，
`journalctl --list-boots` 显示上一次开机是 07:47、这次是 16:10 —— 与恢复严丝合缝。

**已改**：恢复流程**不再自动发这条报文**。改为在响应里返回
`backendNeedsRestart` + `restartHint`，界面上如实告诉用户
「后台服务内存里仍是恢复前的数据，需要重启才生效，请自行选择时机」。
这是一台随时要打铃的广播服务器，什么时候重启必须由人来按。

函数本身保留，但改名为 `ServerReboot` 并在注释里写明杀伤力 ——
免得下一个人再按名字猜一遍。

复验：第二次恢复（16:18:04）全程 `server?state=1` 报文数为 0，
机器 uptime 从 439 秒连续涨到 473 秒，没有重启。

#### ⚠ 补充：这台机器**还会自己重启**，与本功能无关

16:42:45 又发生了一次重启，而那段时间新版一条 `server?state=1` 都没发过
（日志里这个报文全天只有 16:09:58 那一条）。两次事件在日志里的形态完全不同：

| | 16:10 那次 | 16:42 那次 |
|---|---|---|
| 关机记录 | **完整**：`systemd-reboot.service` → `Reached target Reboot` → `Shutting down` | **没有**，日志在 heartbeat 输出中途戛然而止 |
| 与 `server?state=1` 的间隔 | 1 秒 | 全天没发过这个报文 |
| 停机时长 | 27 秒（16:10:10 → 16:10:37） | **6 分钟**（16:42:45 → 16:48:42） |

有完整关机流程 + 1 秒间隔 ⇒ 16:10 那次是 `server?state=1` 触发的有序重启，
结论不变。而 16:42 那次是**没有关机流程的硬中断**，
更像掉电、硬复位或外部强制断电，与新版无关。

顺带查到的环境情况，运维需要知道：

- `/etc/ha.d/ha.cf` 配的是 `node ha515h` / `node ha526h`，
  但网络上收到的心跳报文 `src=ha30` —— 这个节点名**不在配置里**，
  于是 heartbeat 每 2 秒刷一次 `ERROR: process_status_message: bad node [ha30]`，
  一个启动周期内刷了 **29923 条**。这是长期存在的配置错位。
- `ha.cf` 里 `watchdog` 是注释掉的，系统也没有 `/dev/watchdog`，
  所以不是软件看门狗把机器打掉的。
- cron 里没有定时重启项。

也就是说：**这台广播服务器本身存在会自行重启的问题**，
在做任何恢复/清空这类长事务操作之前都要意识到这一点。

### 11.2 备份包里没有任何 DDL —— 这是与旧版最根本的分歧

旧版备份是逐表拼：

```
DROP TABLE IF EXISTS <t>;          ← DDL
<SHOW CREATE TABLE <t> 的原文>;     ← DDL
INSERT INTO <t> VALUES (…);        ← 数据
```

恢复时把这坨东西按 `;` 拆开逐条执行。于是「恢复一个结构不一致的旧包」
就等于**把线上表结构改成备份那一刻的结构** —— R1 红线上最大的实际风险来源。

新版是**纯数据备份**：包里只有每张表的行数据，一条 DDL 都没有。
恢复 = 在现有表里 `DELETE` + `INSERT`，全程不碰表结构。

这不是保守，而是这套部署下**唯一可行**的做法。新版数据库账号的授权是：

```sql
GRANT SELECT, INSERT, UPDATE, DELETE ON `audioserver`.* TO `htweb`@`%`
```

连 CREATE / DROP 都没有，旧版那种恢复方式在这里根本执行不了。
代价是「结构不同的包恢复不了」—— 而这正是手册 BR-272 要求的行为。

**实测证据**（包内 109 个条目：89 个 `db/*.json` + 19 个 `media/*` + 1 个 `_manifest.json`）：

| 关键字 | 是否出现在包里 |
|---|---|
| `drop table` | ✗ |
| `create table` | ✗ |
| `alter table` | ✗ |
| `insert into` | ✗ |
| `truncate` | 仅作为**列名** `isTruncate` 出现在 `_manifest.json` 的结构描述里，不是语句 |

### 11.3 现网事实支撑这个设计

| 事实 | 意义 |
|---|---|
| 89 张表**全是 InnoDB** | `DELETE + INSERT` 可以整体放进一个事务，真正可回滚 |
| 外键 0、触发器 0、视图 0、存储过程 0 | 不必考虑删除/插入顺序 |
| 全库 1.44 MB、约 390 行 | 一次性导出导入毫无压力（实测备份 3.2s、恢复 1.9~4.8s） |
| 没有任何 BLOB / BINARY 列 | 所有值都能按文本导出 |
| 但**有非 utf8 的列** | `terminal.postion`、`book_msg.*` 是 gbk；`TKdeviceinfo` / `TKstationinfo` / `enabletask` 的一批列是 latin1 |

非 utf8 列的往返是安全的：连接字符集是 utf8，MySQL 在读写两个方向自动转换，
值既然是从这些列里读出来的，写回去就一定表示得了。
实测 `terminal.postion` 恢复后 HEX 与恢复前逐字节一致。

### 11.4 新版自身的缺陷 N-11（本轮发现并已修复）

**N-11 时间类型被 `parseTime=true` 变成 RFC3339，写回时报错**

连接串里带了 `parseTime=true`（media / task 等模块依赖它），
驱动会把 DATE/DATETIME/TIMESTAMP/TIME 列解析成 `time.Time`；
再扫进 `sql.NullString` 时 `database/sql` 用 RFC3339Nano 格式化：

```
2011-06-14T20:11:30+08:00
```

这个字符串写回 MySQL 直接报错，第一次恢复就是这样整体失败的：

```
[500] 恢复备份: 写入表 filefolder: Error 1292 (22007):
      Incorrect datetime value: '2011-06-14T20:11:30+08:00'
      for column `audioserver`.`filefolder`.`createtime` at row 1
```

**但这次失败恰好验证了事务设计是对的**：89 张表里 88 张校验和与恢复前
逐字节一致，媒体一个字节没动，`task` 70024 的 `state=1` 保持原样，
唯一变化的是 `log`（恢复期间写进去的审计行）。回滚是干净的。

修复：导出时对时间类型列用 `CAST(col AS CHAR)`，让 MySQL 给出规范文本，
绕开驱动的时间解析。顺带把 `0000-00-00` 这种零日期也保住了 ——
它进不了 `time.Time`，靠驱动解析这条路本来就走不通。

复验：`filefolder.createtime` 导出为 `2011-06-14 20:11:30`，
`task` 导出为 `2011-01-01` / `2060-01-01` / `04:00:00`，
`disableday` 的 `0000-00-00` 原样保留。

### 11.5 防 Zip Slip 与目录穿越

旧版三处漏洞：

| 编号 | 旧版 | 后果 |
|---|---|---|
| D-231 | mp3 条目用 `fopen(zip_entry_name($h), "w ")` 直接写，路径完全来自包内 | 构造一个包就能往服务器任意位置写文件（`../../../../etc/cron.d/x`），等价于远程代码执行 |
| D-232 | 模式字符串写成 `"w "`（多个空格） | — |
| D-224 / D-237 | 备份包名来自 URL，不过滤路径分隔符 | 目录穿越读写 |

新版：

- 包名白名单正则 `^[A-Za-z0-9._-]{1,120}$` + 必须 `.zip` 结尾 + 解析后前缀断言
- 媒体条目：只认 `media/` 前缀 → 逐段清洗（拒绝绝对路径、拒绝任何 `..` 段、
  最多一层子目录）→ 拼出目标路径后再做一次根目录前缀断言

实测三种穿越尝试全部拒绝：

```
GET /api/backups/../../etc/passwd/restore-precheck  → 40001 备份包名称不合法
DELETE {"name":"../../etc/passwd"}                   → 40001 备份包名称不合法
GET /api/backups/nope.zip/restore-precheck           → 40401 备份包不存在
```

### 11.6 恢复的四道闸门

1. **仅超级管理员**（按 id=1 判定）。旧版这三个入口
   （`backup_restore_form.php` / `restore_backup_file.php` / `del_backup_file.php`）
   **一个权限校验都没有**（D-222 / D-229 / D-238），其中恢复等价于任意 SQL 执行。
2. **结构指纹比对**（BR-272）。指纹取自 `information_schema` 的表名 + 列名/类型/可空/字符集，
   **不用 `SHOW CREATE TABLE`** —— 后者的输出里掺着 `AUTO_INCREMENT` 当前值这类
   会随数据变化的东西，拿它算指纹会「什么都没改，指纹却变了」。
   不一致时逐表逐列给出差异清单（`TABLE_NOT_IN_DB` / `COLUMN_NOT_IN_DB` /
   `TYPE_CHANGED` / `CHARSET_CHANGED` / `COLUMN_NOT_IN_BACKUP` / `TABLE_NOT_IN_BACKUP`），
   而不是只说一句「不兼容」。
3. **确认文本逐字相同**。实测传 `confirmText:"xxx"` → `40001 确认文本与备份包名不一致，已取消`。
4. **自动安全备份**（BR-273）。它失败就不继续 —— 没有退路的恢复不该开始。

### 11.7 媒体：跳过 tmp/，用 rename 绕开属主问题

现网 `/opt/apps/a9000/backup/mediadata`：

| 位置 | 内容 | 处理 |
|---|---|---|
| 顶层 | 18 个 mp3，67MB | 备份 |
| `tts/` | 1 个 TTS 产物，476K | 备份 |
| `tmp/` | 12 个转码中间产物，11MB，全 root 属主 | **跳过**（可再生，备进去只会撑大包，恢复时还因权限写不回去） |

顶层文件里有一批是 **root 属主**，而服务跑在 `tw` 下。直接以 `O_TRUNC` 打开会 EPERM，
所以写法是**先写 `.part` 再 rename** —— 只要目录可写就能成，正好绕开属主问题，
而且中途失败不会留下半个文件顶掉原来的好文件。

> 副作用：恢复后这些文件的属主会统一变成 `tw`、mtime 变成恢复时刻。
> 内容逐字节不变（已用 sha256 逐个核对）。后台 C 服务以 root 运行，读写不受影响。

## 12. 服务器参数与恢复出厂（F-56 / F-57）的实测结论

### 12.1 旧版的写入语句

```php
UPDATE serverbaseparam SET dataport='$_POST[dateport]', ip='$_POST[ip]',
  gateway='$_POST[gateway]', port='$_POST[port]', udpport='$_POST[udpport]',
  maxbandwidth='$_POST[maxbandwidth]', maxhttpconnections='$_POST[maxhttpconnections]',
  offlineport='$_POST[offlineport]', backupmode='$servermodes'
```

八个字段纯 `$_POST` 拼接、零校验，而且 **UPDATE 不带 WHERE**（D-208）——
表只有一行才侥幸没出事。新版参数绑定 + 逐字段校验 + 显式 `WHERE id = 1`。

### 12.2 ⚠ `webport` 这个列名是个陷阱

它**不是 Apache 端口**，是后台 C 服务的 **UDP 通知端口**（现网 8886）——
`notify` 包读的就是它。改了它，新版发通知的目标端口会立刻跟着变，
而后台服务要重启后才在新端口上监听。这一点在界面上写明了。

### 12.2b 「web端口」和「sdk端口」根本不在数据库里（D-213）

这是排查参考图 `docs/image/1.png` 与实际取值对不上时挖出来的。图上三个端口是
**web端口 80 / 离线端口 8901 / sdk端口 99**，而 `serverbaseparam` 里
`webport = 8886`、`rtspport = 8091`、`offlineport = 8901` —— 只有离线端口对得上。

原因：前两个字段旧版压根不从库里取，取自 Apache 配置。现网实测：

| 界面字段 | 真实来源 | 现网值 | 数据库同名列的真实用途 |
|---|---|---|---|
| web端口 | `httpd.conf` 的 `ServerName <ip>:<port>`（第 242 行），旁证 `LISTEN 80` | 80 | `webport` = 后台 C 服务 UDP 通知端口（8886），见 §12.2 |
| sdk端口 | `swagger-ui/dist/swagger1.json` 的 `"host": "<ip>:<port>"`（第 11 行） | 99 | `rtspport` = RTSP 端口（8091） |
| 离线端口 | 数据库列 `offlineport` | 8901 | 主备同步的 rsync 端口，旧版写进 `/etc/rsyncd.conf` 的 `port =` |

三条独立证据链：

1. `do.php` 保存时写的就是这两处 ——
   `sed -i '241c ServerName ...'`、`sed -i '11c "host": ...'`；
   而那条 `UPDATE serverbaseparam`（见 §12.1）里**根本没有 `webport` 和 `rtspport`**。
2. 旧版 swagger 文档对这三项的措辞：
   `offlineport(离线端口) listen(网页端口) sdklistens(sdk端口)` ——
   离线端口是库里的列名，另外两个是 Apache 的「监听」概念。
3. 现网 `httpd.conf` 是 `LISTEN 80` / `LISTEN 81` / `LISTEN 99`，
   `httpd-vhosts.conf` 里 `:80 → oktw`、`:81 → ok112`（旧版后台）、
   `:99 → lumen/public`（对外 API），与 `a9000_apache` 容器发布的 80/81/99/443 完全吻合。
   `8901` 则是 `a9000_rsync` 容器的 `8901 → 873`。

**新版处理**：`serverparam/apache.go` 解析这两个文件，只读、绝不回写
（回写就要重蹈 §12.3 那套按行号 sed 的覆辙）。读不到时回退到数据库同名列，
并在页脚明确写出「这两列另有用途，仅供参考」，不装作取到了。
配置项 `legacy.apache_conf` / `legacy.swagger_file`，默认指向现网路径。

### 12.3 改 Web 端口那套 `sed` 逻辑：整段放弃，不做替代

旧版改 webport 的做法是 `sed -i '241c ...'` **按行号改 Apache 配置**（D-209）：
配置文件行数一变就改错行、写坏 httpd.conf，Web 直接起不来；
而且 sed 命令是字符串拼 `$ip`、`$listenport`，还带命令注入（D-210）。

新版 Web 是独立进程监听自己的端口，跟 Apache 没有关系，
所以**只把值写进数据库，绝不去动任何系统配置文件**。
哪些改动需要重启什么，保存后在 `restartReason` 里逐条列出来，由运维去执行。

同样地，改「服务器 IP」也只改数据库记录，系统网卡配置不碰 —— 界面上明说了。

### 12.4 子网掩码校验：旧版对非连续掩码算得出「看着合理」的错误答案

旧版用 `decbin()` 累加再 `substr_count($shi_mask,"1")` 数 1 的个数（D-212）。
`255.0.255.0` 会被数出 16 个 1，于是当成 /16 —— 但它根本不是合法掩码。

新版用 `net.IPv4Mask(...).Size()`：标准库对**非规范**（1 不连续）的掩码返回 `(0, 0)`，
正好是判据；而 `0.0.0.0` 返回 `(0, 32)` 仍算合法。
实测 `255.0.255.0` → `子网掩码 255.0.255.0 不是合法掩码（必须是连续的 1，例如 255.255.255.0）`。

### 12.5 `sounddetect` 的双写

`sounddetect` 在 `serverbaseparam` 与 `serverconfig` **两张表里冗余存了两份**（D-216 / 契约 C-42）。
旧版是两段散在不同分支的代码，先查 `serverconfig` 有没有行再决定 INSERT 还是 UPDATE。
新版把这段收进 `syncServerConfig`，与主表更新放同一个事务，保证两处永远一致。

### 12.6 恢复出厂：表清单做成「三分类 + 未知表拦截」

手册 D-221 指出旧版把表清单硬编码在代码里，新增表时容易遗漏 ——
遗漏的后果是「以为清空了，其实某张表里还留着上一个项目的数据」。

新版把 89 张表**穷举**成三类，运行前拿实际库里的表清单比对，
**只要出现一张不认识的表就拒绝执行**：

|---|---|---|
| 清空 | 54 | 清单逐字取自旧 `delsqldate()` 的 DELETE 序列 |
| 按条件保留 | 5 | `book_admin.id=1` / `filefolder.id<=9` / `filetaskfree.id=1` / `media.id<=1` / `task.taskid=70000` |

「有意不动」那 30 张里有几个值得留意：`usersn`、`userterminal`、`logincheck`

但把它们列在界面上，让操作者自己判断要不要另行处理。

### 12.7 媒体物理文件（修 D-217）

只删顶层普通文件，不递归。

### 12.8 新版自身的缺陷 N-12（本轮发现并已修复）

**N-12 被拒绝的恢复出厂尝试也写了审计行**

审计确实必须写在执行之前 —— 恢复出厂会把 `log` 表整个清掉，事后写就成了
「清空后的第一行」，追不回是谁按的（BR-265）。但我把它写在了**确认文本校验之前**，
于是一次被拒绝的尝试也留下一行「恢复出厂设置（清空业务数据）」，
读日志的人会以为真清过。

修复：确认文本先在 handler 里挡一道，通过后再写审计，文案也改成「开始恢复出厂设置」。
复验：连续三次错误确认文本，`log` 表 `MAX(id)` 保持 184 不变。

## 13. 离线管理（F-43 ~ F-47）的实测结论

手册开篇说这一域是**旧代码质量最差的部分**，五个「幽灵表/幽灵字段」里占了三个，
多个功能在当前 schema 下**从未成功执行过**。本轮在现网逐条核实，全部属实。

### 13.1 现网证实的三件事

**① `terminaloftask` 确实没有 `offlineparam` 这一列**

现网这张表只有 `id / taskid / terminalid / workstate / groupid / area` 六列。
旧 `set_offline_task` 引用 `terminaloftask.offlineparam` 并带 `or die()` ——
**「离线任务下发」这个功能一次都没成功过**，一点按钮页面直接中断（D-153 / G-03）。

新版改用已经存在的 `offlinetaskofterminal.offlinestate` 表达同一语义，
任务自身的离线状态写 `task.offlinestate`（BR-210）。**绝不新增字段。**

**② `offlinetaskofterminal.area` 的列默认值是 `'''11111111'''`**

建表时把引号也写进了默认值里，带着三层单引号。依赖默认值插入会得到一串脏数据。
新版显式写 `11111111`（BR-209）。实测插入后 `LENGTH(area) = 8`，干净。

**③ `offlinemedia.id` 必须显式等于 `media.id`**

这一列虽然是 `auto_increment`，但旧代码是
`INSERT INTO offlinemedia (id, ...) VALUES ('$row[id]', ...)` 显式写入 ——
后台服务据此把离线副本关联回 `media`。这是一条**未被文档化的强契约**（BR-201）。
同理 `offlinetask.taskid` 显式等于 `task.taskid`（BR-207）。新版原样保持。

### 13.2 「停止离线音乐」也从来没生效过

旧 `stop_offline_music` 的 WHERE 里写的是 `and task='0'` ——
**该列叫 `taskid`，列名写错了**，后面还跟着 `or die()`（D-147 / G-05）。
新版修正为 `taskid = 0`。实测停止 2 条传输，`offlinestate` 正确变成 11。

### 13.3 M×N 查询与九张表的表锁

| 编号 | 旧版 | 后果 |
|---|---|---|
| D-146 | `for(媒体){ for(终端){ 4~5 条 SQL } }` | 10 媒体 × 50 终端 = 2000+ 次查询，页面必然超时 |
| D-151 | `LOCK TABLES ... media WRITE` | 下发期间**全站媒体功能阻塞** |
| D-154 | `do_offline_task` 一次锁 **9 张表** | 期间全站几乎所有功能阻塞 |
| D-156 | 三层嵌套循环（任务 × 终端 × 媒体）逐条 SQL | 同上 |

新版：三条批量查询把现状读进内存，比对后批量 INSERT / UPDATE，一个事务，**无表锁**。

### 13.4 离线副本的 `filename` 必须同步更新

旧版「更新已存在的 offlinemedia」分支**只更新 size/timelength/sample/bitrate，
不更新 filename**（D-149）。媒体被重新上传后物理路径变了，离线副本还指向已删除的旧文件，
终端拉一个不存在的文件 —— 现象是「下发成功但放不出声」，极难排查。

新版同步 `name / size / typeid / priority / filename / folderid / timelength /
channel / sample / bitrate / codecid` 全部字段（BR-204）。
实测三条副本的 `filename` 与 `media.filename` 逐一相等。

### 13.5 12 态状态机：Web 只写「下发意图」

Web 允许写的只有 5 个：1（空闲离线）、2（立即离线）、4（空闲删除）、5（立即删除）、
11（停止传输）。进行中与完成态（3/6/7/8/9/10/12）归后台服务写（BR-203）。

接口层的 `ParseMode` 只接受这 5 个对应的 mode 名，其余一律拒绝 ——
实测传 `mode=done`（想伪造「离线完成」）被挡下。

状态字典由 `GET /api/offline/states` 下发，前后端共用同一份（BR-215）——
旧版把它写成模板里一长串 if/elseif（D-160）。

### 13.6 通知：旧版漏发「空闲离线」

旧版通知条件写成 `if($flag==5 || $flag==2)`，`flag=1`（空闲离线）**不通知**（D-152），
后台就不知道有新的空闲传输任务排进来了。新版所有状态变更都发 `task?state=15&id=0`。

### 13.7 清空全部离线数据

旧版 `stop_offline_music` 的 `flag==14` 分支执行 **4 条无 WHERE 的 DELETE**，
仅靠前端一个 confirm 保护，服务端没有任何确认或权限校验（D-148 / BR-206）。

新版：独立接口 + 逐字确认文本「清空全部离线数据」+ **超级管理员**权限 +
写审计日志 + 一个事务。另外多做一步：把 `task.offlinestate` 一并复位为 0 ——
旧版删完四张表却把 task 上的离线标记留着，任务永远显示「离线中」。

## 14. 终端分区 / 节假日 / 遥控任务 / 时间设置的实测结论

参考图 `docs/image/1.png` 里这四项对应旧版的
StreamManager、holidaymanager、keytask_mapping、set_server_time。

### 14.1 终端分区：真正在用的是 `serverplaystream`，不是 `terminalgroup`

库里有一张 `terminalgroup`（groupid / streamid / groupname / info），字段名看着更像
「终端分区」，但旧版全站只在恢复出厂时 `DELETE FROM terminalgroup` 提到过它，**从不读写**。
真正在用的是：

```
serverplaystream (streamid, name, info, createtime, userid)   ← 分区定义
terminalofgroup  (id, terminalid, groupid=streamid)           ← 成员
```

### 14.2 一台终端属于哪个分区，库里记了四份（D-215）

| 位置 | 谁在读 | 旧版有没有维护 |
|---|---|---|
| `terminal.groupid` | 终端编辑页 | ❌ **分区页从头到尾没写过** |
| `terminalofgroup.groupid` | 终端列表、分区页 | ✅ |
| `terminaloftask.groupid` | 后台 C 服务下发 | ⚠ 只在 `= 0` 时填 |
| `terminalofalarmgroup.groupid` | 后台 C 服务 | ✅ |

第一行是旧版的漏洞：终端列表读 `terminalofgroup`、终端编辑页写 `terminal.groupid`、
分区页两者只写后者，三方各说各话。新版四处一起维护。

### 14.3 ⚠ `terminaloftask.groupid` 的 `= 0` 限定必须去掉（本轮实测发现）

旧版 `streamadd_msg` 里这一段是：

```php
$results = mysqli_query($con,"SELECT groupid FROM terminaloftask
                              WHERE terminalid='$terminalid' and groupid='0'");
if(...) { UPDATE terminaloftask SET groupid='$getnewstreamid' WHERE terminalid='$terminalid'; }
```

终端第一次进分区 A 时值被写成 A，**之后再挪到分区 B，这段因为 `groupid` 已经不是 0
而整个跳过 —— 任务行永远停在 A**。后台按 A 下发，而终端实际在 B，播出来的范围就是错的。

我一开始照搬了这个限定，现网立刻复现：把终端 4 从 A 挪到 B 之后，
A 的成员数是 1，任务引用数却还是 23 —— 那 23 条全是终端 4 的残留。

**修法与依据**：这一列没有独立语义。全部写入方
（`task/edit.go`、`task/copy.go`、`bell/edit.go`）填进去的都是「该终端当时所属的分区」，
界面上从来没有「给这条任务单独指定一个分区」这个操作。
既然它只是终端分区的快照，分区一变就该整体跟着走 —— 改成无条件覆盖。
终端编辑页改分区时同样补上了这一段（原先它只写 `terminal.groupid` 与 `terminalofgroup`）。

实测四个方向都对：A→B 十七条任务行跟着从 2 变 3；B→A 反向；移出分区复位成 0；
删除分区 `resetTasks:10`，收尾时 `terminaloftask` 全部回到 `groupid = 0`。

### 14.4 旧版那个一调必炸的编辑接口（D-216）

`streamedit_msg` 更新的是 `feed` / `feedfile` / `outputformat` / `inputformat` /
`AudioCodec` / `MaxTime` / `AudioBitRate` / `AudioChannels` / `AudioSampleRate` /
`AudioQuality` —— 这些列在 `serverplaystream` 里**一个都不存在**，一调必然
`Unknown column`。真正在用的是 `streambatedit_msg`。新版只实现后者的语义。

### 14.5 ⚠ 节假日的 `projectstate` 与 `task` 表**正好相反**

```
holidaytime.projectstate : 1 = 启用, 0 = 停用
task.projectstate        : 0 = 启用, 1 = 停用   （见 §7.2 的更正）
```

依据是旧版 `do.php` 里那对函数名，没有歧义：

```php
function enableholiday()  → UPDATE holidaytime SET projectstate = '1'
function disableholiday() → UPDATE holidaytime SET projectstate = '0'
```

列默认值 `DEFAULT 1` 也和「新建即启用」吻合。红线禁止改表，这个不一致只能靠常量名
（`holiday.StateEnabled = 1`）和注释挡住。现网实测：新建后落库 `projectstate = 1`，
调停用后变 0，按 `state=0` 筛只出停用那条。

### 14.6 节假日不校验起止日期顺序（D-214）

旧版 `INSERT INTO holidaytime(name,startdate,enddate) VALUES(...)` 纯 `$_POST` 拼接，
结束日填在开始日之前照存。后台按空区间处理 —— **这条节假日静默失效，放假那天照样打铃**。
新版拒绝倒挂的区间，并对重叠区间给出提示（不阻断：同一段假期拆成两条录入是合理的）。

顺带补的：名称非空、`varchar(32)` 按字节校验、日期格式必须 `YYYY-MM-DD`。
列表直接算出区间天数并标出「今天生效」，不用自己拿日历对。

### 14.7 ⚠ 遥控任务：`mediaid` 列里装的是 `taskid`，而旧版拿它去 join `media`（D-217）

`shortcutkeytask (id, keyid, mediaid, keyname)`。写入端 `keyset_task_mapping_msg`
的取值是：

```sql
SELECT taskid, taskname FROM task WHERE tasktype IN (2,15) AND info=''    -- 文件广播
SELECT taskid, taskname FROM task WHERE tasktype = 3                       -- 采播
SELECT taskid, taskname FROM task WHERE tasktype = 5 AND sec_task_id = 0 AND prepower = 0  -- 终端功放
```

拿到的是 **taskid**，POST 变量也叫 `task_map_id`，却塞进了名为 `mediaid` 的列。

要命的是读取端 `keytask_mapping.php`：

```sql
SELECT media.name, media.typeid FROM shortcutkeytask, media
 WHERE shortcutkeytask.mediaid = media.id AND shortcutkeytask.keyid = '$keyid'
```

**拿 taskid 去 join `media.id`。** 现网 `task.taskid` 从 70001 起、`media.id` 是小整数，
join 不上就整行消失 —— 也就是说旧版这个页面配好之后，明细列**永远是空白的**。

新版：写入沿用旧语义（存 taskid，列名不能改），读取改成 join `task`。
实测 5 键绑「下课 + 跑操」后，明细正确显示两条任务名与类型。

同时补了旧版一条都没有的校验：键号 1~999、任务必须存在、任务类型必须落在可绑的三类里
（实测传作息条目 70016 被拒）、一个键最多 20 条、名称按字节校验。
键号唯一性旧版查了但没有锁，两人同时提交同一键号会双双写进去
（表主键是 `(id,keyid,mediaid,keyname)` 四列复合，拦不住）——
新版用命名锁 `htweb_remote_keyid` 串行化「查重 + 写入」。

### 14.8 ⚠ `serverbaseparam.adjusttime` 不是开关，是终端 ID（新版缺陷 N-13，已修）

旧版 `setgpsterminal.php`：

```php
$sqls = "update serverbaseparam set adjusttime='$gpsselects'";   // $gpsselects = 选中终端的 id
```

0 表示不启用 GPS 校时。列名看着像布尔，我在服务器参数页把它当 0/1 开关渲染并校验
「只能是 0 或 1」（N-13）：真选一台 id=7 的终端会被判非法，而写进 1 又会指向另一台
毫不相干的设备。

**修法**：从服务器参数页的 `UPDATE` 语句里**整列摘除**，由「时间设置」页专门维护。
这样服务器参数页无论怎么保存都不可能碰坏它。
实测 `adjusttime = 3` 之后再保存一次服务器参数，值仍是 3。

### 14.9 ⚠ 「取消 GPS 校时」会重启整台机器（D-219）

`setgpsterminal.php?gpsselects=-1` 分支：

```php
$msg = "server?state=1"; $socket->send_data(...);
$command="cmdhost -c 'sudo reboot'"; system($command);
@system("sudo reboot");
```

一个「取消 GPS 校时」的链接，顺手把整栋楼的广播主机重启，没有任何确认。
新版**不提供**这条路径：取消就是把 `adjusttime` 写回 0。

### 14.10 「修改服务器系统时间」整段不做（D-218）

旧版 `set_server_time.html` 的核心是：

```php
@exec("date $date_value", ...);
@exec("time $time_value", ...);
@exec("setrtc $year $month $day $hour $minute $second", ...);
```

三个问题叠在一起：

1. `date MM/DD/YY` + `time HH:MM:SS` 是 DOS/Windows 语法，Linux 上 `date` 不接受这种参数，
   `time` 更是 shell 内建的计时关键字 —— **这段代码在现在的部署形态下从来没生效过**。
2. 它跑在 PHP 容器里。容器与宿主共享内核时钟，没有 `CAP_SYS_TIME` 改不动；
   真改成功了改的也是整台宿主机。
3. 参数是 `$_POST` 直接拼进 `exec`，命令注入。

更根本的是：这台机器正跑着按时刻表打铃的广播服务。把系统时间往前拨会让一批任务
瞬间集体触发，往后拨会让今天剩下的铃全部哑掉。这种事不该藏在一个网页表单后面。

新版只**显示**服务器当前时间、时区、主机运行时长，并额外显示数据库时间与两者的秒差 ——
后者是判断「Web 与数据库是不是同一台机器/同一时区」最直接的线索。
真要校准用 NTP，或由运维在主机上操作。

`sync_time`（`terminal?state=30&id=N`，给终端下发校时）是这一页里唯一真正在工作的功能，
新版保留。

### 15.1 tasktype 的完整取值：只能从各页面写死的 SQL 反推

`task.tasktype` 的列注释只写到 5（「1-作息 2-文件 3-采播 4-电话 5-功放」），
9/13/15/17/19/20/23/24/25/27/30 全都没有注释。现网实测到的分布与出处：

`keyset_task_mapping.php`（遥控候选）把它和 2 一起当文件广播。两边都不是笔误 ——
15 的任务**是**一条播放文件的任务，只是那个文件由 TTS 合成。新版照搬这个重叠，
强行二选一会让其中一个页面丢数据。

而删掉它其实是在改另一条任务的配置。

### 15.2 ⚠ 「列名叫 mediaid，存的却不是 mediaid」在这套库里出现了三次

| 表.列 | 列名暗示 | 实际存的 | 旧版怎么用 |
|---|---|---|---|
| `shortcutkeytask.mediaid` | 媒体 id | **taskid** | 写对读错（D-217，见 §14.7） |
| `ttssentence.sentenceid` | 语句 id | **media.id** | 读写一致 |
| `mediaoftask.mediaid`（LED 任务） | 媒体 id | **ledsentence.id** | 读写一致 |

后两处旧版自己是自洽的，只是名字骗人。新版全部保留原语义（红线禁止改表），
在三个包的注释里各钉了一根路标。**这套库里「mediaid」这个名字基本不能按字面理解。**

### 15.3 文字语音：一条任务串了四张表

```
task(tasktype=15)
  └ mediaoftask(taskid, mediaid)
      └ media(id, typeid='tts', filename='tts')   ← 合成的虚拟媒体，磁盘上没有文件
          └ ttssentence(sentenceid = media.id, mediaseq, content, speed, volume, male, pitch)
```

后台 TTS 服务（`a9000_tts` 容器）读 `ttssentence` 去合成语音。
新建任务时新版按这条链依次写四张表；修改时「全清再写」并连带删掉旧的 `typeid='tts'` 媒体行 ——
不删就会在文件管理里留下一条永远找不到文件的孤儿记录。
实测：建两段 → 改成一段，`ttssentence` 从 2 行变 1 行，媒体行 71 被 72 取代，
`SELECT ... WHERE typeid='tts' AND id NOT IN (SELECT mediaid FROM mediaoftask)` = 0 条孤儿。

**注意**：`media.typeid='tts'` 的行磁盘上没有实际文件，媒体模块的「物理文件缺失」检查要放过它们。

### 15.4 为什么启停不复用 task 包

`task.Control` 要求「启动前必须有媒体」（BR-176）。那是文件广播的正确规则，
但**终端功放任务本来就没有媒体** —— 它是一条「几点几分把某个通道的电源打开」的指令
（`cmd` 0=打开/1=关闭，`cmdargs`=通道号）；采播任务的音源也不在 `mediaoftask` 里
（`cmd` 存的是采播源终端 id）。套用那条规则会让这两类永远启动不了。

新版 `typedtask` 另写一套判定，「这一类启动前需要什么」写在 spec 表里：

| 类别 | 要媒体 | 要终端 |
|---|---|---|
| 终端功放 | ✗ | ✓ |
| 采播 | ✗ | ✓ |
| 文字语音 | ✓ | ✓ |
| LED 播放 | ✗ | ✓ |

实测：功放任务无媒体也能启动；停用方案后再启动被拒；
拿 `tts` 的路由去操作功放任务被拒（`BAD_TYPE 任务类型 5 不属于文字语音`）。

### 15.5 ⚠ `enabletask` 的三列类型都不像它们的用途

```
id       int(4) unsigned zerofill   → 查出来是 "0001"
enstate  varchar(1024) DEFAULT '0'  → 只存 "0"/"1"，给了 1024 字节
taskid   varchar(2048)              → 逗号分隔的**任务 id 列表**
```

表上只有 `UNIQUE KEY (id)`，**没有 PRIMARY KEY**。

`taskid` 一列多值是典型反范式。新版读时拆开并按 id 去 `task` 补名字（悬空 id 标成
「任务已删除」——旧版删任务时不清 `enabletask`），写时拼回去，
并且**在保存前按字节数挡住超长**：`varchar(2048)` 截断很可能落在某个 id 中间，
后台就会解析出一个**别的**任务，这比报错危险得多。

**⚠ `enstate`：1 = 启用、0 = 停用。** 与 `task.projectstate`（0=启用）相反，
与 `holidaytime.projectstate`（1=启用）一致。**三张表两种约定，只能逐表记住。**

`flag` 列旧版恒写 0、全站没有任何地方读它或改它。新版跟着写 0，不猜语义、不暴露给界面。

### 15.6 声场分区：终端归属又是记两份（D-220）

`soundgroup` 关联表 + `terminal.soundsgroupid` 单值列。
旧版**删除**分区时两处都清，但**新建和修改时只写 soundgroup、从来不写
`terminal.soundsgroupid`** —— 建完分区，终端自己那一列还是 0，后台按它取值就找不到分区。
这已经是同一个毛病第三次出现（报警分区 D-138/D-139、终端分区 D-215、声场分区 D-220）。

新版两处同时维护，实测：建分区后终端 3、4 的 `soundsgroupid` 都是 1；
把终端 4 移出后它复位成 0；删分区后两台都回到 0。

`sounddevice.dbvalue` 是探头采回来的实测值，由后台回写。旧版新增时写死 0、修改时不碰它 ——
这一点旧版是对的，新版照做：界面上只展示，不提供编辑。
`devaddr` 是 `tinyint(3) unsigned`，旧版不校验，填 300 会被静默截成 255 指向另一台设备；新版挡住。

### 15.7 云广播终端 / 任务传送：判据与放开的两处限制

**「云广播终端」是哪些终端**：判据只有一个 —— `terminal.totalcapacity != 0`
（旧版 `offlinemusicmanager.php` 写死的）。没有存储容量的设备存不下东西。
顺带澄清：`terminaltype.id = 23` 那个叫「离线终端」的型号现网一台都没有，
旧版也从不按它筛选，**别拿它当判据**。

**⚠ `resetcapacity` 大概率是 `restcapacity`（剩余）的拼写错误**，但现网所有终端
`totalcapacity` 与 `resetcapacity` 都是 0，无从佐证。所以新版**原样列出两个数字、
不做减法、不算百分比** —— 算错了会让运维以为终端满了或空着。
（现网因此这一页是空列表：没有任何终端 `totalcapacity != 0`。）

**任务传送放开了旧版两处限制**：
- 旧版 `displayofflinetask.php` 必须先选一台终端才能看。新版不选就列全部副本。
- 旧版限定 `tasktype IN (1,2)`。那会让功放/语音/LED 的离线副本凭空消失 ——
  `offlinetask` 的列结构和 `task` 完全一样，它们确实能被下发。新版不限类型。

这两页都是只读视图，下发动作仍然走已有的 `/api/offline/*`，不重复开写接口。

### 16.2 ⚠ N-14：TTS 的 `media.sample` 里存的是 **taskid**，新版漏写

旧版语句（do.php 9960 / 10740 / 1788 三处一模一样）：

```php
INSERT INTO media(name, typeid, filename, folderid, timelength, channel, sample, bitrate)
VALUES ('$taskname','tts','tts','0','0','0','$gettaskid','$tasktype')
```

第 7 个值 `$gettaskid` 落在 `sample` 上、第 8 个 `$tasktype` 落在 `bitrate` 上。
现网 6 条 TTS 媒体行**无一例外**印证：

| media.id | sample | 实际挂的 taskid | bitrate | 该任务 tasktype |
|---|---|---|---|---|
| 59 | 70009 | 70009 | 30 | 30 |
| 61 | 70014 | 70014 | 128000 | 19 |
| 63 | 70020 | 70020 | 30 | 30 |
| 67 | 70024 | 70024 | 30 | 30 |
| 68 | 70035 | 70035 | 30 | 30 |
| 69 | 70033 | 70033 | 0 | 15 |

`sample == taskid` 是 6/6。新版早前写 0，**新建的语音任务会丢掉这条回指链路**，
后台 TTS 服务若靠它反查任务就找不到。已改为写 taskid，实测新建任务 70069 → `sample=70069` ✅。

`bitrate` 保持 0：由本页产生的那一行（media 69 / task 70033）就是 0，
另外两行的 128000 与 30 来自别的代码路径，不作为本页依据。

这是这套库里**第四处**「列名不能按字面理解」：

| 表.列 | 列名暗示 | 实际存的 |
|---|---|---|
| `shortcutkeytask.mediaid` | 媒体 id | taskid |
| `ttssentence.sentenceid` | 语句 id | media.id |
| `mediaoftask.mediaid`（LED 任务） | 媒体 id | ledsentence.id |
| `media.sample`（TTS 行） | 采样率 | **taskid** |

### 16.3 ⚠ N-15：`endtime` 不该等于 `playtime`

新版 typedtask 早前无条件按 `playtime + durationSec` 算 endtime。
但四个页面里只有终端功放有「持续时长」输入，其余三类 `durationSec=0`，
于是一条 11:00 的语音任务拿到 `endtime=11:00:00` —— 后台若拿 endtime 判断何时收尾，
这条任务等于「一开始就该结束」。

现网所有可对照的行都是 `00:00:00`：tasktype 15 / 19 / 30 / 20 全部。
已改为 `durationSec <= 0` 时写 `00:00:00`。实测：
语音任务 endtime=00:00:00 ✅；功放填 3600 秒仍算出 09:30→10:30 ✅；功放不填时长回到 00:00:00 ✅。

### 16.4 ⚠ N-17：`interval_s / intplaylength / intplaylengthtype` 必须显式写 0

这三列的列默认值是 `0 / 1 / 2`。旧版那条共用 INSERT 把
`$intervallength / $allintervallen / $intervaltype` 一路带下来，
这四个页面不 POST 它们 → PHP 空串 → MySQL 归成 **0 / 0 / 0**。
新版不写就会拿到 0/1/2，与旧版产出的行不一样。

判据是现网数据：这几类任务已有的行里 `intplaylength` **无一例外是 0**
（tasktype 15 / 19 / 30 全是 0），也就是后台服务一直以来见到的就是 0。
已改为显式写 0/0/0，实测新建任务落库 `0 | 0 | 0` ✅。

### 16.5 ⚠ N-16：服务器名称在旧版是可改的，新版当成了只读

旧版 `setmaster_backup`：

```php
UPDATE `serverbaseparam` SET `name`='$servername', `model`='$servermodel',
  `subnetmask`='$subnetmaskip', `masterip`='$master_ip', `slaveip`='$Slave_IP', `slavename`='$slavename'
```

`name` 和主备参数是同一条 UPDATE，在**主备服务器配置**页里保存。
新版早前把它归进 `ReadOnly`（注释写着「由后台服务与注册模块维护」）—— 判断错了，等于砍掉一个功能。

已把 `name` 移进 `HA` 分组、加进 UPDATE 语句、在主备配置页加上输入框并做非空与 255 字节校验。
实测：改成「审计测试主机」落库成功，空名被拒，改回 `ha515h` ✅。

### 16.6 记下但不改的三件事

**① `task.createtime` 带 `ON UPDATE CURRENT_TIMESTAMP`**

全库四个 timestamp 列里只有它带。也就是说这一列名叫「创建时间」，
**实际语义是「最后修改时间」**——任何 UPDATE 都会把它刷新。
新版没有被它坑到：后端只在 `alarmarea` / `filefolder` / `serverplaystream` 上读 createtime，
那三张都不带 ON UPDATE；`task.createtime` 从不 SELECT，复制任务时也显式排除（copy.go）。
将来若要在任务列表上加「创建时间」列，得知道它其实是修改时间。

**② `leddevice` 旧版全站没有 INSERT**

`do.php` 与所有页面里只有 `UPDATE leddevice SET name=..., subterminalid=...` 和
`UPDATE leddevice SET defaulttext=...`。也就是说旧版的 LED 屏是**后台自动发现**登记的
（LED 搜索页），Web 只负责改名和设默认文字。

新版的「新建 LED 设备」是**新增能力**，不是旧版行为。手工建出来的行后台不一定认识 ——
正常流程仍应是先让设备被发现、再改名。这一点已在 LED 设备对话框里说明。

**③ `enabletask` 的 `flag` 列**

旧版 UPDATE 里带 `flag='0'`，新版 UPDATE 不写它。结果相同（新增时写 0、之后无人改动），
不构成差异。新版刻意不写：全站没有任何地方读它，写一个猜出来的语义比不写更糟。
