# 0. 【最高优先级】幽灵表 / 幽灵字段清单

旧代码中存在若干 SQL，引用了 **`audioserver.sql` 中根本不存在的表或字段**。
这些语句在当前库上**必然执行失败**（多数带 `or die()`，会直接中断页面）。

> ⚠️ **修复红线：绝对不允许通过 `CREATE TABLE` / `ADD COLUMN` 来"补上"这些对象。**
> 正确做法是：**功能不实现**，或**用现有字段重新实现等价语义**。

| # | 幽灵对象 | 引用位置 | 现状 | 新版处置（零 DDL） |
|---|---|---|---|---|
| **G-01** | 表 **`medialist`** | `do.php` L3353（`filedel_msg`）<br>L8283（`medialistadd_msg` — **活跃**）<br>L8312（`madlistdel_msg` — **活跃**） | 表不存在。`medialistadd_msg` / `madlistdel_msg` 是**已挂到 `do.php` 分发表上的活跃动作**，一旦被调用即报错 | **功能不实现**。媒体与任务的关联一律走已存在的 **`mediaoftask`**（`mediaid`/`taskid`/`sort`）。`filedel_msg` 源码自注"未被使用"，新版同样不实现 |
| **G-02** | 表 **`mediaofterminal`** | `do.php` L14253（**未注释，活跃**）<br>另有 L11996/L12328/L12526/L20138/L22451/L22583/L22715/L22850/L25712 已注释 | 表不存在。L14253 的 `INSERT INTO mediaofterminal (mediaid,terminalid,taskid)` 会直接失败 | **功能不实现**。"媒体下发到终端"的语义已由 **`offlinemediaofterminal`**（`mediaid`/`terminalid`/`offlinestate`/`taskid`/`sort`）承载，新版统一走该表 |
| **G-03** | 字段 **`terminaloftask.offlineparam`** | `do.php` L8425、L8427（`set_offline_task`） | `terminaloftask` 只有 `id`/`taskid`/`terminalid`/`workstate`/`groupid`/`area`，**无 `offlineparam`**。`set_offline_task` 整个动作**从未成功执行过** | 该动作的意图是"标记任务是否参与离线传输"。新版用已存在的 **`offlinetaskofterminal.offlinestate`** 表达（取值见手册 §5.8 的 12 态表），**不新增字段** |

### 【交互点】

| 4 | — | 列表页仅 `is_admin()` 才可写，但 `usergroupdel_msg` 之外的动作**服务端未复检** | 服务端每个写接口强制校验 |

## 1.2 功能 F-15：新建用户组

### 【功能描述】

创建用户组，设定名称、描述、级别与 13 项功能权限。

### 【交互点】

| 字段 | 控件 | 校验 |
|---|---|---|
| 组名称 * | 文本框 | 非空；**只允许中文/字母/数字** |
| 描述 | 文本框 | `maxlength=30`，默认值 `NO Description` |
| 级别 | 下拉 | **选项范围 10 ~ 109**（JS 循环生成） |
| 权限 | 13 个复选框 | 勾选 → 值 `1`；不勾 → 不提交 → 服务端默认 `0` |
| 按钮 | 提交 / 重置 | — |

### 【原有实现问题 & 新版优化方案】

| # | 编号 | 原有问题 | 新版优化方案 |
|---|---|---|---|
| 1 | D-41 | **`level` 的语义与字段注释矛盾**：`usergroup.level` 注释写"用户组级别 最大值5"，但 UI 下拉是 **10~109**，且任务优先级换算逻辑是 `floor(level/10)` 与 `level%10` —— 实际语义是**两位复合值：十位=组级别，个位=组内任务优先级基数** | **保留 10~109 的取值域与复合语义**（这是运行时事实，后台 C 服务按此解析）。在新版 UI 上**拆成两个控件**：「组级别 1~9」+「优先级基数 0~9」，提交时合成 `level = 级别*10 + 基数`。**字段与取值格式完全不变**，只改录入方式 |
| 2 | — | 组名重名校验后紧跟 `INSERT`，中间无保护 | `GET_LOCK('usergroup_create')` 应用级锁；**不建唯一索引** |
| 3 | — | 用 `LOCK TABLE usergroup WRITE` | 改用事务 |
| 4 | — | SQL 中硬编码库名前缀 `INSERT INTO audioserver.usergroup` | 库名由连接配置决定 |
| 5 | — | 名称正则只允许中文/字母/数字，空格与连字符被拒 | 放宽为"非空 + 长度 ≤42 字符 + 禁止控制字符"（列为 `varchar(128)`，utf8 中文 3 字节） |
| 6 | — | 描述 `maxlength=30` 但列是 `varchar(128)`，限制过严 | 放宽到 42 字符（列容量内） |

### 【数据库】

| 项 | 内容 |
|---|---|
| **表** | `usergroup` |
| **读（重名校验）** | `SELECT 1 FROM usergroup WHERE name = ? LIMIT 1` |
| **写** | `INSERT INTO usergroup (name, info, taskpriv, terminalpriv, mediapriv, userpriv, serverpriv, folderpriv, terminalgrouppriv, alarmgrouppriv, bellpriv, admpriv, telephonepriv, powerplay, level, ttspriv) VALUES (?,?,?,?,?,?,?,?,?,?,?,?,?,?,?,?)` |

| **不写字段** | `id`（自增）、`welcome`（保持 NULL） |
| **DDL 变更** | **无** |

**`POST /api/usergroups`**　权限：管理员；非备机

```json
{ "name": "教学楼管理员", "info": "负责教学楼广播",

```

| 字段 | 约束 |
|---|---|
| `name` | 非空，≤42 字符，全局唯一 |
| `info` | ≤42 字符 |

## 1.3 功能 F-16：修改用户组

### 【功能描述】

修改组名、描述、级别与 13 项权限。修改级别时**联动重算该组下所有用户的任务优先级**。

### 【原有实现问题 & 新版优化方案】

| # | 编号 | 原有问题 | 新版优化方案 |
|---|---|---|---|
| 1 | D-42 | **系统组保护逻辑只做了一半**：若 `group_id == 1`，仅校验"13 项权限是否全为 1"，**名称、描述、level 仍可被随意修改** | 系统组（id=1）**名称、level、权限全部只读**，仅允许改描述 |
| 2 | D-43 | **优先级重算只处理了首个用户**：`if($row = mysqli_fetch_array($result))` 用 `if` 而非 `while`，而该查询会返回该组下**每一个用户**一行 → **只有第一个用户的任务优先级被重算**，其余用户的任务优先级与新 level 不一致 | 改为 `while` 遍历全部用户；重算在**单事务**内批量完成 |
| 3 | D-44 | 优先级重算条件 `floor($get_priority/10) == floor($get_level/10)` 使用的 `$get_level` 是**旧 level**，而 `$newlevel = $level + $get_priority % 10` 用的是**新 level** —— 逻辑上是"只重算那些优先级十位与旧组级别一致的任务"，但循环内 `$get_level` 会被后续行覆盖，**多用户时判断基准漂移** | 显式区分 `oldLevel` / `newLevel` 两个变量；条件与赋值都用明确来源；逐用户独立计算 |
| 4 | — | 重算 `UPDATE task SET priority=? WHERE priority=? AND task_user_id=?` 在循环内逐条执行 | 单条 `UPDATE ... WHERE task_user_id IN (...)` + `CASE`，或批量参数化 |
| 5 | — | 无 `LOCK`/事务包裹整个"改组 + 重算优先级"过程 | 全程单事务 |

### 【数据库】

| 步 | 操作 | 表·字段 |
|---|---|---|
| 1 | 重名校验 | `SELECT 1 FROM usergroup WHERE id <> ? AND name = ? LIMIT 1` |
| 2 | 取旧 level | `SELECT level FROM usergroup WHERE id = ? LIMIT 1` |
| 3 | 取该组全部用户 | `SELECT id FROM book_admin WHERE usergroupid = ?` |
| 4 | 逐用户取任务优先级 | `SELECT taskid, priority FROM task WHERE task_user_id = ?` |
| 5 | 重算并回写 | `UPDATE task SET priority = ? WHERE taskid = ?`（`newPriority = newLevel + oldPriority % 10`，仅当 `floor(oldPriority/10) == floor(oldLevel/10)`） |
| 6 | 更新组 | `UPDATE usergroup SET name=?, info=?, taskpriv=?, terminalpriv=?, mediapriv=?, userpriv=?, serverpriv=?, folderpriv=?, terminalgrouppriv=?, alarmgrouppriv=?, bellpriv=?, admpriv=?, telephonepriv=?, powerplay=?, level=?, ttspriv=? WHERE id = ?` |

**DDL 变更：无。** 优先级重算只依赖已有的 `usergroup.level`、`task.priority`、`task.task_user_id`。

### 【接口设计（新版）】

**`PUT /api/usergroups/{id}`**　权限：管理员；非备机
请求体同 §1.2；响应额外返回重算结果：

```json
{ "code":0, "data": { "id":5, "level":45,
  "priorityRecalc": { "affectedUsers": 3, "affectedTasks": 17 } } }
```

**错误**：`40001` `40002` `40301` `40302` `40303`（系统组受保护字段）

### 【业务规则】

| # | 规则 |
|---|---|
| BR-96 | **系统组（id=1）的名称、级别、13 项权限不可修改**，仅描述可改 |
| BR-97 | 修改组级别时，**必须重算该组下所有用户的所有任务的 `task.priority`**：新优先级 = 新 level + (旧优先级 % 10)，仅对"旧优先级十位 == 旧 level 十位"的任务生效 |
| BR-98 | 重算与改组必须在同一事务内 |

## 1.4 功能 F-17：删除用户组（★超高危级联）

### 【功能描述】

删除用户组，**同时删除该组下的全部用户，以及这些用户拥有的全部数据**。

### 【级联删除范围（旧系统实际行为）】

删除一个用户组会连带删除：

```
usergroup
 └─ book_admin（该组全部用户）
     ├─ userterminal          用户-终端绑定
     ├─ usersn                用户序列号
     ├─ filefolder            用户创建的文件夹
     │   └─ media             这些文件夹里的全部媒体
     ├─ filetaskfree          用户的任务分组
     ├─ serverplaystream      用户的终端分区
     │   └─ terminalofgroup   分区内终端归属
     ├─ alarmarea             用户的报警分区
     │   ├─ terminalofalarmgroup
     │   └─ alarmgroupmap
     └─ task（task_user_id）  用户创建的任务
         ├─ terminaloftask
         ├─ mediaoftask
         ├─ ttssentence（该任务媒体对应的 TTS 语句）
         ├─ media（typeid='tts' 的任务专属 TTS 媒体）
         ├─ terminalkeymap / terminalkey
         └─ 次任务（sec_task_id != 0）同样级联
```

### 【原有实现问题 & 新版优化方案】

| # | 编号 | 原有问题 | 新版优化方案 |
|---|---|---|---|
| 1 | **D-45** | **只清理了组内第一个用户的数据**：`if($row = mysqli_fetch_array($result))` 用 `if` 而非 `while` 取用户 ID，导致 `$get_userid` 只是**第一个用户**。随后所有 `... IN($get_userid)` 的清理（文件夹、媒体、分区、报警区、任务）**只对这一个用户生效**。但紧接着 `DELETE FROM book_admin WHERE usergroupid = '$group_id'` **把该组所有用户都删了** → **第 2 个及以后用户的文件夹、媒体、任务、分区、报警区全部变成孤儿数据，永久残留** | 改为 `while` 取出**该组全部用户 ID**，对完整用户集合执行级联清理；ID 集合分批参数绑定 |
| 2 | D-46 | 次任务清理循环里用的是**外层残留变量 `$getrow`** 而非当前 `$getrows`（L6350-6351），导致次任务的 TTS 语句与 TTS 媒体清理**指向错误的任务** | 修正为当前循环变量 |
| 3 | D-47 | `LOCK TABLES` 与 `START TRANSACTION` 混用（同 D-26），**ROLLBACK 失效**；且 `UNLOCK TABLES` 在 COMMIT 判断**之前**执行 | 移除表锁，全程单事务，提交后再释放资源 |
| 4 | D-48 | **删除媒体记录但不删物理文件** → 磁盘垃圾无限累积 | 事务内收集待删 `media.filename` 清单，COMMIT 后统一 `unlink()`（跳过 `id=1`） |
| 5 | D-49 | **不发送后台通知** → 后台仍持有已删除的媒体与任务缓存 | 删除完成后发 `file?state=0&id=<各 folderid>` 与 `task?state=6&id=<各 taskid>` |
| 6 | D-50 | 没有任何"影响面预览"，管理员点一下就连锁删掉几百条数据 | 提供 **delete-preview 接口**，明确列出将被删除的用户数、文件夹数、媒体数、任务数、分区数、报警区数；删除需二次确认 |
| 7 | — | 未校验组内是否还有用户 | 保留"连带删除"语义（与旧系统一致），但**必须先预览确认** |

### 【数据库】

**读（预览与收集）**

| 目的 | SQL |
|---|---|

## 2.4 功能 F-21：启用 / 停用用户

### 【功能描述】

批量启用或停用用户，并联动其名下任务的启用状态。

> ### ⚠️ 先读这条：`task.projectstate` 的真实语义与列注释**相反**
>
> `audioserver.sql` 中 `task.projectstate` 的注释写的是"**方案是否启用，1启用，0停用**"，
> 但**全部运行时代码与模板一致地按相反语义使用**：
>
> | `task.projectstate` | **实际语义** | 证据 |
> |---|---|---|
> | **`0`** | **启用**（列表显示红色 ● "Enabled"） | `BellManager/bellManager_form.html`：`projectstate == 0` → `Enabled●`<br>`FileAd/FileTaskManager_from.html`：`projectstate == 0` → `Enable●` |
> | **`1`** | **停用**（列表显示 "Disabled"） | 同上：`projectstate == 1` → `Disabled` |
>
> 其它一致证据：
> - `bellstart_msg`（启用方案）写 `projectstate = 0`，同时向后台发 `project state=1`（启用）
> - `bellstop_msg`（停止方案）写 `projectstate = 1`，同时向后台发 `project state=2`（停止）
> - `taskmanager.php` 用 `ORDER BY projectstate, playtime ASC` —— 启用的任务（0）排在前面
>
> **结论：列注释是过时/错误的，运行时约定 `0=启用 / 1=停用` 才是事实。**
> **新版必须沿用 `0=启用 / 1=停用`**，否则所有方案与任务的启停状态会全部反过来。
> 这条已列为兼容契约 **C-36**。
>
> ⚠️ 另注意：**`holidaytime.projectstate` 用的是相反的约定**（`1=启用 / 0=停用`，见 `enableholiday`/`disableholiday`）。
> **两张表同名列语义相反**，是本系统最容易踩的坑之一，已列为契约 **C-37**。

## 4.4 功能 F-35：删除任务

### 【原有实现问题 & 新版优化方案】

| # | 编号 | 原有问题 | 新版优化方案 |
|---|---|---|---|
| 1 | **D-118** | **删除条件带 `AND info = '' AND channel = 0` 而清理关联表时不带** —— `DELETE FROM terminaloftask WHERE taskid IN(…)` 与 `DELETE FROM mediaoftask WHERE taskid IN(…)` **无条件执行**，但 `DELETE FROM task … AND info='' AND (tasktype=2 or 7 or 15) AND channel=0` 有条件。若任务不满足条件（例如 `info` 非空的"方案"任务），**关联数据被删光而任务本身留下** → 任务变成空壳，播放失败 | 先按 ID 查出**真正可删的任务集合**，再对该集合统一删除任务与关联表；不满足条件的任务在响应中列为 `blocked` |
| 2 | D-119 | `DELETE FROM terminalkey WHERE id IN (SELECT keyid FROM terminalkeymap WHERE terminalid IN($taskid))` —— **把 taskid 当成 terminalid 用**（字段语义错配），会误删无关终端的快捷键 | 移除该逻辑；快捷键与任务的关系走 `terminalkeymaptask.taskid` |
| 3 | D-120 | 功放子任务清理只处理了 `prepower > 0` 的情况，若主任务的 `prepower` 被改为 0 后再删除，**功放子任务永久残留** | 直接按 `sec_task_id = 主任务ID AND tasktype = 9` 清理，不依赖 `prepower` |
| 4 | D-121 | 不删除 `offlinetaskofterminal` / `offlinemediaofterminal` 中该任务的记录 | 补齐清理 |
| 5 | D-122 | `COMMIT` 判断用 `if(!mysqli_error($con))`，而 `mysqli_error` 只反映**最后一条语句** | 逐条判定或用异常传播 |

| 序 | SQL |
|---|---|
| 1 | `SELECT taskid, prepower, info, channel, tasktype FROM task WHERE taskid IN (?,…)` → 筛出可删集合 |
| 2 | `SELECT taskid FROM task WHERE sec_task_id IN (可删集合) AND tasktype = 9` → 功放子任务 |
| 3 | `DELETE FROM terminaloftask WHERE taskid IN (可删集合 + 子任务)` |
| 4 | `DELETE FROM mediaoftask WHERE taskid IN (可删集合 + 子任务)` |
| 5 | `DELETE FROM terminalkeymaptask WHERE taskid IN (可删集合)` |
| 6 | `DELETE FROM offlinetaskofterminal WHERE taskid IN (可删集合)` |
| 7 | `DELETE FROM offlinemediaofterminal WHERE taskid IN (可删集合)` |
| 8 | `DELETE FROM task WHERE taskid IN (可删集合 + 子任务)` |
| 9 | LED 关联任务（`tasktype = 24 AND sec_task_id = 主任务`）单独清理 |

**DDL 变更：无。**
