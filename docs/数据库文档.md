> 配套《开发文档》。那一份说「功能怎么做」，这一份说「数据长什么样」。

# 1. 总览与红线

| | |
|---|---|
| 库名 | `audioserver` |
| 字符集 | `utf8`（不是 utf8mb4） |
| 引擎 | InnoDB 为主，少数 MyISAM |
| 表数 | **95** = 旧库 89 + 新建 6 |
| 旧库 89 张里新版读写的 | **45** |
| 旧库 89 张里遗留未用的 | **44**（见第 6 章） |
| 新建的 | **6**（`assistant_*`，见第 8 章） |
| 本地建库 | `audioserver.sql`（结构+字典）或 `audioserver-demo.sql`（带样例数据） |

## R1 · 不动旧表；新表可以建

> **2026-09-08 调整**：原来是「一张表都不许建」，现在放开了新建表，
> **对现有 89 张表的任何改动仍然一律禁止**。

```
✅ 可以新建表（表名加前缀，与旧库零冲突）
❌ 旧库那 89 张一个字节都不动：不加列、不改类型、不加索引、不改字符集、不加外键
```

不许改旧表的三个理由，任何一个单独成立：

1. 旧系统 ok112 还在跑，同一个库。加一列，它那些 `SELECT *` + 按下标取值的老代码就错位。
2. 后台 C 服务是编译好的二进制，按固定列序读数据。表结构一动，行为无法预测。
3. 数据库账号本身就没有 DDL 权限 —— 这是最后一道锁：

```sql
CREATE USER 'htweb'@'127.0.0.1' IDENTIFIED BY '<强口令>';
GRANT SELECT, INSERT, UPDATE, DELETE ON `audioserver`.* TO 'htweb'@'127.0.0.1';
```

建新表要用**另一个有 DDL 权限的账号**手工执行建表脚本 —— 程序自己永远不建表。

**推论一**：零碎的界面状态照旧落库外（表格列设置 → localStorage；
日志保留期、看板配置 → 服务端 JSON 文件）。成规模、要查询的状态才建新表。

**推论二**：⚠ 每加一张新表，**两处必须同步改**，否则静默坏掉 ——
`internal/serverparam/factory.go` 的表清单（恢复出厂会拒绝执行）、
备份结构指纹（见第 8 章末尾）。

⚠ 「往那些 0 行的空表里塞点东西」仍然**不行**：`shortcutkeytask`、`ctrltask` 这些
虽然现在空着，但都是后台 C 服务可能扫描的业务表 —— 万一被当成真任务执行，
就会在一所正在上课的学校里放出一段没人预期的广播。**要放新东西就建新表。**

# 2. 十条必须先知道的坑

## ① 列名 ≠ 列义

| 表.列 | 字面像什么 | 实际是 |
|---|---|---|
| `usergroup.serverpriv` | 服务器权限 | **遥控管理** |
| `usergroup.admpriv` | 系统维护 | **采播管理** |
| `usergroup.powerplay` | 强插播放 | **终端功放** |
| `usergroup.ttspriv` | 语音合成 | **文字语音** + 启用管理 |
| `usergroup.folderpriv` | 查看任务 | **媒体文件夹管理** |
| `usergroup.telephonepriv` | 电话广播 | **led播放**（新版改挂，旧版是电话管理） |
| `shortcutkeytask.mediaid` | 媒体 id | **任务 id**（`task.taskid`） |
| `serverbaseparam.adjusttime` | 是否校时（布尔） | **GPS 校时终端的 id**，0 = 不启用 |
| `ledsentence.mediaid` | 字幕 id | **`media.id`**（虚拟媒体那一行） |
| `ttssentence.sentenceid` | 句子 id | **`media.id`** —— 而它旁边那个 `mediaid` 列恒写 0 |

## ② `task.projectstate`：**0 = 启用，1 = 停用**

列注释是反的。而 `holidaytime.projectstate` 又是 **1 = 启用** —— 两个别混。
`enabletask.enstate` 跟 task 一样：0 启用 / 1 停用。

## ③ `usergroup.level` 是两位复合值（10 ~ 109）

```
十位 = 组级别（1~9）        个位 = 组内任务优先级基数（0~9）
```

列注释写「用户组级别 最大值5」是过时的。后台 C 服务按复合值解析任务优先级，
**存储格式必须原样保持**。界面上拆成两个控件录入，提交时合成。

## ④ `task.tasktype` 的取值比列注释多

列注释只写了「1-作息 2-文件 3-采播 4-电话 5-功放」。实际还有：

| 值 | 含义 |
|---|---|
| 1 / 15（`info` 非空） | 作息方案的一次打铃 |
| 2 | 文件广播 |
| 3 | 采播 |
| 5 | 终端功放 |
| **9** | 功放子任务（`prepower > 0` 时自动建，`sec_task_id` 指回主任务） |
| 15 / 17 / 19（`sec_task_id=0`） | 文字语音 |
| 24 / 30（`sec_task_id=0`） | 独立 LED 任务 |
| 24 / 30（`sec_task_id≠0`） | **LED 字幕子任务** |
| 25 | 声场任务 |

⚠ LED 的「独立 / 附属」**不看类型号**（现网全是 30），看 `sec_task_id` 是不是 0。

## ⑤ 作息方案没有自己的表

一个「方案」= `task` 表中共享同一个 **`task.info`** 的一组行，每行是一次打铃。
过滤条件四项缺一不可：`tasktype IN (1,15)` + `info` 非空 + `channel = 0` + `sec_task_id = 0`。

## ⑥ 「终端属于哪个分区」库里记了四份

```
terminal.groupid                 单值，终端自己记
terminalofgroup.groupid          多对多关联            ← 列表读这个
terminaloftask.groupid           这台终端在某条任务里的分区号   ← 后台下发读这个
terminalofalarmgroup.groupid     这台终端在某个报警分区里的分区号 ← 后台下发读这个
```

**增删分区必须四处同步**。旧版做到了后两者，从头到尾没写过 `terminal.groupid`（D-215）；
终端编辑页写的又只有 `terminal.groupid`（D-85）。所以旧版改完分区列表里看不到变化。
声场分区同型：`soundgroup` 表 + `terminal.soundsgroupid` 单值列（D-220）。

## ⑦ 文字语音 / LED 的正文挂在一条**虚拟 media** 行上

磁盘上没有对应文件：

```
media       typeid='tts'、filename='tts'、sample = 任务 id     ← 虚拟行
mediaoftask 把它挂到任务上
ttssentence / ledsentence  正文
```

⚠⚠ **两张正文表的关联列不是同一个，别写反**：

| 表 | 关联列 | 那一列里装的 | 另一列 |
|---|---|---|---|
| `ttssentence` | **`sentenceid`** | `media.id` | `mediaid` 恒写 0；只有「提示音」那一条例外，它指向真实的提示音媒体 |
| `ledsentence` | **`mediaid`** | `media.id` | 没有 sentenceid 这一列 |

也就是说 `ttssentence` 有一列名叫 `mediaid` 却几乎总是 0，真正的媒体 id 在
名叫 `sentenceid` 的那一列里 —— 又一处列名与列义对不上。
旧版 `DELETE FROM ttssentence WHERE sentenceid IN (...)` 也是按 sentenceid 删的。

`ledsentence.mediaid` 同样存 `media.id`，不是 `ledsentence` 自己的 id ——
以前这里写 0，后台按 media.id 去找就找不到（N-20）。

## ⑧ `enabletask` 的两列是并列的逗号分隔串

```
taskid  = "70007,70012,70020"      varchar(2048)
enstate = "0,1,0"                  varchar(1024)   逐项对应，0启用 1停用
```

`taskid` 超长会被**静默截断**，截断处可能落在某个 id 中间 → 后台解析出一个别的任务。
保存前按字节数挡住。另外 `enabletask.id` 是 `int(4) unsigned zerofill` 且**没有主键**
（只有 UNIQUE KEY），查出来是 `"0001"`，一律 CAST 成整数用。

## ⑨ 三条没被文档化的强契约（离线/云广播）

- `offlinemedia.id` 虽是 auto_increment，但**必须显式写入** `media.id` 的值（BR-201）；
  `offlinetask.taskid` 同理显式等于 `task.taskid`（BR-207）。后台靠它反查。
- `offlinetaskofterminal.area` 的**列默认值是脏的**（带三层单引号的 `”'11111111”'`），
  插入时必须显式写 `11111111`（BR-209）。
- `terminaloftask` **没有 `offlineparam` 列**（只有 id/taskid/terminalid/workstate/groupid/area）。
  旧版「离线任务下发」引用它并带 `or die()` —— 这个功能**一次都没成功过**（D-153）。

## ⑩ `area` 是 8 位掩码字符串

`terminaloftask.area` / `terminalofalarmgroup.area` 等，形如 `"11111111"`，
表示这台终端的 8 个分区/通道通不通。没勾过就用全 1 默认值。
`task.exemodel` 是同一套路的 **7 位星期掩码**（周日在第 0 位）。

# 4. 核心关系图

```
book_admin ──usergroupid──▶ usergroup (13 权限位 + level 复合值)
    │
    ├── userterminal ──▶ terminal
    └── task.task_user_id            ← 数据可见范围靠这一列

filetaskfree (任务分组树)
    ▲ parentid
    │
   task ─────────┬── mediaoftask ────▶ media ──folderid──▶ filefolder (媒体目录树)
   (tasktype)    │                        │
                 │                        ├─ ttssentence   (typeid='tts' 虚拟行)
                 │                        └─ ledsentence   (mediaid = media.id)
                 │
                 ├── terminaloftask ──▶ terminal ──groupid──▶ serverplaystream (终端分区)
                 │        └ groupid / area 掩码                    ▲
                 │                                                 │
                 ├── sec_task_id ──▶ 子任务：tasktype=9 功放 / 30 LED 字幕
                 │                                                 │
                 └── ledoftask ──▶ leddevice           terminalofgroup (多对多)

alarmgroupmap ──▶ alarmarea ──▶ terminalofalarmgroup ──▶ terminal
soundgroupinfo ──▶ soundgroup ──▶ terminal      sounddevice.groupid ──▶ soundgroupinfo
```

**没有一条外键约束** —— 库里一条 FK 都没建，全靠应用层保证。
所以删东西必须自己清干净关联行，这也是每个删除接口都配 `delete-preview` 的原因。

  真正在用的是拼写正确的那张。
- **`terminaltypekey`**：终端型号的按键字典，字典数据在 `audioserver.sql` 里，

## 恢复出厂时的处理

「恢复出厂」把 89 张表**穷举**成三类：**清空 / 按条件保留 / 有意不动**，
运行前拿实际库里的表清单比对，**只要出现一张不认识的表就拒绝执行**。
与其漏清一张，不如让人来决定它属于哪一类。

只用 `DELETE`，不用 `TRUNCATE`（BR-262），一条 DDL 都不执行；
仅超级管理员可用，要逐字输入确认文本，操作前后各写一行审计，全程一个事务。

# 7. 一致性自检 SQL

改完东西、或者怀疑哪里不对劲时，挨个跑一遍。**正常情况全部返回 0 行**。

```sql
-- ① 孤儿：任务的媒体清单指向不存在的媒体
SELECT mt.* FROM mediaoftask mt LEFT JOIN media m ON m.id = mt.mediaid WHERE m.id IS NULL;

-- ② 孤儿：任务的终端清单指向不存在的终端
SELECT tt.* FROM terminaloftask tt LEFT JOIN terminal t ON t.id = tt.terminalid WHERE t.id IS NULL;

-- ③ 孤儿：清单挂在不存在的任务上
SELECT taskid FROM mediaoftask   WHERE taskid NOT IN (SELECT taskid FROM task)
UNION ALL
SELECT taskid FROM terminaloftask WHERE taskid NOT IN (SELECT taskid FROM task);

-- ④ 孤儿子任务：sec_task_id 指向已经不存在的主任务
SELECT taskid, tasktype, sec_task_id FROM task
 WHERE COALESCE(sec_task_id,0) <> 0 AND sec_task_id NOT IN (SELECT taskid FROM task);

-- ⑤ 孤儿字幕 / 正文  ⚠ 两张表的关联列不一样，见第 2 章⑦
SELECT ls.* FROM ledsentence ls
  LEFT JOIN mediaoftask mt ON mt.mediaid = ls.mediaid    -- ledsentence 用 mediaid
 WHERE mt.mediaid IS NULL;
SELECT ts.* FROM ttssentence ts
  LEFT JOIN mediaoftask mt ON mt.mediaid = ts.sentenceid -- ttssentence 用 sentenceid
 WHERE mt.mediaid IS NULL AND ts.type <> 0;              -- type=0 是提示音行，不走这条链

-- ⑥ 孤儿 LED 屏绑定
SELECT o.* FROM ledoftask o LEFT JOIN task t ON t.taskid = o.taskid WHERE t.taskid IS NULL;

-- ⑦ 分区四处不一致：终端自己记的分区和关联表对不上
SELECT t.id, t.terminalname, t.groupid AS on_terminal, g.groupid AS on_relation
  FROM terminal t LEFT JOIN terminalofgroup g ON g.terminalid = t.id
 WHERE COALESCE(t.groupid,0) <> COALESCE(g.groupid,0);

-- ⑧ 任务里引用了不存在的分区号
SELECT DISTINCT groupid FROM terminaloftask
 WHERE groupid <> 0 AND groupid NOT IN (SELECT streamid FROM serverplaystream);

-- ⑨ 归属为空的任务（可见范围会失效）
SELECT taskid, taskname FROM task WHERE COALESCE(task_user_id,0) = 0;

-- ⑩ 用户组 level 落在合法区间外（应为 10~109）
SELECT id, name, level FROM usergroup WHERE level < 10 OR level > 109;

-- ⑪ enabletask 的两串长度对不上（应当逐项对应）
SELECT id, taskid, enstate FROM enabletask
 WHERE LENGTH(taskid) - LENGTH(REPLACE(taskid, ',', ''))
    <> LENGTH(enstate) - LENGTH(REPLACE(enstate, ',', ''));

-- ⑫ 虚拟媒体行没有对应的正文
SELECT m.id, m.name FROM media m
 WHERE m.typeid = 'tts'
   AND m.id NOT IN (SELECT sentenceid FROM ttssentence)   -- ⚠ sentenceid
   AND m.id NOT IN (SELECT mediaid    FROM ledsentence);  -- ⚠ mediaid
```

## 样例库里已知的一处「不干净」

拿 `audioserver-demo.sql` 建的库跑上面这些，**只有第 ④ 条会返回 1 行**：

```
taskid=70000  taskname='reset'  tasktype=13  sec_task_id=417
```

这是旧系统留下的一条陈年数据 —— `tasktype=13` 不在任何一页的取值范围里，
`sec_task_id` 指向的 417 号任务早就不存在了。新版任何一个页面都不会碰它，
留着是因为不擅自改现网数据。**看到这一行是正常的，不用去修。**
其余 11 条检查全部返回 0 行。

**建库自检**：导完 `audioserver.sql` 或 `audioserver-demo.sql` 之后

```sql
SELECT COUNT(*) FROM information_schema.tables WHERE table_schema='audioserver';  -- 应为 89
SELECT username FROM book_admin;                    -- 至少有 admin
SELECT id, name, level FROM usergroup;              -- 至少有 id=1 的系统组
```

# 8. 新建的 6 张表（AI 助手）

建表脚本：**`db/assistant_tables.sql`**。由管理员用一个有 DDL 权限的账号执行一次：

```bash
mysql -uroot audioserver < db/assistant_tables.sql
```

htweb 的运行账号**有意不给 DDL**，所以程序自己不会建表，也建不了。

**为什么要新建表**：助手有一批必须持久化、旧库里又无处可放的状态 ——
会话上下文、指令历史、任务覆盖、临时播放登记、撤销凭据。
原来那套 Python 实现把它们放在 `backend/data/*.json` 里，
进程重启或多实例部署就会丢/打架。

**字符集为什么是 utf8 不是 utf8mb4**：htweb 的连接串写死 `charset=utf8`（改不得，
理由见 `config.DSN` 的注释）。连接是 utf8 时四字节字符在协议层就被截断了，
列声明成 utf8mb4 也救不回来。所以新表跟着用 utf8，**四字节字符（emoji）
由 Go 侧在写入前剔除**。

| 表 | 装什么 | 对应原实现 |
|---|---|---|
| `assistant_session` | 多轮会话上下文：上一轮意图槽位、待确认动作、锁定项、连续失败次数 | 进程内存 / ContextVar |
| `assistant_message` | 对话与指令历史 | `assistant_command_logs.json` |
| `assistant_setting` | 助手设置（键值，可分全局/按人） | `assistant_settings.json` |
| `assistant_task_override` | **任务覆盖与影子任务**，单日例外靠它实现 | `task_overrides.json` |
| `assistant_runtime_play` | 立即播放建的临时任务登记 | 只在进程内存里（重启即丢） |
| `assistant_undo` | 撤销凭据 + 变更前快照 | `ChatResponse.undo_token` |

⚠ **不要把对话往 `log` 表里塞** —— 那张是操作日志，混进去会污染审计。

## 这 6 张表实际用起来是什么样

建完之后又过了一轮开发，下面是各表**真正**在被怎么用 —— 与上面那张
「对应原实现」的表配着看。

### `assistant_session`

`last_intent` / `last_slots` 支撑两件事：

- **指代消解**：「把刚才那个停掉」→ 从上一轮回填 `task_name`。
  只回填对象类槽位（任务、终端、分区、媒体），**时间那几个故意不回填** ——
  「把刚才那个也停掉」指的是同一个对象，不是同一个时间。
- **缺槽位续问**：上一轮回了「还差时间范围」，这一轮用户只说「明天」，
  要接着上一轮那个意图做。上下文存在 `locked` 一列里
  （键 `__ask_intent__` / `__ask_slots__`）。

`pending` 存待确认动作（「这次还是永久」「确定要删吗」）。它有两重超时：
会话本身的 `session_ttl`（默认 30 分钟），以及 pending 自己的 5 分钟 ——
隔了十分钟才回一句「就这一次」，用户多半已经在说别的事了。

### `assistant_runtime_play`

立即播放会在 `task` 表里留下一条**真实任务**（tasktype=2、exemodel 全 0、
priority 10、起止日期都是今天）。这张表记的是"哪条任务是助手临时建的"：

```sql
-- 谁还在播
SELECT r.taskid, r.taskname, r.terminal_ids, r.starttime
  FROM assistant_runtime_play r WHERE r.state = 'playing';
```

`taskname` 存的是**媒体名**不是内部任务名 —— 用户说「停止播放」时听到的是
这个名字，回一句「助手即时播放_出旗曲.mp3_0908064302 已停止」只会让人困惑。

停止时会把那条临时任务连同 `mediaoftask` / `terminaloftask` 一起删掉，
顺序是先停再删。不删的话任务列表里会越堆越多，而且每一条都长得像用户自己建的。

### `assistant_setting`

目前用到两个键，键名与原实现一致：

| 键 | 取值 | 谁在用 |
|---|---|---|
| `default_schedule_kind` | 小学 / 中学 / 高中 / 大学 | `create_schedule` 挑模板 |
| `default_schedule_season` | 夏季 / 冬季 | 同上 |

`userid = 0` 那一份是全局的，只有管理员能改。

### `assistant_task_override` —— 目前还没用上

原本打算用它记单日例外。实际做下来，**一次性操作落在了 `enabletask` 上**
（见《开发文档》10.5「一次性操作落在 enabletask 上」）—— 那是这套库里
本来就有的「启用管理」，运维在页面上看得见、改得动、删得掉，
比另起一张只有助手认识的表好。

一次性挪动会额外建一条**影子任务**（复制源任务、钉到目标那一天）。
影子任务现在靠命名约定认出来：`{原名}_once_{源任务id}_{日期}`。
这张表留着，等影子任务多到需要台账时再用；现在它是空的。

### `assistant_undo` —— 目前还没用上

立即播放的撤销走的是「说一句停止播放」那条路（`stop_task` 在没指名任务时
会去找这个用户还在播的那一条），不需要令牌。这张表留给后面真正需要
「撤销一次写操作」的场景。

⚠ 这两张空表**不是遗留垃圾**，`db/assistant_tables.sql` 里保留它们是有意的：
删掉再加回来是一次 DDL，而 htweb 的运行账号没有 DDL 权限，
每次都要找管理员。留着不占地方。

## 助手会写哪些**旧表**

助手不只写自己那 6 张。下面是它会动的旧表，以及走的是谁：

| 旧表 | 什么时候写 | 走谁 |
|---|---|---|
| `task` | 启停、调音量、挪动、对调、位移、建方案、立即播放 | `task.Control` / `task.SetVolume` / `bell.*` |
| `mediaoftask` | 建方案、立即播放、影子任务复制 | `bell.Create` / `task.Create` / `task.Copy` |
| `terminaloftask` | 同上，以及给任务加减终端 | 同上 / 助手自己（主任务与子任务一个事务里换） |
| `enabletask` | 一次性取消、一次性挪动 | `enable.Create` |
| `serverplaystream` | 新建 / 删除分区 | `zone.Create` / `zone.Delete` |

## 加表带来的两个连带影响（都已处理）

**① 恢复出厂会被挡住。** tao 的恢复出厂把库里所有表穷举成三类，
遇到一张不认识的就**拒绝执行**（有意的保险）。加完 6 张表后实测确实被挡了：

```
executable: false
blocker: 数据库里有 6 张表不在任何一份清单里（assistant_message、…）
```

处理：6 张全部归入 `clearTables`（`internal/serverparam/factory.go`）——
它们装的都是业务数据，恢复出厂理应一并清掉；而且
`assistant_task_override` / `assistant_runtime_play` 里记着影子任务和临时任务的
taskid，`task` 表被清之后那些记录就是指向空气的，必须跟着清。
改完实测：清空 60 张、未知 0 张、`executable: true`。

**② 建表之前做的备份会全部作废。** 备份包带结构指纹，加表后指纹就对不上了，
预检会判「结构不一致，已阻止」。

处理：把「当前库比备份包**多**出来的表」从阻断项里摘出来 ——
恢复时本来就不会碰这些表，拦住它没有任何安全收益，代价却是每加一张新表
就让此前所有备份作废。其余几种差异照旧拦死。实测两个方向：

| 情形 | 判定 |
|---|---|
| 当前库比备份包多一张表 | ✅ 可恢复，提示「恢复不会动它们」 |
| 备份包里有、当前库没有 | ❌ 仍然拦住 |
| 列类型 / 字符集变了 | ❌ 仍然拦住 |
