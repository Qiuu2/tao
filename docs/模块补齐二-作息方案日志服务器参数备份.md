# 0. 本册最重要的三个结论（先读）

| # | 结论 | 影响 |
|---|---|---|
| **①** | **作息方案不是一张独立的表。** 一个方案 = `task` 表中**共享同一个 `task.info`（方案名）**、且 `tasktype IN (1,15)`、`channel = 0`、`sec_task_id = 0` 的**一组行**；每一行是一节课/一次打铃。方案的起止日期由 `MIN(startdate)`/`MAX(enddate)` 聚合得到 | 若按"方案表 + 明细表"建模，会与旧数据**完全对不上**。已列为契约 **C-38** |
| **②** | **`playbelloftask` 与 `belltask` 两张表在业务代码中完全未被使用**，只出现在"恢复出厂"的清空例程里 | 不要误当作作息方案的主表。已列为契约 **C-39** |
| **③** | **恢复备份会执行 `DROP TABLE` + `CREATE TABLE`** —— 备份包里存的就是 `SHOW CREATE TABLE` 的原文。恢复一个**结构不一致的旧备份包，会直接把线上表结构改掉** | 这是 DDL 红线上最大的实际风险。必须在恢复前校验备份包结构，见 §4.2 与契约 **C-40** |

# 1. 业务域十：作息方案（打铃）

## 1.0 数据模型（必须先理解）

```
一个"作息方案"（例如"春季作息"）
   = task 表中 info = '春季作息' 的一组行
       ├─ task 行1：taskname='早读铃', playtime='07:20:00', tasktype=1 …
       │            └─ mediaoftask(taskid=行1, mediaid=铃声, sort=1)
       │            └─ terminaloftask(taskid=行1, terminalid=…)
       ├─ task 行2：taskname='第一节上课', playtime='08:00:00' …
       ├─ task 行3：taskname='第一节下课', playtime='08:45:00' …
       └─ …（每节课一行）

聚合出的"方案"属性：
   方案名     = task.info
   方案代表ID = MIN(taskid)          ← 列表里"这一行方案"的 id
   打铃条目数 = COUNT(taskname)
   起始日期   = MIN(startdate)
   结束日期   = MAX(enddate)
   方案状态   = CASE ROUND(AVG(projectstate),0) …   ← 组内多数状态
   创建者     = book_admin.username（经 task.task_user_id 关联）
```

**过滤条件（三项缺一不可）**：`tasktype IN (1,15)`、`task.info <> ''`、`channel = 0`、`sec_task_id = 0`。

> ⚠️ **`task.projectstate` 的取值：`0` = 启用，`1` = 停用**，与列注释相反。
> 证据与说明见分册（一）§2.4 与主手册 §5.8，契约 **C-36**。

## 1.1 功能 F-48：作息方案列表

### 【功能描述】

以"方案"为单位聚合展示打铃方案，每行一个方案，展示条目数、起止日期、状态、创建者。

### 【交互点】

| 元素 | 说明 |
|---|---|
| 表格列 | 选择 · 方案名称(`task.info`) · **状态**（`projectstate==0` → 红色●"启用"；`==1` → "停用"）· 条目数 · 创建者 · 起始日期 · 结束日期 · 浏览 |
| 浏览 | 跳 `displayplantask.php?taskid=<MIN(taskid)>`，展开该方案的全部打铃条目 |
| 筛选 | 搜索条件 = `方案名称`（对应 `task.info`）；关键字（模糊）；排序下拉 |
| 底部按钮 | 全选 / 取消 / **添加方案** / **修改方案** / **修改单条** / **批量修改** / **复制方案** / **删除方案** / **启用** / **停止** / **导出下载** / **恢复导入** |
| 未注册时 | 部分按钮被 JS 隐藏（`registerflag ∉ {1,2}`） |

### 【原有实现问题 & 新版优化方案】

| # | 编号 | 原有问题 | 新版优化方案 |
|---|---|---|---|
| 1 | **D-161** | **分页被整体注释掉** → 一次渲染全部方案 | 恢复服务端分页。聚合查询用 `COUNT(DISTINCT info)` 取总数 |
| 2 | **D-162** | 排序 `ORDER BY '$_GET[searchsequence]' DESC` —— **加引号变常量排序**，排序下拉永远不生效（与 D-40/D-51/D-99 同一批复制粘贴错误） | 白名单映射；对聚合列排序用别名 |
| 3 | **D-163** | 状态聚合用 `CASE ROUND(AVG(projectstate),0) WHEN 1 THEN 1 WHEN 0 THEN 0 END` —— **方案内条目状态不一致时，显示的是"多数派"状态**，用户看到"启用"但其中某几节课实际是停用的，且**界面无任何提示** | 保留聚合显示（兼容），但**额外返回 `mixedState: true` 标记**，UI 上标注"部分条目状态不一致"，点击可展开查看 |
| 4 | D-164 | 搜索分支的 SQL 用 `tasktype=1`，无搜索分支用 `tasktype IN(1,15)` —— **两者过滤范围不同**，一搜索就把 `tasktype=15` 的方案漏掉了 | 统一为 `tasktype IN (1,15)` |
| 5 | D-165 | 搜索分支**缺少 `task.info != ''` 条件**（无搜索分支有）→ 搜索时可能把 `info` 为空的普通任务当成方案聚合进来 | 过滤条件提为公共 WHERE 片段 |
| 6 | D-166 | `book_admin` 用逗号隐式内连接 → **创建者被删除后整个方案在列表中消失**（同 D-22 模式） | `LEFT JOIN book_admin`，创建者缺失时显示"(用户已删除)" |
| 7 | D-167 | 管理员判定用 `$_SESSION['username']=="admin"` 字符串比较 | 统一为 `usergroupid = 1` |

### 【数据库】

| 项 | 内容 |
|---|---|
| **主表** | `task`（聚合）、`book_admin`（创建者） |
| **读字段** | `MIN(task.taskid) AS taskid`、`task.info`、`COUNT(task.taskname) AS itemCount`、`MIN(task.startdate)`、`MAX(task.enddate)`、`ROUND(AVG(task.projectstate),0) AS projectstate`、`MIN(task.projectstate)`/`MAX(task.projectstate)`（用于判断是否混合）、`book_admin.username` |
| **WHERE（固定）** | `task.tasktype IN (1,15) AND task.info <> '' AND task.channel = 0 AND task.sec_task_id = 0` |
| **WHERE（可见范围）** | 管理员：无；普通用户：`AND task.task_user_id = :uid` |
| **WHERE（筛选）** | `AND task.info LIKE :kw` |
| **GROUP BY** | `task.info` |
| **ORDER BY** | 白名单，默认 `projectstate, MIN(startdate) ASC` |
| **总数** | `SELECT COUNT(DISTINCT task.info) FROM task WHERE <同条件>` |
| **关联** | `task.task_user_id → book_admin.id`（**LEFT JOIN**） |
| **写字段** | 无 |
| **DDL 变更** | **无** |

### 【接口设计（新版）】

**`GET /api/bell-plans`**　权限：`bellpriv` 或管理员

| 参数 | 说明 |
|---|---|
| `keyword` | 模糊匹配 `task.info`（方案名） |
| `orderBy` / `order` | 白名单：`info` / `startdate` / `projectstate` |
| `page` / `pageSize` | 分页 |

```jsonc
{ "code":0, "data": {
  "list": [
    { "planName": "春季作息", "representativeTaskId": 70021,
      "itemCount": 18,
      "startdate": "2026-03-01", "enddate": "2026-07-15",
      "projectstate": 0, "projectStateText": "启用",
      "mixedState": false,

  "total": 4, "page": 1, "pageSize": 18, "totalPages": 1 } }
```

> `planName`（即 `task.info`）才是方案的**业务主键**；`representativeTaskId` 只是 `MIN(taskid)`，用于兼容旧的按 taskid 传参的接口。

### 【业务规则】

| # | 规则 |
|---|---|
| BR-216 | **一个作息方案 = `task` 中共享同一 `task.info` 的一组行**；`task.info` 是方案的业务主键 |
| BR-217 | 方案的过滤条件固定为 `tasktype IN (1,15) AND info <> '' AND channel = 0 AND sec_task_id = 0`，**所有分支必须一致**（旧版搜索分支不一致，是缺陷） |
| BR-218 | 方案状态取组内 `projectstate` 的四舍五入平均值；**组内不一致时必须标记 `mixedState`** |
| BR-219 | `projectstate`：**`0` = 启用，`1` = 停用**（契约 C-36） |
| BR-220 | 普通用户只能看到自己创建的方案（`task.task_user_id`） |
| BR-221 | 方案的起止日期是组内条目的 `MIN(startdate)` / `MAX(enddate)` |

## 1.2 功能 F-49：新增 / 修改作息方案

### 【功能描述】

创建一个方案：填方案名 + 生效日期范围 + 星期 + 终端范围，然后**逐条添加打铃条目**（课程名、打铃时间、铃声媒体、时长）。

对应模板：`addbelltask.html`（75KB）、`modifybell.html`（90KB）、`modifybellall.html`（93KB）、`modifybelltime.html`（32KB）——
这四个模板是全系统最大的页面，本质上是**一张可动态增删行的课表编辑器**。

### 【表单结构】

| 层级 | 字段 | 落库 |
|---|---|---|
| **方案级**（对组内每一行都相同） | 方案名称 | `task.info` |
| | 起始日期 / 结束日期 | `task.startdate` / `enddate` |
| | 星期掩码 | `task.exemodel` |
| | 终端范围 | `terminaloftask`（组内每条任务都要写一份） |
| | 音量 | `task.defaultvolume` |
| | 优先级 | `task.priority` |
| | 提前开电源 | `task.prepower` |
| | 发送模式 | `task.datasendmodel` |
| **条目级**（每节课一行） | 课程/铃声名称 | `task.taskname` |
| | 打铃时间 | `task.playtime` |
| | 铃声媒体 | `mediaoftask(mediaid, taskid, sort)` |
| | 播放时长 / 循环次数 | `task.timelengthtype` + `task.timelength` |

**每添加一个条目 = 向 `task` 表插入一行**，`info` 都填同一个方案名。

### 【原有实现问题 & 新版优化方案】

| # | 编号 | 原有问题 | 新版优化方案 |
|---|---|---|---|
| 1 | **D-168** | **方案名重名校验只在"复制"时做，新增时不做** → 可以建出两个同名方案，之后它们会被 `GROUP BY info` **聚合成一个**，条目混在一起，且启停会互相影响 | 新增/改名时都做唯一性校验；用 `GET_LOCK('bell_plan_' + name)` 防并发（**不建唯一索引**） |
| 2 | **D-169** | 修改方案名时，需要把组内**每一行**的 `info` 都改掉；旧代码逐行 UPDATE 且无事务 → 中途失败会把一个方案**劈成两半**（一部分是新名、一部分是旧名） | 单条 `UPDATE task SET info = :new WHERE info = :old AND tasktype IN (1,15) AND channel = 0`，事务包裹 |
| 3 | D-170 | 条目级的"删一条加一条"没有事务边界 | 事务包裹 |
| 4 | D-171 | 终端清单要为组内每条任务各写一份 `terminaloftask` —— 18 节课 × 50 终端 = **900 行逐条 INSERT** | 批量 INSERT（一条语句多组 VALUES，分批 500） |
| 5 | D-172 | 新增任务后用 `SELECT MAX(taskid)` 取自增 ID（同 D-52，并发风险） | `LAST_INSERT_ID()` |
| 6 | D-173 | 打铃时间不校验是否与同方案内其它条目重复 | 校验同方案内 `playtime` 不重复，重复时提示 |
| 7 | D-174 | 方案名可含单引号等字符，直接拼进 `WHERE info = '$name'` → 注入 + 语句断裂 | 参数绑定 |
| 8 | D-175 | 页面 75~93KB，全部逻辑内联在模板 JS 中，媒体与终端下拉一次性渲染全量数据 | 前端组件化；媒体/终端改远程搜索下拉 |

### 【数据库】

| 操作 | SQL |
|---|---|
| 方案名唯一性 | `SELECT 1 FROM task WHERE info = ? AND tasktype IN (1,15) AND channel = 0 LIMIT 1` |
| 新增条目 | `INSERT INTO task (taskname, info, israndomplay, projectstate, timelengthtype, timelength, prepower, datasendmodel, state, startdate, enddate, playtime, endtime, exemodel, priority, tasktype, channel, bandrate, samplerate, cmd, cmdargs, playfileid, defaultvolume, task_user_id, sec_task_id, parentid) VALUES (…)` |
| 条目铃声 | `INSERT INTO mediaoftask (mediaid, taskid, sort) VALUES (?,?,?)` |
| 条目终端 | `INSERT INTO terminaloftask (taskid, terminalid, workstate, groupid, area) VALUES (?,?,?,?,?)` |
| 改方案名 | `UPDATE task SET info = ? WHERE info = ? AND tasktype IN (1,15) AND channel = 0` |
| 改方案级属性 | `UPDATE task SET startdate=?, enddate=?, exemodel=?, defaultvolume=?, priority=?, prepower=?, datasendmodel=? WHERE info = ? AND tasktype IN (1,15) AND channel = 0` |
| 改单条条目 | `UPDATE task SET taskname=?, playtime=?, timelengthtype=?, timelength=? WHERE taskid = ?` |
| 删单条条目 | `DELETE FROM mediaoftask WHERE taskid = ?` + `DELETE FROM terminaloftask WHERE taskid = ?` + `DELETE FROM task WHERE taskid = ?` |

**DDL 变更：无。**

## 1.3 功能 F-50：启用 / 停止方案

### 【功能描述】

按方案整体启停（不是按单条条目）。

### 【原有实现流程】

1. 用传入的 `taskid` 反查 `task.info`（方案名）
2. 按方案名批量更新组内**所有** `tasktype IN (1,15,9)` 的行 —— 注意**包含功放子任务 `tasktype=9`**
3. 向后台发 `project?state=1&info=<方案名>`（启用）或 `state=2`（停止）

### 【原有实现问题 & 新版优化方案】

| # | 编号 | 原有问题 | 新版优化方案 |
|---|---|---|---|
| 1 | ~~"启停倒置"~~ | ~~`bellstart_msg` 写 `projectstate=0`~~ —— **不是缺陷**。在 `0=启用` 的真实约定下逻辑正确（见 §0 与契约 C-36） | 原样保留；代码中用具名常量替代裸数字 |
| 2 | **D-176** | 更新语句 `WHERE task.info = '$row[info]' AND task.tasktype IN(1,15,9)` **不带 `channel = 0`** —— 而列表查询是带的。若存在同名的 `channel != 0` 任务，会被一起启停 | 补上 `AND channel = 0`，与列表口径一致 |
| 3 | D-177 | **不校验方案归属** —— 传任意 taskid 即可启停别人的方案 | 校验 `task_user_id`（管理员除外） |
| 4 | D-178 | 启停同时把 `state = 0`、`offlinestate = 0` 一并重置，但**未在任何地方说明**；若方案正在离线传输中，会被静默打断 | 保留行为（兼容），但在响应中提示"已重置离线传输状态" |
| 5 | D-179 | `if($row = ...)` —— **taskid 不存在时函数静默结束**，页面无任何反馈 | 明确返回 404 |
| 6 | D-180 | 方案名直接拼进 SQL | 参数绑定 |
| 7 | D-181 | 后台通知用 `send_socket_schedules("project", 1|2, info)` —— **以方案名（字符串）作为标识下发**，方案名含特殊字符时协议会截断 | 保持协议不变（兼容要求），但对方案名做长度与字符校验，拒绝含协议分隔符的名称 |

### 【数据库】

| 操作 | SQL |
|---|---|
| 反查方案名 | `SELECT info, task_user_id FROM task WHERE taskid = ? AND tasktype IN (1,15) LIMIT 1` |
| 启用 | `UPDATE task SET projectstate = 0, state = 0, offlinestate = 0 WHERE info = ? AND tasktype IN (1,15,9) AND channel = 0` |
| 停止 | `UPDATE task SET projectstate = 1, state = 0, offlinestate = 0 WHERE info = ? AND tasktype IN (1,15,9) AND channel = 0` |
| 通知 | `project?state=1&…`（启用）/ `project?state=2&…`（停止），标识为方案名 |

**表·字段**：`task.info`、`task.projectstate`、`task.state`、`task.offlinestate`、`task.tasktype`、`task.channel`。**DDL 变更：无。**

### 【接口设计（新版）】

**`PUT /api/bell-plans/{planName}/enable`** / **`PUT /api/bell-plans/{planName}/disable`**

```json
{ "code":0, "data": { "planName":"春季作息", "affectedTasks": 20,
                      "offlineStateReset": true, "notified": true } }
```

### 【业务规则】

| # | 规则 |
|---|---|
| BR-228 | 启停以**方案为单位**，作用于组内全部条目 |
| BR-229 | 启停范围包含该方案的**功放子任务（`tasktype = 9`）** |

## 4.1 功能 F-58：备份列表 / 创建备份

### 【功能描述】

在服务器端生成数据库备份包，并列出已有备份供下载、恢复、删除。

### 【备份包的实际内容（关键）】

`backup_restore_form.php` 的备份逻辑：

```
对数据库中每一张表：
    "DROP TABLE IF EXISTS <表名>;"           ← ⚠️ DDL
  + SHOW CREATE TABLE <表名> 的原文 + ";"    ← ⚠️ DDL（CREATE TABLE）
  + "INSERT INTO <表名> VALUES (...),(...);" ← 数据
    → 写入一个 <表名>.sql 条目
所有条目打进一个 ZipArchive，文件名后缀却是 .tar
```

> ⚠️ **备份包里存的是"备份那一刻的表结构 DDL"**。这意味着：
> **恢复一个结构不一致的备份包 = 把线上表结构改成备份时刻的结构。**
> 这是"禁止 DDL"红线上最大的实际风险来源。

## 4.2 功能 F-59：恢复备份（★DDL 红线上的最高风险功能）

### 【功能描述】

从备份包恢复数据库。

### 【原有实现流程】

1. 遍历备份目录找到同名 `.tar`
2. `zip_open()` 打开，逐条目读取内容
3. **非 mp3 条目**：把内容按 `;` 拆开，**逐条 `mysqli_query()` 执行**（其中包含 `DROP TABLE` / `CREATE TABLE`）
4. **mp3 条目**：`fopen(zip_entry_name(...), "w ")` 直接写文件到条目名指定的路径
5. 完成后向后台发 `server?state=1`

### 【原有实现问题 & 新版优化方案】

| # | 编号 | 原有问题 | 新版优化方案 |
|---|---|---|---|
| 1 | **D-229** | **`restore_backup_file.php` 完全没有会话与权限校验**（文件头只 require 了 config），**任何人访问 `restore_backup_file.php?file_name=xxx` 即可触发恢复** —— 而恢复等价于**执行任意 SQL（含 DROP TABLE）**。这是全系统**最高危的漏洞** | 服务端强制管理员权限 + CSRF 防护 + 二次确认 + 审计日志 |
| 2 | **D-230** | **`analyze_sql()` 用 `explode(";", $sql)` 拆分 SQL** —— 任何字段值中包含分号（媒体名"上课铃;备用"、任务备注、报警描述等**极其常见**）都会把 `INSERT` 语句**从中间劈开**，导致**恢复失败或数据被截断写入** | 改用**流式 SQL 解析器**（正确处理引号内的分号、转义、注释、多行语句），或直接调用 `mysql` 客户端导入 |
| 3 | **D-231** | **Zip Slip 路径穿越**：mp3 条目用 `fopen(zip_entry_name($file_handle), "w ")` 直接写入，**路径完全来自压缩包内部** → 精心构造的备份包可向服务器任意位置写文件（如 `../../../../etc/cron.d/x`），**等价于远程代码执行** | 条目路径必须 `basename()` + 限定到媒体根目录 + `realpath()` 断言 |
| 4 | **D-232** | `fopen(..., "w ")` —— **模式字符串多了一个空格** | 修正为 `"wb"` |
| 5 | **D-233** | **不校验备份包的表结构与当前 schema 是否一致** → 恢复旧版本备份包会把线上表结构改回旧结构，**直接违反"表结构锁定"红线** | **恢复前强制校验 `_manifest.json` 的结构指纹**；无 manifest 的旧包 → 先解析包内 `CREATE TABLE` 与 `audioserver.sql` 逐表逐列比对，**不一致则拒绝恢复并列出差异** |
| 6 | **D-234** | `START TRANSACTION` … `COMMIT` 包裹恢复过程，但 **`DROP TABLE` / `CREATE TABLE` 是 DDL，会隐式提交事务** → **ROLLBACK 完全无效**，恢复中途失败会留下半个库 | 恢复前**自动生成一份当前库的安全备份**；恢复失败时提示可回滚到该安全点。事务对 DDL 无效这一事实必须在 UI 上明确告知用户 |
| 7 | D-235 | 恢复过程无进度、无日志，大库时页面白屏 | 异步任务 + 进度 + 详细执行日志 |
| 8 | D-236 | 恢复完成只发 `server?state=1`，**不重启 Web 会话** → 当前登录用户的 session 指向的可能是已被覆盖的用户表 | 恢复后强制所有会话失效，要求重新登录 |
| 9 | D-237 | `search_foloder_file()` 用 `basename($file,".tar") == $file_name` 匹配，**未过滤 `$file_name` 中的路径分隔符** | 白名单字符校验 |

| **DDL 变更** | ⚠️ **有** —— 这是**唯一允许的 DDL 场景**，且执行的必须是**与 `audioserver.sql` 结构完全一致**的 DDL |

| 1 | **D-238** | **`del_backup_file.php` 没有任何会话与权限校验** → 任何人可删除服务器上的备份文件 | 强制管理员权限 |

# 5. 本册新增的兼容性契约

| # | 契约 | 违反后果 |
|---|---|---|
| **C-40** | **恢复备份是全系统唯一的 DDL 入口**；只允许恢复结构与 `audioserver.sql` **完全一致**的备份包，恢复前必须做结构指纹校验 | 恢复旧版本备份包会直接把线上表结构改掉，破坏新旧系统兼容 |
| **C-41** | **`logtask` 与 `logmedialist` 两表业务代码未使用**，新版同样不读不写 | 误用会写出旧程序读不到的数据 |
| **C-42** | **`sounddetect` 在 `serverbaseparam` 与 `serverconfig` 两处冗余存储，必须同时写、保持一致** | 两处不一致时旧程序与后台服务读到的开关状态不同 |
| **C-43** | **`task.info` 是作息方案的业务主键**；改方案名必须把组内所有行一起改 | 方案被劈成两半，启停与删除只作用于一半 |
| **C-44** | **作息方案的过滤条件固定为 `tasktype IN (1,15) AND info <> '' AND channel = 0 AND sec_task_id = 0`**，所有读写分支必须一致 | 口径不一致会漏掉或误伤任务 |

| | **D-231** | 备份包 Zip Slip 路径穿越 = 任意文件写入 = RCE |
| | **D-238** | 删除备份接口无鉴权 |

| **P0 数据正确性** | **D-230** | `explode(";")` 拆 SQL —— 字段值含分号即恢复失败/数据截断 |
| | **D-233** | 恢复不校验结构，会改掉线上表结构（**直接违反 DDL 红线**） |
| | **D-234** | DDL 隐式提交致恢复无法回滚 |
| | **D-189** | 复制方案用"新 ID 减 1"推算功放子任务关联 |

| | **D-168 / D-169** | 方案重名、改名非原子 |
| | **D-176** | 方案启停不带 `channel = 0` |
| | **D-209** | 按行号 `sed` 改 Apache 配置，易写坏 |

## 6.2 schema 合规性自检（本册全部方案）

| 优化动作 | 触及 schema | 判定 |
|---|---|---|
| 方案按 `task.info` 聚合 + `COUNT(DISTINCT info)` 分页 | 否 | ✅ |
| 改方案名用单条 `UPDATE … WHERE info = ?` | 否 | ✅ |
| 复制方案用 `LAST_INSERT_ID()` + 显式回填 `sec_task_id` | 否 | ✅ |
| 方案名唯一性用 `GET_LOCK` | 否 | ✅ **不建唯一索引** |
| 日志清空改 `DELETE`（弃用 `TRUNCATE`） | 否 | ✅ |
| 日志筛选列走白名单 | 否 | ✅ |
| 服务器参数 `UPDATE … WHERE id = 1` + 参数绑定 | 否 | ✅ |
| 恢复出厂逐表 `DELETE` + 保留条件 | 否 | ✅ |
| 备份包内新增 `_manifest.json` 结构指纹 | 否（**写进备份文件，不是数据库**） | ✅ |
| 恢复前做结构指纹比对并可拒绝 | 否（只读比对） | ✅ |
| 恢复时执行备份包内的 DDL | **是** | ⚠️ **唯一允许的 DDL 场景**，且必须与现行 schema 一致（C-40） |
| ~~给 `task(info)` 建索引加速方案聚合~~ | **是** | ❌ **禁止** → 用应用层缓存；`task` 表规模有限 |
| ~~给 `task` 加 `plan_id` 字段替代按 `info` 聚合~~ | **是** | ❌ **禁止** → 按 `info` 聚合是既有语义（C-43） |
| ~~新建"作息方案主表"~~ | **是** | ❌ **禁止** → 方案不是独立表（C-38） |
| ~~启用 `playbelloftask` 作为方案明细表~~ | **是**（语义变更，写出旧程序读不到的数据） | ❌ **禁止**（C-39） |
| ~~给 `log` 表建时间索引 / 改分区表~~ | **是** | ❌ **禁止** → 用时间范围 `DELETE` + 应用层限流 |
| ~~把 `sounddetect` 从 `serverbaseparam` 移除只留 `serverconfig`~~ | **是** | ❌ **禁止** → 双写保持一致（C-42） |

**结论：本册 81 条缺陷的修复方案中，除"恢复备份"这一唯一且受控的 DDL 场景外，全部零 DDL 变更。**
