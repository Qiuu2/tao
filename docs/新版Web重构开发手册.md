> # ⛔【重要硬性约束】
>
> **数据库 `audioserver.sql` 表结构完全锁定，禁止任何 DDL 变更。**
>
> - 禁止 `CREATE TABLE` / `ALTER TABLE` / `DROP TABLE` / `RENAME TABLE`
> - 禁止新增字段、删除字段、修改字段类型、修改字段注释、修改默认值
> - 禁止新建索引、外键、视图、触发器、存储过程、事件
>
> **新版程序读写数据库必须和旧存储完全兼容，新旧系统可共用一套数据库同时在线运行。**
> 旧数据必须能被新版 Web 直接、正确地读取；新版写入的数据必须能被旧 Web 与后台 C 广播服务正确读取。
>
> **业务 bug 只能在代码逻辑层修复，不能改动表、字段。**
> 凡是"改 SQL 写法、改分页算法、改递归实现、改事务与锁策略、改校验顺序、加应用层缓存/锁"的方案均可采纳；
> 凡是需要改动 schema 的方案一律否决，必须找到不改表的等价实现。
>
> 本手册每一个功能点的【数据库】小节，只列出 `audioserver.sql` 中**已存在**的表与字段。
> 合规性逐条自检见 [§7.6 字段依赖自检](#76-字段依赖自检合规性验证)。

# 1. 项目概述与重构约束

## 1.1 系统定位

网络广播 / 公共广播管理系统的 Web 管理端。管理对象包括：

- **终端设备**：网络终端、网络话筒、寻呼终端、网络功放、一体化音箱、LED 设备等 48 种类型
- **媒体资源**：音频文件的目录化管理、上传、试听、下载、删除
- **播放任务**：作息方案（打铃）、文件广播、采播、网络电台、TTS、LED 字幕、视频、声场
- **联动**：报警映射、快捷键映射、远程任务、离线下发
- **系统**：用户与权限、日志、备份恢复、服务器参数

Web 端**不直接控制硬件**，而是：写数据库 + 通过 UDP/TCP 向后台 C 广播服务（`audioserver`）发送变更通知，由后台服务执行实际的播放调度与终端通信。

## 1.2 旧系统技术形态

| 项 | 现状 |
|---|---|
| 语言 | PHP + Smarty 模板（`<{ }>` 定界符） |
| 页面结构 | frameset 三段式（top / menu / main），业务页内再嵌 frameset |
| 代码规模 | 295 个明文 PHP + 7 个 PM9SCREW 加密 PHP + 735 个 HTML 模板 |
| 写操作入口 | **`do.php` 单文件 30605 行**，200+ 个 `switch case` 分支 |
| 数据访问 | `mysqli_*` 过程式，**全部字符串拼接 SQL，无预处理** |
| 会话 | PHP `$_SESSION` |
| 质量 | 无分层、无测试、大量死代码与复制粘贴、SQL 注入遍布、事务语义被破坏 |

**7 个加密文件**（`adadd.php`、`addfile.php`、`admin.php`、`application.php`、`dataselect.php`、`left.php`、`phptest.php`）无法逆向，需要按运行时行为黑盒补齐。

## 1.3 重构目标

| 目标 | 说明 |
|---|---|
| **G1 存储零变更** | 数据库表结构一个字节都不动，新旧系统共用一套库 |
| **G2 业务语义一致** | 所有业务规则、状态取值、字段写入约定与旧系统完全一致 |
| **G3 实现层升级** | 修复注入、越权、递归、分页、事务等实现缺陷 |
| **G4 前后端分离** | 提供结构化 REST API，前端 SPA 化 |
| **G5 平滑共存** | 新旧 Web 可同时在线，用户可随时在两者间切换 |

## 1.4 重构红线（不可逾越）

| # | 红线 |
|---|---|
| R1 | **不执行任何 DDL**。若某方案"必须加字段才能实现"，则该方案作废，重新设计 |
| R2 | **不改变字段的业务取值语义**。如 `filefolder.priority` 必须继续表示"共享标记 0/1"，不得挪作他用 |
| R3 | **不改变写入格式约定**。如 `media.size` 单位仍是 KB、`media.typeid` 上传后仍是 `'mp3'`、`book_admin.userpwd` 仍是 MD5 |
| R4 | **不改变系统预置数据**。文件夹 id 1~9、用户 `admin`、用户组 1 保持原样 |
| R5 | **不占用后台服务维护的字段**。`serverbaseparam.*change`、`media.timelength/bitrate/sample/channel` 等由 C 服务回填，Web 侧只读（上传时写 0 除外） |
| R6 | **保留与后台服务的通知协议**。`file?state=X&id=Y` 必须照发 |
| R7 | **连接字符集固定 `utf8`**，不得升级 utf8mb4 |

> ### ⚠️ R1 的唯一例外：恢复备份
>
> 全系统只有一个功能会执行 DDL —— **恢复数据库备份**。备份包内存放的就是 `DROP TABLE IF EXISTS` + `SHOW CREATE TABLE` 的原文 + `INSERT`，恢复即执行这些语句。
>
> 这**不是"可以改表"的许可，恰恰相反**：正因为它能改表，它是本红线下**风险最高**的功能。约束如下：
>
> 1. **只允许恢复结构与 `audioserver.sql` 完全一致的备份包**；恢复前强制做结构指纹校验，不一致则拒绝并列出差异。
> 2. 恢复前自动生成一份安全备份。
> 3. **DDL 会隐式提交事务，恢复无法原子回滚** —— 必须在 UI 上明确告知。
> 4. 仅超级管理员可执行，需二次确认与审计日志。
>
> 详见 §7.2 契约 **C-40** 与《模块补齐二》§4.2。**除此之外，应用代码中不得出现任何 DDL 语句。**

## 1.5 技术选型

> ### ✅ 选型已定稿（2026-08-22 确认）
>
> | 层 | 选定方案 |
> |---|---|
> | **前端基座** | **Geeker-Admin**（`HalseySpicy/Geeker-Admin`，MIT，8,066⭐）——已落地到本仓 `web/` |
> | **后端** | **自写 Gin**，`database/sql` / `sqlx` 手写 SQL |
> | **数据库** | 现网 `audioserver`，**零 DDL** |
>
> #### ⛔ 为什么不用 gin-vue-admin / go-admin 这类全栈脚手架
>
> 技术栈虽然完全吻合，但 `gin-vue-admin` 的 `server/initialize/gorm.go::RegisterTables()` 会
> **`AutoMigrate` 34 张自有表**（`SysUser`/`SysAuthority`/`SysBaseMenu`/`casbin_rule`/`SysDictionary`/
> `MediaUpload`/`FileUploadAndDownload` …）。虽有 `System.DisableAutoMigrate` 开关，但关掉只是"不自动建"，
> 这些表**仍必须存在**框架才能启动。因此：
>
> - 指向 `audioserver` 库 → **当场违反 R1 红线**；
> - 指向独立库 → 引入 **SysUser + Casbin 第二套账号权限体系**，与旧系统的
>   `book_admin` + `usergroup`（13 个 priv 列）**并存**，形成两套用户、两套权限，
>   旧 Web 与新 Web 的账号体系分裂 → **直接违背 G5「新旧共存、可随时切换」**。
>
> **结论：只取纯前端模板，后端自写。** 这是同时满足"成熟 UI"与"零 DDL"的唯一路径。

选型已在 `docs/新架构说明.txt` 中确定，本手册沿用：

| 层级 | 技术选型 | 本手册补充约束 |
|---|---|---|
| 前端框架 | **Vue 3 + Vite** | 保留"左树右表"布局范式（见 §2.1） |
| UI 组件库 | **Element Plus** | 树用 `el-tree`（懒加载）；表用 `el-table` |
| 图表 | ECharts | 终端状态统计 |
| 地图 | Leaflet / MapLibre | 终端拓扑定位 |
| 后端 | **Go (Gin)** 或 C++ (libevent) | **数据访问强制 `database/sql` 预处理 + 参数绑定** |
| 数据库 | **MySQL，沿用现有 `audioserver.sql`** | **零 DDL 变更**（见本页硬性约束） |
| 音频处理 | FFmpeg | 转码参数须遵守 BR-38 ~ BR-40 |
| 实时通信 | WebSocket | 终端状态与任务状态推送 |
| 媒体协议 | RTP/RTSP/SIP | 与后台服务保持既有协议 |
| 认证 | Session 或 JWT | **密码哈希必须继续用 MD5**（见 R3） |

**数据访问层的强制要求**：

1. **禁止使用带自动迁移能力的 ORM**。若使用 GORM，必须**不调用 `AutoMigrate`**；使用 `sqlx` / `database/sql` 手写 SQL 是更安全的选择。
2. 所有 SQL 一律 `?` 占位符 + 参数绑定，**禁止 `fmt.Sprintf` 拼接 SQL**。
3. 表结构以 `audioserver.sql` 为唯一事实来源，结构体字段与列一一对应，**不得声明数据库中不存在的列**。
4. **CI 强制检查**：扫描代码与迁移目录中是否出现 `ALTER TABLE` / `CREATE TABLE` / `DROP TABLE` / `CREATE INDEX` / `ADD COLUMN` / `CREATE VIEW` / `CREATE TRIGGER` / `AutoMigrate`，**命中即构建失败**（见 §7.7 检查项 1、2）。

## 1.6 部署环境与共存约束（192.168.2.159 · 实测）

> 部署目标已确认：**新版 Web 与旧 ok112 同机部署在 `192.168.2.159`**。
> 本节内容为 **2026-08-22 通过 SSH 实地勘察所得**，非源码推测。
> ⚠️ 早期版本据旧源码推测"Apache 在 8886"，**该结论已被实测推翻**，见 §1.6.2。

### 1.6.1 服务器基本情况

| 项 | 实测值 |
|---|---|
| 操作系统 | **银河麒麟桌面版 V10 (SP1)**，内核 6.1.0-6-generic |
| 架构 | **x86_64** → Go 交叉编译目标 `GOOS=linux GOARCH=amd64` |
| 登录账号 | `tw`（属 `sudo` 组，`sudo` 需密码，实测可提权到 root） |
| 磁盘 | `/` 55G，已用 26G，**可用 27G** |
| 宿主已装 | `gcc 9.3.0`、`make 4.2.1`、`tar`、`curl`、`wget`、`docker 20.10.7`、`docker-compose` |
| 宿主**未装** | **`go`、`node`、`npm`、`git`、`mysql` 客户端、`php`** |

> `php` 与 `mysql` 未装在宿主上并不矛盾 —— 见下节：**整套旧系统跑在 Docker 里**。

### 1.6.2 【核心】旧系统是 Docker Compose 架构

实测 `ps -ef` 与容器挂载信息，旧系统由多个容器组成：

| 容器 | 作用 | 关键端口 |
|---|---|---|
| `httpd` (Apache) | 托管 PHP 前端，**三个虚拟主机分别对应三套应用**（见 §1.6.3） | **TCP 80 / 81 / 99 / 443** |
| `php-fpm` | 执行 ok112 的 PHP | — |
| `mysql` (mysqld) | 数据库 | **TCP 3306（已发布到宿主 `0.0.0.0:3306`）** |
| `audioserver` | **后台 C 广播服务** | **UDP 8886（已发布到宿主 `0.0.0.0:8886`）** |
| `a9000sdk` / `soundsdk` | SDK 服务 | UDP 8888 / 8900 等 |
| `filetransfer` | 文件传输 | TCP 8901 / 8902 |
| `xftts` | 语音合成 | — |
| `uvicorn` | Python 服务（AI/人脸） | TCP 8000 |

**两条关键结论：**

1. **`mysql` 与 `audioserver` 是 Docker 内部 DNS 名，`/etc/hosts` 中不存在。**
   宿主机上的进程**无法解析**这两个主机名 —— 旧 PHP 代码里的 `$DB_HOST="mysql"`、
   `$_SESSION['serverip']="audioserver"` 之所以能用，是因为 PHP 跑在容器内。
   **新版 Go 服务跑在宿主上，必须改用已发布的回环地址**（见 §1.6.4）。

2. **`serverbaseparam.webport`（值 8886）不是 Apache 端口，而是后台服务的 UDP 通知端口。**
   实测：TCP 8886 **无监听**，UDP 8886 **有监听**；Apache 实际在 80/81/99。
   旧代码 `inc/socket_conf.php` 把 `webport` 读出来当 UDP 目标端口用，语义即为此。
   **新版同样必须从 `serverbaseparam.webport` 读取该值再发 UDP，不得硬编码 8886。**

### 1.6.2b 【实测】同机三套 Web 应用的端口归属

`httpd-vhosts.conf` 实测配置 —— **这台服务器上同时跑着三套 Web 应用**：

| 端口 | DocumentRoot（容器内） | 对应宿主目录 | 应用 | 实测 |
|---|---|---|---|---|
| **80** | `/var/www/html/oktw/public` | `…/html/oktw` | oktw | 200 |
| **81** | `/var/www/html/ok112` | `…/html/ok112` | **旧 ok112 系统** | **200 ✅** |
| **99** | `/var/www/html/lumen/public` | `…/html/lumen` | lumen | 200 |
| **443** | `/var/www/html/ok112` | `…/html/ok112` | ok112 (SSL) | — |
| **8080** | —（Go 进程自身托管） | `…/html/htweb` | **新版 htweb** | **200 ✅** |

> ⚠️ **旧 ok112 的正确入口是 `http://192.168.2.159:81/`，不是 `/ok112/` 子路径** ——
> 因为 81 端口的 DocumentRoot 已经指向 ok112 目录本身，再加 `/ok112/` 会去找
> `…/html/ok112/ok112/`，必然 404。早期文档误写为 `/ok112/`，已据实测更正。
>
> 另注意：**Apache 的任何一个虚拟主机都没有指向 `html/htweb`**，
> 所以新版前端不会被 Apache 顺带托管，只能通过 `:8080` 访问。
> 这反而更干净：新旧两套在 Web 层完全隔离，互不影响。

### 1.6.3 目录与路径映射（实测）

**`/opt/apps/a9000/html` 被 bind-mount 到 httpd 容器的 `/var/www/html`**：

```
宿主 /opt/apps/a9000/html          ⇄  容器 /var/www/html          （Apache DocumentRoot）
     ├── ok112/                    ⇄       /var/www/html/ok112    ← 旧系统（勿动）
     ├── lumen/                    ⇄       …
     ├── oktw/                     ⇄       …
     └── htweb/   ← 新版放这里      ⇄       /var/www/html/htweb

宿主 /opt/apps/a9000/backup        ⇄  容器 …/link/backup
     └── mediadata/                     ← 媒体物理文件（实测 18 个 mp3）
```

**媒体路径映射规则（已实测验证）**：

| 来源 | 值 |
|---|---|
| 数据库 `media.filename` | `/backup/mediadata/1617155672594644.mp3` |
| **宿主真实路径** | **`/opt/apps/a9000/backup` + `/backup` 之后的部分**<br>→ `/opt/apps/a9000/backup/mediadata/1617155672594644.mp3` ✅ 文件确实存在 |

> 即：**宿主路径 = `/opt/apps/a9000` + `media.filename`**。
> 新版 Go 服务读写媒体文件按此规则拼接，**`media.filename` 字段本身的存储格式不变**（契约 C-05）。

### 1.6.4 新版部署方案（已定）

```
/opt/apps/a9000/html/htweb/          ← 前端 dist（Apache 也能顺带托管）
/opt/apps/a9000/htweb/
    ├── htweb                        ← Go 单二进制（linux/amd64，静态编译）
    ├── config.yaml
    └── logs/
```

**连接方式（全部走宿主已发布端口，不进 Docker 网络）**：

| 用途 | 目标 | 依据 |
|---|---|---|
| MySQL | **`127.0.0.1:3306`** | 3306 已发布到宿主 |
| 后台服务 UDP 通知 | **`127.0.0.1:<serverbaseparam.webport>`**（当前 8886） | UDP 8886 已发布到宿主 |
| 媒体文件 | `/opt/apps/a9000/backup/mediadata/` | 直接读宿主目录，**与旧系统同一份** |
| 新版监听端口 | **TCP 8080**（实测空闲；9000 亦空闲备选） | 避开 80/81/99/8000/8090 |

**为什么 Go 服务跑在宿主而不是做成容器**：宿主已发布了 3306 与 UDP 8886 两条必需链路，
跑在宿主即可完整工作；**不改动 docker-compose、不新增容器、不碰现网编排**，回滚只需停掉一个 systemd 服务。

**前端访问的两条路径**（都可用，二选一即可）：

| 方式 | 地址 | 是否改动现网 |
|---|---|---|
| **A（推荐）** Go 自身托管静态文件 | `http://192.168.2.159:8080/` | **零改动** |
| B 经现有 Apache | `http://192.168.2.159/htweb/` | 需在 httpd.conf 加 `/api` 反代 → **改现网配置，不推荐** |

> 采用 **A**：Go 同时提供 `/api/*` 与静态文件，**完全不碰 Apache 配置**，把对生产广播系统的影响面降到最低。
> 文件仍放 `/opt/apps/a9000/html/htweb/`（符合约定），方式 B 作为备选随时可启用。

### 1.6.5 共存三原则（实测校准后）

| # | 原则 | 落实 |
|---|---|---|
| **P1 换端口** | 新版占 **TCP 8080**，不碰 80/81/99/443 | 旧 Web 保持 `http://192.168.2.159:81/` 可用（实测 200） |

### 1.6.6 构建与安装策略（把服务器改动降到最小）

| 组件 | 在哪构建 | 服务器需要装什么 |
|---|---|---|
| 前端 | **开发机 Windows**（已有 node v24 / npm 11）→ 产出 `dist/` | **无需装 node** |
| 后端 | **开发机交叉编译** `GOOS=linux GOARCH=amd64` → 单个静态二进制 | **无需装 go** |

#### 换服务器时用 `deploy/install.sh`，别再手工装

打包与安装步骤见 **`deploy/README.md`**。脚本是幂等的，
`config.yaml` 已存在时不覆盖，前端上一版留在 `html/htweb.prev`。

它比手工多做了一件容易漏的事：**装受限免密 sudo 规则**
（`deploy/install-sudoers.sh` → `/etc/sudoers.d/htweb`）。
没有它，「服务器信息 → 版本设置」的提交和「时间设置」的两个按钮会**静静变灰**
—— 不报错，只是不能用，换台机器就得重排一遍。

⚠ 与之配套的一条：systemd 单元里**不能**有 `NoNewPrivileges=true`。
它会禁掉 setuid 提权路径，而 sudo 正是 setuid 程序，
加了这行则 sudoers 配得再对也无效。原委见《旧接口与源码缺陷清单》§19.3。

#### ⚠️ 实测：该服务器无法通过 apt 安装第三方软件包

尝试安装 `mariadb-client` 时被拒绝：

```
dpkg: 处理归档 …/mariadb-common_1%3a10.3.22-1ubuntu1_all.deb (--unpack)时出错：
 软件包 …deb 验证失败，拒绝安装！
```

排查结论：**不是 apt 损坏**（`/` 为 `rw`、磁盘 26G 可用、inode 仅用 11%），
而是**银河麒麟的软件包签名校验策略**主动拒绝了来自 Ubuntu focal 源、缺少麒麟签名的包。

**这条约束反过来确认了本方案的正确性：**

| 方案 | 是否受签名策略影响 |
|---|---|
| apt 安装 Go / Node / MySQL 客户端 | ❌ **被拒绝** |
| **上传单个静态编译的 Go 二进制** | ✅ **不经过 dpkg，不受影响（已实测运行成功）** |

> **因此：绝不要为了装依赖去关闭麒麟的签名校验。** 那是生产广播系统的安全控制。
> 正确做法就是当前方案 —— **CGO_ENABLED=0 静态编译，产出零依赖单文件**，`scp` 上去直接跑。
> 数据库排障能力由自带的 `doctor` 子命令提供，不依赖 `mysql` 客户端。

### 1.6.9 【重要】数据库建连固定耗时 10 秒的成因与规避

**现象**：从宿主机连 MariaDB，TCP 拨号瞬时完成，但 MySQL 握手**固定耗时约 10.01 秒**；
而**复用已建立的连接执行查询是 0ms**。

**实测数据**（`dbdiag` 工具）：

| 观测项 | 结果 |
|---|---|
| TCP 拨号 `127.0.0.1:3306` | **0s** |
| 第 1/2/3 次**新建**连接 | **10.010s / 10.008s / 10.011s** |
| 复用连接执行 `SELECT COUNT(*)` ×3 | **0s / 0s / 0s** |
| 服务端看到的连接来源 | **`212.218.2.1`** |

**根因**：MariaDB 未开启 `skip_name_resolve`，会对连接来源 IP 做**反向 DNS 解析**。
而本机 Docker 网桥的网关地址被配置为 **`212.218.2.1`** —— 这是一个**公网段地址**，
反向解析请求会真的发往外部 DNS 服务器，一直等到超时（约 10 秒）才继续完成握手。

> 旧 PHP 系统之所以感觉不到，是因为它跑在容器内，来源是同网段的容器 IP；
> 而新版跑在宿主机上，来源变成了网关地址。

**已实施的客户端规避（不改动生产配置）**：

| 措施 | 说明 |
|---|---|
| DSN `timeout=30s` | 避免握手被 10s 超时切断（原先设 10s 恰好与之竞态，导致启动失败） |
| `SetConnMaxLifetime(0)` + `SetConnMaxIdleTime(0)` | 连接建立后**永不因存活/空闲时长被回收** |
| `SetMaxIdleConns == SetMaxOpenConns` | 空闲连接数与上限取齐，池子建好就一直留着 |
| **启动时并发预热** | 8 条连接并发建立，总耗时仍约 10s（串行则需 80s） |
| `max_open: 8` | 池子够用即可，减少偶发重建的概率 |

**实测效果**：启动日志 `连接池预热完成: 8/8 条，耗时 10.011s`，之后所有请求均命中已有连接，接口响应正常。

**建议的根治方案（需停机窗口，由运维决策，本期未执行）**：

在 MariaDB 配置中加入 `skip-name-resolve`，可彻底消除该延迟，**并同时加速旧 PHP 系统的建连**。

> ⚠️ 执行前必须确认两件事：
> 1. **现有账号中没有以主机名（而非 IP 或 `%`）授权的**。开启 `skip-name-resolve` 后，
>    形如 `user@'somehost'` 的账号将无法登录。实测当前 `htweb@%`、`root@%` 均为通配，不受影响，
>    但需完整核对 `mysql.user` 全表后再动手。
> 2. 修改需重启 MariaDB 容器 → **数据库短暂中断** → 广播服务与旧 Web 会受影响，
>    必须安排在非广播时段。
>
> 在未执行根治前，上述客户端规避已足以保证新版稳定运行。

### 1.6.8 数据库账号安全建议

现网 `inc/config.php` 中为 `root` / 明文密码。**新版不要复用 root**，建议：

```sql
-- ⚠️ 这是账号授权（DCL），不是表结构变更（DDL），不违反 R1 红线
CREATE USER 'htweb'@'%' IDENTIFIED BY '<强密码>';
GRANT SELECT, INSERT, UPDATE, DELETE ON audioserver.* TO 'htweb'@'%';
-- 刻意不授予 CREATE / ALTER / DROP / INDEX / REFERENCES
FLUSH PRIVILEGES;
```

> 这在**数据库权限层**为 R1 上了一道硬保险：即使应用代码写错，也**物理上无法执行 DDL**。
> 唯一例外是"恢复备份"（C-40），该功能需单独的高权限账号并独立审批，不与日常运行账号共用。

|---|---|---|
| 1 | **三层嵌套 `while` 写死**，第 4 层递归代码被注释掉 → 第 4 层及以下文件夹**存在于库中但 UI 上完全不可见**，成为孤儿目录 | **一次性 `SELECT` 全表（`filefolder` 数据量极小）→ 在内存中按 `parentid` 建邻接表 → 迭代（非递归）构建任意深度的树**。数据库层仍只读 `id`/`parentid` 两列，零 schema 变更。<br>⚠️ **注意区分"渲染能力"与"业务规则"**：构树实现支持任意深度，是为了**把旧数据中已存在的第 4 层及以下文件夹完整展示出来**（不再产生不可见的孤儿目录）；而**新建时仍强制 3 层上限**（BR-10，已定稿）。两者不矛盾 |
| 2 | 每渲染一个节点就发一条 SQL，N 个节点 = N+1 次查询 | 全表一次取回，查询次数从 O(N) 降为 **1** |
| 3 | `get_folder_info()` 是**读函数却带写副作用**：查录音库时会自动 `INSERT` 一条文件夹并 `UPDATE media SET folderid=...`。并发渲染会重复插入；切换界面语言会按不同语言名重复创建目录 | **读函数纯读**。把"录音归档子目录保障"抽为**独立幂等的初始化任务**（启动时执行一次），且目录名**固定中文**，翻译只在展示层做 |
| 4 | 旧数据可能存在 `parentid` 成环或指向不存在的父节点 → 递归死循环 / 节点丢失 | 构树时用 `visited` 集合**防环**；`parentid` 指向不存在节点的文件夹**挂到"游离节点"分组下展示**（不丢弃、不隐藏），并输出运维告警 |
| 5 | 顶层库 ID 1~9 硬编码散落在十几个文件中 | 收敛为**单一常量配置** `SYSTEM_FOLDER_IDS = [1..9]`、`TTS_FOLDER_ID = 6`、`RECORD_FOLDER_ID = 5`、`TIP_FOLDER_ID = 9` |
| 6 | 语言翻译用硬编码 `switch` 词表，只覆盖 6 个库名 | 移入 i18n 资源文件，按 `filefolder.id` 映射，不依赖名称字符串匹配 |

### 3.1.4 功能 F-04：删除文件夹（递归）

#### 【功能描述】

删除一个或多个文件夹，连同其**整棵子树**的所有子文件夹与媒体一并删除；被任务等对象引用的媒体所在的文件夹不可删除。

#### 【原有实现问题 & 新版优化方案】

| # | 原有问题 | 新版优化方案 |
|---|---|---|
| 1 | **只递归 1 层子级**（`DELETE FROM filefolder WHERE parentid IN (ids)`），三层树中删顶层会留下"孙级"文件夹与其下媒体，成为**永久孤儿数据** | 用 F-01 的内存树**自顶向下收集整棵子树的全部文件夹 ID**（迭代 BFS + visited 防环），对整棵子树统一处理 |
| 2 | **事务语义被完全破坏**：`LOCK TABLES` → `START TRANSACTION` → `COMMIT` → `UNLOCK TABLES`。MySQL 中 `LOCK TABLES` 隐式提交事务、`START TRANSACTION` 隐式释放表锁，**两者混用导致 ROLLBACK 完全无效**。删除中途失败 → 媒体已删、文件夹未删，数据不一致且不可回滚 | **彻底移除 `LOCK TABLES`**，全程单个 InnoDB 事务；需要防并发时对目标 `filefolder` 行用 `SELECT ... FOR UPDATE` 行锁 |
| 3 | 删除子级媒体的循环里，判断与拼路径**用错变量**（用了外层循环残留的 `$row_folder` 而非当前 `$row`）→ 子级媒体的物理文件要么没删（残留垃圾），要么重复删了上一个文件 | 重写为正确的按行处理；随整棵子树逻辑一并重构 |
| 4 | 物理文件用 `system("rm -rf link" . $filename)` —— **命令注入**，且 `filename` 为空时变成 `rm -rf link`，**直接删掉整个媒体链接目录** | 改用 `unlink()`；删除前断言路径非空且 `realpath()` 后仍位于媒体根目录内；空值跳过并记警告 |
| 5 | 物理文件在事务内删除 → 事务回滚了但文件已经没了 | **事务内只收集待删文件清单，`COMMIT` 成功后再删文件** |
| 6 | `whether_have_exit()` 只把 1~5 加入保护名单，**遗漏 6/7/8/9**（虽然外层单独判了，但两处规则不一致） | 保护名单统一为单一常量 `SYSTEM_FOLDER_IDS = [1..9]` |
| 7 | 引用校验只查 `mediaoftask`，**漏查 `shortcutkeytask` / `alarmgroupmap` / `playbelloftask`** | 引用校验链补全为 4 项（见 BR-23） |
| 8 | 逗号分隔的 ID 串直接拼进 `IN (...)` —— 注入 + 超长 SQL 风险 | ID 解析为整型数组 → 逐个校验 → **分批（≤1000/批）用 `?` 占位符绑定** |
| 9 | 异常路径直接 `exit`，`UNLOCK TABLES` 永不执行 → **表锁悬挂，阻塞其它请求** | 移除表锁；资源释放走 `try/finally` |

#### 【数据库】

| 步 | 操作 | 表·字段 |
|---|---|---|
| 1 | 系统保留校验：`id ∈ 1..9` → 拒绝 | `filefolder.id` |
| 2 | 收集整棵子树 ID（内存树，迭代 + 防环） | `filefolder.id`, `filefolder.parentid` |
| 3 | 取子树内媒体：`SELECT id, filename, folderid FROM media WHERE folderid IN (?,?,…)` | `media.id/filename/folderid` |
| 4 | 引用校验（4 项，见下）；命中则该文件夹及其**祖先链**标记为不可删 | `mediaoftask.mediaid`、`shortcutkeytask.mediaid`、`alarmgroupmap.mediaid`、`playbelloftask.bellid` |
| 5 | 级联清理：`DELETE FROM camer_alarmofmedia WHERE mediaid IN (…)` | `camer_alarmofmedia.mediaid` |
| 6 | 删媒体：`DELETE FROM media WHERE folderid IN (…)` | `media.folderid` |
| 7 | 删文件夹：`DELETE FROM filefolder WHERE id IN (…)` | `filefolder.id` |
| 8 | 提交后删物理文件（**跳过 `media.id = 1`**） | — |
| 9 | 通知后台：`file?state=0&id=<folderIds>` + `file?state=0&id=3` | — |

**DDL 变更：无。** 完整递归仅依赖已有的 `filefolder.id` / `filefolder.parentid`。

见 [§4.3.4 `DELETE /api/folders`](#434-delete-apifolders)

| # | 规则 |
|---|---|
| BR-21 | **系统预置文件夹 (id 1~9) 一律禁止删除**（任何角色） |

## 3.2 业务域二：媒体资源管理

### 3.2.1 功能 F-05：媒体列表查询（分页 + 筛选）

#### 【功能描述】

分页展示指定文件夹下的媒体，支持按名称/类型模糊搜索、按大小排序，并显示该文件夹的媒体总容量。

#### 【原有实现问题 & 新版优化方案】

| # | 原有问题 | 新版优化方案 |
|---|---|---|
| 1 | **翻页丢失搜索条件**（用户可感知的最大缺陷）：筛选是 POST，分页链接是 GET 且不带 `searchkey/searchvalue/orderby` → **翻到第 2 页筛选全部失效**，展示的是未筛选的全量数据 | 筛选统一改 **GET**，全部条件进 URL query；分页链接携带完整查询参数 |
| 2 | **同一条完整 SQL 执行两遍**：先无 LIMIT 查一次仅为取行数，再带 LIMIT 查一次 | `SELECT COUNT(*)`（同 WHERE，不带 ORDER BY）+ `SELECT ... LIMIT ? OFFSET ?` |
| 3 | 分页组件里"共 N 页"写死 `ceil(total/18)`，与实际 `limit` 解耦 | 由分页服务统一返回 `{total, page, pageSize, totalPages}` |
| 4 | `page` 参数**先用后判**、无类型与边界校验：`page=0` → `LIMIT -18,18` **SQL 语法错误**；传字符串直接拼进 SQL | `page = max(1, int(page))`；`pageSize` 白名单；超出总页数返回空列表而非报错 |
| 5 | 非 admin + 按名称搜索 + 不排序 的分支里 `"FROM media"` 后紧跟 `"WHERE"` → 生成 **`FROM mediaWHERE`**，该分支必然 SQL 报错、页面 die | 随查询构造器重写统一消除 |
| 6 | **TTS 过滤口径不一致**：无筛选分支**不过滤** TTS，有筛选分支才过滤；且一处用 `filename!='tts'`、另一处用 `typeid!='tts'` | 提到公共 WHERE 片段，**统一为 `typeid <> 'tts' AND filename <> 'tts'`**，所有分支一致 |
| 7 | 目录容量统计把该文件夹**所有行的 `size` 取回 PHP 再累加** | `SELECT COALESCE(SUM(size),0) FROM media WHERE folderid = ?` |
| 8 | 排序字段直接来自用户输入拼进 `ORDER BY` | **白名单映射**：`{'size' → media.size DESC, 'id' → media.id DESC}` |
| 9 | `LIKE` 关键字未转义 `%` `_` `\` | 转义后再绑定 |
| 10 | 用户名字符串 `'admin'` 硬编码判定管理员，与"用户组=1"的判定标准不一致 | 统一用 `usergroupid = 1` 判定管理员 |
| 11 | "能否建子目录"判定 SQL 带 `(userid=$userid or userid=0)` —— `userid=0` 是无意义条件；且逻辑与树渲染耦合 | 改用内存树算深度 |

| 项 | 内容 |

| BR-29 | **TTS 占位记录（`typeid='tts'` 或 `filename='tts'`）在所有普通媒体列表中不显示** |
| BR-30 | 可见范围：**任何登录用户都看得到该文件夹下的全部媒体**，不按 `media.userid` 收敛（见 BR-05）。<br>⚠ 改过一次：原为"普通用户只看自己上传的媒体"。能不能删仍然只看归属 |

> ✅ **已定稿（2026-08-22 产品确认）**：**媒体按"只看自己上传的"过滤，目录按"共享则全员可见"过滤**，两者互不混淆：
> - **媒体（`media`）**：普通用户 `WHERE media.userid = :currentUserId`，**即使媒体位于共享目录内，也只显示自己上传的**。
> - **目录（`filefolder`）**：普通用户 `WHERE priority = 1 OR userid = :currentUserId`，共享目录全部可见、可进入。
>

> 列表不再标注"仅显示我上传的媒体"—— 现在谁都看得到全部媒体，没有可解释的差异了。

### 3.2.2 功能 F-06：上传媒体

#### 【功能描述】

#### 【原有实现问题 & 新版优化方案】

| # | 原有问题 | 新版优化方案 |
|---|---|---|
| 1 | 上传接口**无会话校验、无权限校验**，任何人可直接 POST | 强制校验：已登录 + `mediapriv` 或管理员 + 非备机模式 + 目标文件夹存在且用户有权访问 |

### 3.3.1 功能 F-11：登录认证

#### 【功能描述】

#### 【原有实现问题 & 新版优化方案】

| 2 | SQL 注入防护只是 `and`/`or`/`updatexml`/`extractvalue` **关键字黑名单**，可被大小写、编码、注释绕过 | 全部改预处理 + 参数绑定，**移除黑名单** |

| 4 | 登录失败计数逻辑（错 5 次禁用）**被注释停用** | 恢复该能力，仍写入 `logincheck` 表的 `ip`/`loginnum`/`logintime` 三列，**不新增字段** |
| 5 | 登录后不重新生成 session id → 会话固定攻击 | `session_regenerate_id(true)` / 签发新 token |
| 6 | 会话失效只判"是否为空"，无超时 | 增加空闲超时与绝对超时 |
| 7 | 用户名/密码长度限制通过 `exit` 硬中断，提示语混用"信息错误" | 明确的字段级错误提示 |
| 8 | `book_admin.usersessionid` 用于单点互踢，但新旧系统会互相覆盖 | **新版不依赖该列做互踢**，避免踢掉旧 Web 的会话（见 §7.4） |

### 3.3.3 功能 F-13：共享与数据可见范围（★最容易出错，必须原样保留）

#### 【功能描述】

`filefolder.priority` 是文件夹的**共享标记**，决定该文件夹对哪些用户可见。这是本系统权限模型的核心。

#### 【共享语义】

| `priority` | 含义 |
|---|---|
| `1` | **共享** —— 所有用户可见 |
| `0` | **不共享** —— 仅创建者（`filefolder.userid`）可见 |

6 个系统预置顶层库全部为 `priority = 1`。

#### 【各入口的可见范围规则】

| 入口 | 旧系统规则 | 新版处理 |
|---|---|---|
| 文件管理·媒体列表 | `username=='admin'` → 全部；其他 → 只看 `media.userid = 自己` | 管理员判定改为 `usergroupid=1`，其余**语义不变** |
| 文件夹管理·列表 | 用户组=1 → 全部；否则 `filefolder.id='0' OR filefolder.userid = <用户组ID>` | **修复**：改为 `priority = 1 OR userid = <用户ID>` |
| 任务媒体选择树·顶层 | `parentid=0 AND id!=6 AND (priority=1 OR userid = <用户ID>)` | **语义不变** |
| 任务媒体选择树·子级 | admin → 全部；其他 → `userid = <用户ID>` | **语义不变** |
| 分区（终端）可见 | admin → 全部；其他 → `serverplaystream.userid = <用户ID>` | **语义不变** |
| 终端可见 | admin → 全部；其他 → `terminal.id IN (SELECT terminalid FROM userterminal WHERE userid = <用户ID>)` | **语义不变** |

#### 【原有实现问题 & 新版优化方案】

| # | 原有问题 | 新版优化方案 |
|---|---|---|
| 1 | **归属判定字段用错**：`filefoldermanager.php` 取的是 `book_admin.usergroupid`（用户组 ID），却拿它去比 `filefolder.userid`（该列语义是**创建者用户 ID**）。而其它页面用的是 `$_SESSION['userid']`（用户 ID）。→ **同一个用户在"文件夹管理页"和"文件管理页"看到的文件夹集合不一致**；用户组 ID 恰好等于某个用户 ID 时会看到别人的私有文件夹 | **统一按用户 ID 判定归属**：`filefolder.userid = :currentUserId`。字段完全不变，只改比较用的变量来源 |
| 2 | 非管理员分支写 `WHERE filefolder.id = '0' OR ...` —— `id` 是自增主键，**不可能为 0**，是恒不成立的死条件（原意应为"共享"） | 按真实业务语义改为 `(filefolder.priority = 1 OR filefolder.userid = :uid)` |
| 3 | 媒体列表按 `media.userid` 过滤，任务媒体选择树按 `filefolder.priority` 过滤，两个入口对同一共享目录呈现的内容不同，用户困惑 | ✅ **已重新定稿**：两个入口都**不再按创建者收敛** —— 文件管理对所有登录用户开放（BR-05 / BR-30），差异随之消失 |
| 4 | 共享属性在新建/修改页被注释隐藏 → 新建恒共享、改名会把不共享改成共享 | 恢复共享开关（见 F-02 / F-03） |
| 5 | 可见范围过滤是"查完再在 PHP 里判断"，存在越权读取窗口 | **过滤条件下沉到 SQL 的 WHERE 子句**，数据库层面就不返回无权数据 |

#### 【数据库】

| 项 | 内容 |
|---|---|
| **表** | `filefolder`、`media`、`book_admin`、`usergroup`、`userterminal`、`serverplaystream` |
| **关键读字段** | `filefolder.priority`（共享标记）、`filefolder.userid`（创建者）、`media.userid`（上传者）、`book_admin.id`、`book_admin.usergroupid` |
| **写字段** | 仅 `filefolder.priority`（在 F-02/F-03 中写） |
| **文件夹可见 WHERE** | 管理员：无条件；普通用户：`(filefolder.priority = 1 OR filefolder.userid = :uid)` |
| **媒体可见 WHERE** | 管理员：无条件；普通用户：`media.userid = :uid` |
| **关联** | `filefolder.userid → book_admin.id`；`media.userid → book_admin.id`；`media.folderid → filefolder.id` |
| **DDL 变更** | **无** |

#### 【业务规则】

| # | 规则 |
|---|---|
| BR-84 | `filefolder.priority = 1` → 全员可见；`= 0` → 仅创建者可见 |
| BR-85 | 归属判定一律用 **`filefolder.userid` ↔ 当前登录用户的 `book_admin.id`** |
| BR-86 | 6 个系统预置顶层库恒为共享，其共享属性不可修改 |
| BR-87 | 媒体的可见范围按 `media.userid` 判定（保持旧语义） |
| BR-88 | 管理员（`usergroupid = 1`）不受可见范围限制 |
| BR-89 | 可见范围过滤必须在 SQL 层完成，不得"查完再过滤" |

# 4. 新版 API 接口文档

## 4.1 通用约定

### 4.1.1 基础

| 项 | 约定 |
|---|---|
| Base URL | `/api` |
| 编码 | UTF-8 |
| 请求体 | `application/json`（文件上传用 `multipart/form-data`） |
| 认证 | `Authorization: Bearer <token>` 或 Session Cookie |
| 时间格式 | `yyyy-MM-dd HH:mm:ss`（**东八区**，与旧系统一致） |

### 4.1.2 统一响应体

> ⚠️ **本节契约已对齐前端基座 Geeker-Admin**，取自其
> `src/enums/httpEnum.ts`（`ResultEnum.SUCCESS = 200`、`OVERDUE = 401`）与
> `src/api/interface/index.ts`（`Result` / `ResultData` / `ResPage`）。
> **信封字段是 `code` / `msg` / `data`（注意是 `msg` 不是 `message`），成功码是 `200` 不是 `0`。**
> 不改模板的 `useTable`/请求拦截器，以免后续升级冲突。

```jsonc
// 成功
{ "code": 200, "msg": "ok", "data": { } }

// 分页（字段名与顺序必须与 ResPage<T> 一致）
{ "code": 200, "msg": "ok",
  "data": { "list": [], "pageNum": 1, "pageSize": 18, "total": 123 } }

// 失败（业务错误码放在 code，前端拦截器会自动 ElMessage.error(msg)）
{ "code": 40901, "msg": "媒体正在被任务使用，不能删除",
  "data": { "blocked": [ { "mediaId": 12, "mediaName": "上课铃", "reason": "TASK", "refName": "早读方案" } ] } }

// 会话过期（前端拦截器识别 401 并跳登录）
{ "code": 401, "msg": "登录已过期，请重新登录", "data": null }
```

**前端拦截器行为（`src/api/index.ts`，不改动）**：
- `data.code === 200` → 正常返回
- `data.code === 401` → 弹提示 + 跳登录
- `data.code` 存在且 ≠ 200 → `ElMessage.error(data.msg)`
- 无 `code` 字段 → 视为文件流（下载接口走这条路径，**下载/试听接口不要包信封**）

**功能**：获取文件夹树（任意深度）　**权限**：登录

```jsonc
{ "code": 0, "data": {
    "rootName": "文件管理",
    "tree": [
      { "id": 1, "name": "共享媒体库", "parentId": 0, "userId": 1, "shared": true,

            "createTime": "2021-03-30 11:07:22", "system": true, "depth": 2,
            "canCreateChild": true, "canModify": false, "canDelete": false,
            "mediaCount": 1, "children": [] }
        ] },
      { "id": 2, "name": "铃声媒体库", "parentId": 0, "shared": true, "system": true,
        "depth": 1, "mediaCount": 15, "children": [] }

```

**字段业务含义**

| 字段 | 来源 |
|---|---|
| `id` / `name` / `parentId` / `userId` / `createTime` | `filefolder.id/name/parentid/userid/createtime` |
| `shared` | `filefolder.priority == 1` |
| `system` | `id ∈ [1..9]` |
| `depth` | 应用层由树计算，**非数据库字段** |
| `canCreateChild` | `depth < 3`（业务规则 BR-10） |
| `canModify` / `canDelete` | `!system && (isAdmin \|\| userId == 当前用户)` |
| `mediaCount` | `SELECT folderid, COUNT(*) FROM media WHERE typeid<>'tts' AND filename<>'tts' GROUP BY folderid`（一次聚合，非 N+1） |
| `orphans` | `parentid` 指向不存在节点的文件夹 |

**规则**

### 4.4.2 POST /api/media/upload

**功能**：上传媒体　**权限**：`mediapriv` 或管理员；非备机；目标非录音库

**请求**：`multipart/form-data`

| 字段 | 类型 | 必填 | 约束 |
|---|---|---|---|
| `folderId` | int | 是 | 目标文件夹 |
| `file` | file | 是 | mp3 / wav；≤300MB |
| `onConflict` | string | 否 | `overwrite`（默认，与旧版一致）/ `skip` / `rename` |
| `chunk` / `chunks` / `uploadId` | — | 否 | 分片上传参数 |

**冲突预检**：`POST /api/media/upload/precheck`
请求 `{ "folderId": 2, "names": ["上课铃", "下课铃"] }`
响应 `{ "code":0, "data": { "conflicts": [ { "name":"上课铃", "existingId":130 } ] } }`

**响应**
```json
{ "code": 0, "data": {
    "results": [
      { "fileName": "上课铃.mp3", "status": "created",  "mediaId": 156, "sizeKB": 289 },
      { "fileName": "下课铃.wav", "status": "overwritten", "mediaId": 133, "sizeKB": 310 },
      { "fileName": "坏文件.mp3", "status": "failed", "errorCode": 50002, "message": "转码失败" }
    ],
    "notified": true } }
```

`status` 取值：`created` / `overwritten` / `skipped` / `renamed` / `failed`

**服务端处理流程**
1. 校验登录、权限、备机模式、目标文件夹合法性、录音库限制
2. 校验扩展名与大小
3. 接收（分片则合并）
4. **ffmpeg 转码**（`escapeshellarg` 转义所有参数）：统一 mp3、128k、双声道；`folderId==9` → 16000Hz，否则 44100Hz；**尾部 concat 2 秒静音**
5. 校验 ffmpeg 退出码与产物文件；失败 → 清理并返回 `50002`
6. `GET_LOCK('media_upload_<folderId>', 5)`
7. 查重 → `INSERT` 或 `UPDATE`
8. `RELEASE_LOCK`
9. 发送 `file?state=1&id=<folderId>`

**写入字段**：见 [§3.2.2 数据库](#322-功能-f-06上传媒体)。**必须遵守 BR-41 ~ BR-49 的写入契约。**

**错误**：`40001` `40301` `40302` `40304` `41301` `41501` `50002` `50003`

## 5.2 核心表：`filefolder`（媒体文件夹树）

| 字段 | 类型 | 默认 | 业务含义 | 读 | 写 |
|---|---|---|---|---|---|

## 7.3 后台服务联动契约（必须实现）

| 触发时机 | 发送内容 | 不发的后果 |
|---|---|---|
| 上传媒体成功后 | `file?state=1&id=<folderid>` | 后台不知道有新媒体 |

| 删除文件夹成功后 | `file?state=0&id=<folderids>` + `file?state=0&id=3` | 同上 |

## 7.4 并发共存风险与应对

| 风险 | 场景 | 应对（纯应用层） |
|---|---|---|
| **表锁冲突** | 旧 Web 执行 `LOCK TABLES media WRITE` 期间，新版所有 media 读写被阻塞 | 新版查询设置合理超时并重试；事务尽量短；**新版自身绝不使用 `LOCK TABLES`** |
| **上传同名竞态** | 新旧 Web 同时上传同名文件到同一文件夹 | `GET_LOCK('media_upload_<folderid>')`。⚠️ **旧程序不参与这把锁** → 读取端仍需容忍同名多条（按 `id` 取最新一条） |
| **删除竞态** | 新版正在删文件夹，旧 Web 同时往里上传 | 删除事务内对目标 `filefolder` 行 `SELECT ... FOR UPDATE`；删除后再次校验并清理残留 |
| **自增 ID 争用** | 两端同时 INSERT | MySQL 自增保证。**前提：新版不手工指定 id** |
| **孤儿数据** | 旧 Web 删文件夹只递归 1 层，留下孤儿目录/媒体 | 新版读取端必须**容忍并展示**：`parentid` 指向不存在节点的文件夹挂到"游离节点"分组；孤儿媒体在任务清单中用 LEFT JOIN 显示 |
| **会话互踢** | `book_admin.usersessionid` 被两端互相覆盖 | **新版不依赖该列做单点互踢**，避免踢掉旧 Web 会话 |
| **权限缓存不一致** | 旧 Web 改了用户组权限，新版会话内仍是旧快照 | 新版权限每请求校验（短 TTL 缓存），不长期缓存 |
